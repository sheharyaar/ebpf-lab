Maps: layout, choosing, sharing

The write counter and its loader never talk to each other. They share one hash map, which the kernel built at 83,968 bytes before the first write, and each of the other map types the counter could use moves that cost somewhere else, into memory for every CPU, into a lock, or into the copies that user space makes to read it.

The counter's map, from its loader and from bpftool

We start with the loader as written, run in while one shell writes ten times a second. From round 1 on it prints one thread and its count forever, and Ctrl-C does not stop it, which is why stopped it with pkill. bpftool needs nothing from the loader to see the same map, because for root it turns the map's ID into a descriptor of its own and asks the kernel what the map is.

$ sudo bpftool map show name write_counts
7: hash  name write_counts  flags 0x0
        key 4B  value 8B  max_entries 1024  memlock 83968B

The type, the two sizes and max_entries come from the map's definition in hashmap.bpf.c, while memlock is what the kernel made of them (book/labs/ch09-root.sh). A thread ID and its count take 12 bytes, so 1,024 of them would fill 12,288, yet the map was charged 83,968 bytes before the first write was counted. The next two sections account for the difference, and the endless line waits for the section on user space, since its cause lies in how a map hands out its keys.

What BPF_MAP_CREATE built

When libbpf sends BPF_MAP_CREATE, the kernel reads the map type first. BPF_MAP_TYPE_HASH selects htab_map_ops (line 2358 of kernel/bpf/hashtab.c), a table of twenty function pointers for creating, looking up, updating and walking this kind of map, and each of the 35 map types in v7.2 has its own.

htab_map_alloc() (line 545) then builds what shows. It rounds max_entries up to a power of two and makes that many buckets, list heads with a lock each. It also makes every element in advance, 64 bytes holding list links, the stored hash, the 4-byte key and the 8-byte value, each rounded up to 8 bytes, with 16 spares beyond max_entries, one per CPU, for updates. htab_map_mem_usage() adds the parts up for the memlock line, 83,968 bytes at the foot of , and a map created with BPF_F_NO_PREALLOC makes its elements as keys arrive instead.

A key finds its bucket by hashing. While it builds the map, htab_map_alloc() draws a random seed for it. A lookup hashes the 4-byte key with jhash2() and that seed, keeps the low ten bits of the result, since 1,024 is a power of two, and walks that bucket's list, comparing the stored hash before the key bytes. The walk takes no lock and runs under RCU, so an element it is passing may be moved to another bucket while it walks. Each list therefore ends in a marker that names its own bucket, and a walk that reaches another bucket's marker starts again.

The memory is charged to the memory cgroup of the process that created the map, with one exception in v7.2 that measures. The per-CPU values a map makes when it is created are allocated before the map records that cgroup, so they are charged to no group at all.

From the counter to the map, and back

The counter names the map in a wide instruction that holds the descriptor libbpf wrote in. At load, check_and_resolve_insns() (verifier.c line 18095) swaps the descriptor for the map's kernel address, which bpftool prints as map[id:7], and add_used_map() records the map in the program's used_maps with a reference, which makes the program one of the map's holders (). A later pass rewrites the calls, as followed in detail, so that in call 1 has become a direct call to __htab_map_lookup_elem() followed by two instructions, and the update a direct call to htab_map_update_elem().

The two added instructions decide what the counter gets back. When no element holds the key, r0 is NULL, the pointer-or-NULL of . Otherwise r0 += 56 moves from the element's address to its value's, past the element's 48-byte header and the key rounded up to 8 bytes (htab_map_gen_lookup(), line 776), and the program holds a pointer into kernel memory that it may read and write with no copy.

The atomic add at slot 13 targets r10 -16, a copy of the value on the stack, so the map changes only at slot 26. There htab_map_update_elem() takes the bucket's lock, links in this CPU's spare element holding the new count, and keeps the old element as the next spare. Two threads never share a key in the counter, so this copy-and-update counts correctly, and what it costs when keys are shared waits for .

The same map from user space

Only programs get a pointer, and user space reaches the same struct bpf_map in the other ways of . The loader uses the descriptor that BPF_MAP_CREATE returned and bpftool one it made from the ID, and each descriptor, like a pin, holds a reference that counts among the map's holders.

Every read from user space is a copy. BPF_MAP_LOOKUP_ELEM runs the same lookup from the ops table, then bpf_map_copy_value() (syscall.c line 309) copies the value out, one system call per key. Arrays created with BPF_F_MMAPABLE, ring buffers and arenas can skip the copies through mmap().

BPF_MAP_GET_NEXT_KEY takes a key and returns the key after it, in bucket order, and given NULL, or a key that is not in the map, htab_map_get_next_key() (line 895) returns the first key. The loader passes prev_key, which is 0 and never changes. No thread has ID 0, so every call returns the same first key, and the inner loop never ends or reads the flag that the Ctrl-C handler sets.

The other map types in the table change the layout but keep the route. A per-CPU map keeps one copy of every value for each CPU, so that programs on different CPUs never write the same memory, and user space reads all the copies in one call. A perf buffer is an array of per-CPU buffers that programs write events into. A ring buffer, since 5.8, is one buffer for all CPUs, built, its documentation says, to share memory across CPUs and keep events in order. An arena, since 6.9, is a set of pages that the program and the process both map; this chapter weighs only its memory, and the next chapter, on memory a program manages itself, teaches it.

From here on we weigh these types against each other by what they cost in memory, locks and copies, all on the same kernel, before choosing one for the counter.

What a layout weighs before the first event

weighs the layouts at the counter's size. An array costs 8.3 bytes an entry, the values alone. A hash costs 82, a 64-byte element and a 16-byte bucket an entry, as drawn in . The per-CPU forms keep a value for every possible CPU, so the counter's map as a PERCPU_HASH would take 209 bytes a thread.

Hashes and arrays are made in advance by default, so max_entries reserves memory as well as capping it. A hash created with BPF_F_NO_PREALLOC starts at 17,280 bytes and reaches 91,008 when full. The work moves onto the event path, since every update takes a fresh element from a per-CPU cache that kernel/bpf/memalloc.c refills, and frees the old one; the counter's update grew 43 ns slower.

The kernel charges a map's memory to the memory cgroup of the process that created it, while memlock is the map's own estimate from its map_mem_usage function. For a hash of 65,536 entries the two agreed within 2 KB. They part for an arena, whose arena_map_mem_usage() returns 0 while each page is charged as it is first touched.

Per-CPU values and the cgroupA preallocated per-CPU hash of 65,536 entries reports 13,632,384 bytes, but its creator's memory.current rose by 5.5 MB, the elements and buckets, and the percpu line of memory.stat not at all. map_create() in syscall.c calls the type's map_alloc before bpf_map_save_memcg() records the cgroup, and bpf_map_alloc_percpu() charges the recorded one, the root until then, which is never charged.

Who waits when several CPUs count

A lookup walks its bucket under RCU and takes no lock, so the waiting in is all on writes. With one writer the counter's lookup and update cost 92 ns more than reading the key alone, for the bucket lock and the swap of the spare element. The lookup and an add through its pointer with __sync_fetch_and_add(), one locked instruction on x86, cost 32.

Eight writers on one key show what the lock does not protect. The counter's lookup, copy and update lost 66 per cent of the counts. Two CPUs read the same old value and each stored its own sum, a lost update, and the bucket lock only made the stores take turns. The atomic add lost nothing. Its price is the cache line, the 64-byte block in which a CPU caches memory, which must travel to whichever CPU writes it next; sharing one took the add from 533 to 714 ns.

A per-CPU map gives each CPU its own copy, so no line travels and a plain add is safe from other CPUs. The price is paid on reading, where user space copies all 16 values of a key and sums them. The copy is private to a CPU but shared by every program on it. An NMI or, on this kernel, a task switch () can slip another program between a load and its store, so a value two programs write wants the atomic add too.

Re-entryIn v7.2 the bucket lock is a resilient spin lock, which returns an error where a spin lock would wait forever: ‑EDEADLK when this CPU already holds it, ‑ETIMEDOUT when a wait passes RES_DEF_TIMEOUT, a quarter of a second. Before 6.15 (commit 4fa8d68aa53e) a per-CPU counter returned ‑EBUSY instead.

What reading the counts costs user space

Every count that user space reads crosses into it as a copy, and the way it asks sets the price. Looking up a known key took 767 ns, and the loader's walk, a next-key call and a lookup for each key, 1,568 ns a key. A per-CPU hash cost 1,084 ns a key for its 16 values, while one BPF_MAP_LOOKUP_BATCH call that fetched all 1,024 keys of a hash came to 95 ns a key. An array created with BPF_F_MMAPABLE and read through mmap() took a quarter of a nanosecond a key, which makes it the place for a count that user space polls often (book/labs/costs-mapread.c, run by book/labs/costs2-root.sh).

A stream is read by a reader that sleeps until data arrives, and each wake-up, the kernel making that reader runnable again, costs it a context switch. A perf buffer is one buffer per CPU, and libbpf asks perf to wake the reader after every event. The ring buffer is one buffer for all CPUs, and bpf_ringbuf_commit() queues a wake-up only when the reader has caught up to the record just committed. With four writers that held the reader to 5 switches per 1,000 events, against 121 for the perf buffer ().

Queued as interrupt work from inside the program, the wake-up cost the program microseconds per event in this VM. Skipping it trades delay and loss. Submitted with BPF_RB_NO_WAKEUP and read every 10 ms, a ring buffer lost 9.8 per cent of four writers' events when its 256 KiB filled. A perf buffer that woke its reader every 64 events left the last 30 of a paced run unread.

"bpf_ringbuf_commit() implementation will send a notification of new record being available after commit only if consumer has already caught up right up to the record being committed."

Which contexts may use which maps

Two rules in come from check_map_prog_compatibility() in verifier.c. Kprobe, tracepoint, perf_event and raw tracepoint programs may not use a value holding a bpf_spin_lock, a lock inside a map value for changing several fields together. Sleepable programs may use only the types on a list of twenty-one, which takes in queues, stacks, tries, maps of maps and arenas, though its message names only "array, hash, ringbuf and local storage maps"; a perf buffer is not on it.

A map for the counter

A busy server creates thread IDs without end, and each is written by one thread at a time. therefore leads the counter to an LRU hash, which evicts the least recently used entry where a full hash refuses a new thread (). The listing adds the count in place and updates only to insert.

u64 one = 1, *v = bpf_map_lookup_elem(&write_counts, &pid);
if (v)
	__sync_fetch_and_add(v, 1);        /* no lock, no copy */
else
	bpf_map_update_elem(&write_counts, &pid, &one,
			    BPF_NOEXIST);   /* a new thread */

With one writer at the write tracepoint this cost 81 ns a run against 152 for the counter as written less its bpf_printk(), which alone added 350 to 1,100 ns, and the map holds at 82,816 bytes (). A per-CPU form would buy nothing, as no key is shared, for 209 bytes a thread. No map recovers 's lost events, because a run skipped as a recursion miss never reaches the map; only a hook where preemption is off brings them back. An LRU hash forgets the threads written least recently, and keeping a count for every thread a server ever ran, in memory fixed in advance, needs approximate counts, for which builds a map type.

Maps of maps

A map of maps is an array or a hash whose values are other maps, the inner maps; each slot holds a pointer to its inner map and a reference on it (). Since the verifier cannot know which inner map a slot will hold, the outer map copies the shape of a sample map into a template when it is created (bpf_map_meta_alloc()). The program's second lookup is checked against the template, and bpf_map_meta_equal() refuses any inner map that differs in type, key or value size, flags or special fields. A template hash of 1,024 entries accepted a hash of 64 and refused, with ‑EINVAL, a hash with 16-byte values and an LRU hash.

The price is the first lookup. By 's method a hash lookup took 14.0 ns alone, 14.9 through an array of maps, whose lookup the kernel writes in place as index arithmetic, and 28.3 through a hash of maps. An array of 1,024 slots weighs 8,496 bytes, and each inner map is charged as a map of its own.

Where the numbers come fromSteps 2, 3 and 6 of book/labs/ch16-root.sh, run as root in a virtme-ng VM of kernel 7.2.15 with 16 virtual CPUs, 12 November 2026.

The return is a swap. One update points a slot at a fresh map, and maybe_wait_bpf_programs() in syscall.c then waits for an expedited RCU grace period. When the call returns, no program other than a sleepable one can still be writing into the old map. The counter could therefore swap in an empty map every second and read the old one at leisure, a snapshot for 7 to 45 µs an update.

Inside the v7.2 source

lists the code this chapter has read, in the order a map's life reaches it. map_create() checks the attributes, and map_create_alloc() indexes bpf_map_types[] with the map type to find the ops table and calls the type's map_alloc. Only after that returns does map_create() record the creator's memory cgroup, which is why the per-CPU values made inside map_alloc are charged to no group. The verifier reaches the map when a program names it, swapping the descriptor for an address and checking that the program's type may use the map.

At run time the counter's lookup lands in __htab_map_lookup_elem(), three calls long: the hash, the bucket and the walk. Its update goes through htab_map_update_elem(), which takes the bucket's resilient lock and asks alloc_htab_elem() for an element, the CPU's spare when the key exists, the next free element when it is new, and -E2BIG when none is left. A map of maps adds three steps of its own in map_in_map.c, and an update of one waits in maybe_wait_bpf_programs().

Each keyed map in this chapter hands a program slots that BPF_MAP_CREATE sized in advance, a key and a value of fixed size and at most max_entries of them, and a value holds bytes. A pointer that a program stores into a value is refused, or comes back from a later load as a plain number, unless the map's BTF declares a field for it, a typed slot for a kernel pointer that the next chapter takes up (check_mem_access() in verifier.c). A list that a program grows one node at a time, a tree it keeps in order, or an object it allocates in one run and finds again in the next needs memory that the program allocates and frees itself, and that is where the next chapter starts.

What it costs

CPU
One writer, over 48 ns for reading the key: 92 ns for the counter's lookup and update, 134 without preallocation, 32 for an atomic add in place, 30 for a per-CPU hash, 2 to 6 for arrays (getppid tracepoint). A hash lookup took 14.0 ns alone, 14.9 behind an array of maps and 28.3 behind a hash of maps (kernel 7.2.15, VM with 16 CPUs, 12 November 2026; book/labs/ch15-root.sh, ch16-root.sh).
Memory
Per entry on 16 CPUs, all at creation: 8.3 bytes for an array, 82 for a hash (83,968 for write_counts), 209 for a per-CPU hash; without preallocation a hash grows from 17,280 to 91,008 bytes. A 256 KiB ring buffer takes 275,776 bytes, a perf buffer 266,240 per CPU, an array of maps 304 bytes and 8 a slot (memlock in fdinfo, same VM and day).
Switches
None in the program, which reads through a pointer. User space pays a system call and a copy: 767 ns a key by lookup, 1,568 for the loader's walk, 1,084 for a per-CPU hash, 95 in one batch, a quarter of a nanosecond through mmap(). Four writers woke a ring buffer's reader 5.3 times per 1,000 events and a perf buffer's 121; an inner-map swap took 7 to 45 µs (costs-mapread.c, same VM and day).
Locking
Lookups none; a hash update takes a resilient bucket lock, a ring-buffer reservation one lock for all CPUs, an atomic add a cache line. Eight writers sharing one key lost 66 per cent of the counter's counts under the bucket lock.

Add in place with an atomic and update only to insert. Go per-CPU when many CPUs write one key, use an LRU hash when keys can outgrow the map, read whole maps in batches or map an array that user space polls, stream through the ring buffer, and pay a map of maps' second lookup only where swapping a whole map is worth it.

When it goes wrong

Most failures with a map are quiet. A program that loses counts still loads and runs, and an update that fails returns an error the counter never reads, so pairs each symptom this chapter met with its usual cause and the command that tells it apart. The first three rows belong to the counter and its loader as written. The fourth and fifth look alike from outside, a total that falls short of the writes, and bpftool prog show separates them, since run_cnt counts the runs that happened and recursion_misses, printed only when it is not zero, the runs that were skipped.

In the middle rows the kernel's own accounting is the witness, memlock against the cgroup's charge and an error code that names a lock. Two refusals come at load from check_map_prog_compatibility(), as soon as the program names the map, and the last rows are a stream that drops or delays events and a map of maps that refuses an inner map. Recap

A map is a struct bpf_map whose type picks an ops table, and the counter's hash is an array of buckets, each with a resilient lock, whose elements are all made in advance by default, 83,968 bytes for 1,024 entries on 16 CPUs. A lookup hashes the key with the map's seed, walks one bucket under RCU and returns a pointer 56 bytes into the element, or NULL; user space gets copies made by bpf() commands, or the pages of the few map types that allow mmap(), and walking a hash needs the last key it saw. Layouts trade memory for locking: 8.3 bytes an entry for an array, 82 for a hash and 209 for a per-CPU hash, while a lookup, copy and update on a shared key lost two counts in three that an atomic add in place kept. The ring buffer wakes its reader only once it has caught up, the verifier keeps bpf_spin_lock out of kprobe, tracepoint, perf_event and raw tracepoint programs and perf buffers out of sleepable ones, and the counter wants an LRU hash with an atomic add. A map of maps checks each inner map against a template, costs one more lookup, and lets user space swap a whole inner map behind an expedited grace period.

Counting only keys and values gives 1024 × 12 = 12,288, which forgets that every element also carries 48 bytes of links and hash and that every key and value is rounded up to 8 bytes.

The map is full. All 1024 elements were made at creation, and every thread that ever wrote holds one, alive or not. An update for a new key finds no free element and returns -E2BIG (alloc_htab_elem() in hashtab.c), and the counter ignores the return value of bpf_map_update_elem(), so the miss is silent. Updates to existing keys still work, through the per-CPU spares. Check with sudo bpftool map dump name write_counts | grep -c key: it says 1024. Use BPF_MAP_TYPE_LRU_HASH, delete threads as they exit, or raise max_entries. No verifier or instruction limit is involved, since the program loaded long ago and still runs.

From one 8-byte value for each of the 16 possible CPUs. A per-CPU map keeps a separate value for every CPU the machine could ever have, and a lookup from user space returns all of them at once, each rounded up to 8 bytes; libbpf checks the size before it calls the kernel (validate_map_op() in libbpf.c). Pass an array of libbpf_num_possible_cpus() values and add them up. Check the count in /sys/devices/system/cpu/possible, which reads 0-15. Sizing the array by the CPUs online now can fall short, because the kernel counts possible CPUs, which can be more.

1,131,392 bytes as a per-CPU hash and 92,032 as the plain hash. htab_map_mem_usage() in hashtab.c starts from the 896-byte struct bpf_htab and 1,024 buckets of 16 bytes, 17,280 in all. A per-CPU hash adds 1,024 elements of 64 bytes, each holding a pointer where the value would be, and 8 bytes for every value on each of 128 possible CPUs: 65,536 + 1,048,576. The plain hash adds 1,024 + 128 elements, one spare per CPU, and 128 pointers to the spares: 73,728 + 1,024. With 16 CPUs the same sums give 's 213,888 and 83,968. Multiplying the whole 64-byte element by the CPUs, about 8.4 MB, is the usual slip; only the value is kept per CPU.

The nested update found its bucket's lock already held by its own CPU and gave up with ‑EDEADLK, 35 on x86. Replacing an element whose value holds a timer calls bpf_obj_cancel_fields() from check_and_cancel_fields() inside htab_map_update_elem(), with the bucket locked, so the fentry program runs inside the outer update. Its own update asks for the same resilient lock, and check_deadlock_AA() in rqspinlock.c finds that lock in the CPU's list of held locks. The second hash has its own buckets and locks, none of them held. Step 4 of book/labs/ch15-root.sh prints both results. Reading ‑35 as a full map is tempting, but that is ‑E2BIG, ‑7; before 6.15 the answer was ‑EBUSY, ‑16.

A tracepoint program may not use a map whose value holds a bpf_spin_lock at all. check_map_prog_compatibility() in verifier.c refuses such a map for every type that is_tracing_prog_type() lists, kprobe, tracepoint, perf_event and raw tracepoint. The source gives no reason beyond the word "yet", but the list holds the types that can fire in an NMI (), where waiting for a lock the interrupted code holds would never end. fentry is BPF_PROG_TYPE_TRACING, which the list leaves out, so the same code loads there (step 5). The counter needs no lock: __sync_fetch_and_add() changes its one 8-byte count whole, and a lock pays only when several fields must change together. Suspecting the lock helper is natural, but the refusal comes as the map is first named, before any call is checked.

Into lost updates. Keyed by process, all eight threads share one element, and the counter reads the count, adds one on its stack and writes the sum back with bpf_map_update_elem(). Two CPUs that read the same old value both store old + 1, so one count disappears, and the bucket lock only makes the stores take turns. In eight writers on one key lost 66 per cent this way, while run_cnt matched the calls made, which is how to tell this apart from 's misses. Adding one in place with __sync_fetch_and_add() lost nothing, and a per-CPU hash would count every write too. Blaming the hook is natural after , but recursion_misses at zero says every run happened.

About 14.9 ns behind an array of maps and 28.3 ns behind a hash of maps. The first lookup costs what a lookup in that kind of outer map costs: the kernel writes an array-of-maps lookup in place as a few instructions of index arithmetic (array_of_map_gen_lookup() in arraymap.c), which adds under a nanosecond, while a hash of maps first makes a full hash lookup of its own, about 14 ns more. Step 3 of book/labs/ch16-root.sh measured both on kernel 7.2.15 with 16 virtual CPUs. It is tempting to double the time for both, but only the hash of maps pays for a second hash lookup.

What this shows. The counter as written pays for an update on every write, a bucket lock and an element swap, although its key already exists; adding through the pointer that the lookup returned leaves only the lookup and one locked add. The LRU hash weighs about the same as the hash and evicts instead of refusing a new thread.

Common wrong turn. Keeping bpf_map_update_elem() after the add. The count stays right, but every write pays for the bucket lock and the element swap again, and the gain disappears. Switching to PERCPU_HASH instead costs 213,888 bytes and a sum on every read, for keys that no two CPUs write at once.

arena
pages that a program and a process both map and address with pointers, since 6.9
bucket
one slot of a hash map's array: the head of a list of elements, with a lock
cache line
the 64-byte block in which a CPU caches memory, which moves to whichever CPU writes it
element
one entry of a hash map: list links, the stored hash, the key and the value
inner map
a map held in a slot of a map of maps, which must match the outer map's template
lost update
two writers read the same old value and each stores its own result, so one result is lost
map of maps
an array or a hash whose values are other maps, looked up in two steps
map type
the kind of map, which selects the kernel's table of functions for it
per-CPU
keeping one copy of each value for every CPU
perf buffer
an array of per-CPU buffers that programs write events into
resilient spin lock
a spin lock that returns an error on a deadlock or after a timeout instead of waiting forever; the hash map's bucket lock since 6.15
ring buffer
one event buffer shared by all CPUs, in order, since 5.8
wake-up
the kernel making a sleeping reader runnable again when data arrives
