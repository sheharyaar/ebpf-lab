Spine. In the write counter was 27 slots of the machine's instructions, three of them wide and holding zeros where a map or a string belongs. This chapter goes back to the compiler that chose those slots, then follows its output, the object file, up to the moment the loader hands it to the kernel.

The counter's C, and what one command makes of it

is the whole write counter, with the command that compiles it. That command writes an object file of 8,112 bytes, of which the 27 slots of take 216, so most of what clang produces is something other than code. This chapter is about the other 7,896 bytes, and about the choices clang made on the way, from the stack slot it gave to pid to the instruction it picked for line 19.

Three lines of the source decide most of what follows. Line 12 puts the function into a section of the object named after the hook it runs at, the sys_enter_write tracepoint, a fixed, named hook that kernel developers placed in the source at the entry to write(). Lines 4 to 9 declare the map, yet no instruction creates it, and the declaration reaches the object only as a description of types. Line 17 calls a helper by its ID and passes it the map, whose address nobody knows until the kernel has created the map.

The object is read by libbpf, the C library that the counter's loader links against, which reads an object file, creates what it describes in the kernel and attaches it. Part of the object is meant for libbpf alone, while the code and a description of the program's types in BTF, the BPF Type Format, go on into the kernel. BTF is a compact record of types, each struct with its fields and their offsets and each function with its signature. The kernel describes its own types in the same format, which starts to matter as soon as a program reads a kernel struct, as the fork tracer does later in this chapter.

Three stages inside clang

Inside clang the counter passes through three stages, which draws from top to bottom. The front end is the part of clang that parses C and writes it out as LLVM IR, the typed intermediate code that every LLVM target shares, with unlimited virtual registers, each assigned once. The middle runs the general optimisations of -O2, and the back end in llvm/lib/Target/BPF turns the IR into BPF instructions and writes the object.

The BPF target also hooks passes into the shared middle. BPFCodeGenPassBuilder.cpp places BPFAbstractMemberAccess and BPFPreserveDIType at the start of the pipeline, so that reads of kernel struct fields and __builtin_btf_type_id() become records before any optimisation can fold them away. BPFAdjustOpt holds back rewrites that would leave code the kernel's checker cannot follow, the checker that runs at load and that walks through.

"In particular, if bpf program tries to access a particular kernel data structure member, the details of the intermediate member access will be remembered so bpf loader can do necessary adjustment right before program loading."

Header comment of llvm/lib/Target/BPF/BPFAbstractMemberAccess.cpp, LLVM 23.1.4

The counter in IR

is the counter's IR at -O2. The map is a global variable in a section named .maps, the license is a four-byte string in license, and the function carries its SEC() name as its section. A helper has no symbol to call, because bpf_helper_defs.h declares bpf_map_lookup_elem as a constant function pointer whose value is 1. The IR therefore calls inttoptr (i64 1 to ptr), and a pattern in BPFInstrInfo.td turns a call to a constant into call 1, the helper ID of .

The NULL test is an icmp eq against null and a branch, and the atomic add is an atomicrmw add with sequentially consistent ordering. Only pid and updated_val still live in memory, as alloca slots, because their addresses go to helpers. At -O0 every local keeps its stack slot, and the program grows to 38 slots and 56 bytes of stack.

Registers, the stack and the atomic

Instruction selection matches IR operations against the patterns in BPFInstrInfo.td, and register allocation then maps the virtual registers onto r0 to r9, spilling to the stack when they run out. BPFRegisterInfo.cpp reserves r10 as the read-only frame pointer, so every stack slot is an offset below it. BPFCallingConv.td passes arguments in r1 to r5 and returns in r0, the convention that read from the kernel's side.

Six and moreIn v7.2, MAX_BPF_FUNC_ARGS in include/linux/bpf.h is 12: a call to another BPF function or to a kernel function exported for programs may pass arguments six to twelve through a hidden register, r11, and clang 23 announces this with __BPF_FEATURE_STACK_ARGUMENT. Helpers keep five.

A helper takes at most five arguments because struct bpf_func_proto, its prototype in the kernel, has five argument slots (arg_type[5] in include/linux/bpf.h). Once the program is compiled to machine code (), each of them reaches the helper in an x86 argument register. The 512-byte stack is MAX_BPF_STACK in the kernel, and BPFRegisterInfo.cpp checks the same number while it lays out the frame, so an oversized buffer stops the build before the kernel could see it.

The -mcpu option picks the version of the instruction set, and clang 23 defaults to v3 (BPFSubtarget.cpp; clang -target bpf -dM -E prints __BPF_CPU_VERSION__ 3). Version 2 adds less-than jumps, version 3 adds 32-bit jumps and the w registers, and version 4 adds sign extension, byte swaps and signed division; Linux has accepted them since 4.14, 5.1 and 6.6. Only for v4 does clang 23 store a constant to memory in one instruction, without first moving it into a register (HasStoreImm), and compares four builds.

The atomic add is where the version matters most. On v3 the atomicrmw becomes XFADDD, a fetch-and-add with opcode 0xdb and the fetch bit in its immediate. Version 1 has no fetching 64-bit add, so clang emits the older add without fetch while the result goes unused, as here, and BPFMIChecking.cpp stops the build when the result is read.

What the object holds besides code

The map's address is unknown until the kernel creates the map, so each reference to it, prepared by LowerGlobalAddress() in BPFISelLowering.cpp, is selected as LD_imm64, the wide instruction of , with its constant left at zero. BPFELFObjectWriter.cpp records a relocation of type R_BPF_64_64 for each, the note under slots 6 and 21 in the listing of that tells libbpf which instruction to fill in. Two map loads and one .rodata load are why 24 instructions fill 27 slots.

As shows, BTFDebug.cpp also turns the debug information into .BTF, the types, and .BTF.ext, which holds one func info record with the function's type, eleven line info records tying slots to source lines, and no CO-RE records. Each line-info record points at the source text among the BTF strings, which is where the C lines come from when the kernel explains a rejection in . The map definition exists only as BTF, because __uint() turns each number into the length of an array type.

Both sections are made from the debug information, so the -g in the Makefile is what creates them. Built without it, the object has neither, and libbpf refuses the counter as soon as it opens the file, with libbpf: BTF is required, but is missing or corrupted., because the 32 zero bytes of .maps say nothing about the map on their own. We checked this with clang 23.1.4 and bpftool 7.8.0 on 2026-11-12; the same build takes something less visible from the fork tracer, which comes back to.

Why a field offset cannot be fixed at build time

The counter reads no kernel struct, so it cares little which kernel it meets. The fork tracer, a smaller program from hello_world/03-tracepoint, runs at the sched_process_fork tracepoint and prints the pid fields of parent and child, so it reads child->pid. To do that the compiled program needs the byte offset of pid inside struct task_struct. That offset is a fact about one kernel build, and it moves when fields are added or removed and when the kernel's configuration switches fields on or off.

compares three ways to get the right offset into the program. The first compiles on every machine against that machine's headers, which is how BCC worked for years: it ships clang and LLVM inside each tool, compiles at start-up and needs the kernel's headers installed on every host.

The second compiles once, against one kernel, and hopes. On a kernel with a different layout the program reads whatever now sits at the old offset, and nothing warns anyone. The third is CO-RE, compile once, run everywhere, which Andrii Nakryiko described for libbpf in February 2020. The compiler records a question beside each field read, and the loader answers it on the target from that kernel's BTF, so that CO-RE moves some work to load time but keeps it to one lookup for each field the program reads.

Where CO-RE stopsCO-RE fixes offsets, but it cannot bring back a function the compiler inlined, which a probe on that function needs. A EuroSys 2025 study found that biotop broke that way in Linux 5.16, and that 83% of 53 real programs depended on something that changed between kernels.

"After libbpf processed BPF program code, to kernel it looks like any other valid BPF program code. It is indistinguishable from a BPF program compiled right there on the host with up-to-date kernel headers."

BTF, and the 3.5 MB vmlinux.h

The answers come from the kernel's own BTF. As shows, the kernel build makes BTF from the compiler's debug information with a tool called pahole, and the running kernel publishes it at /sys/kernel/btf/vmlinux, which is 6.5 MB on the 7.2 kernel we use. The same file is read twice, once when a header is written from it and again by libbpf on whichever machine loads the program. BTF went into Linux 4.18 in 2018.

The program folder's Makefile writes that header with bpftool btf dump file /sys/kernel/btf/vmlinux format c. The result is vmlinux.h, which holds every type in the kernel, 166,183 lines and 3.5 MB of C for our kernel, so that no kernel headers need to be installed, and both of our programs include it. Its fifth line, a #pragma clang attribute that adds preserve_access_index to every struct and union in the file, tells clang to treat each of them as relocatable, and the next section follows what that does to one field read.

One relocation, from clang to the running kernel

Because of that pragma, the front end writes every read through such a struct as a call to llvm.preserve.struct.access.index. The counter has none, since it never reads through ctx, but a read of ctx->args[2] would add one. BPFAbstractMemberAccess then replaces the call with a global whose name spells out the path to the field, BPFMISimplifyPatchable folds that global into the load instruction, and BTFDebug writes a record about the load into .BTF.ext.

The fork tracer has two such reads. When we run llvm-objdump -dr on it, slot 2 reads w4 = *(u32 *)(r1 + 0xb38), with a line under it: CO-RE <byte_off> [6] struct task_struct::pid (0:95). That line is a CO-RE relocation, a record kept in the object's .BTF.ext section. It says that slot 2's offset field, the 16-bit field of , holds the offset of pid and must be checked at load.

follows the record from compile to load. The offset 0xb38, byte 2872, is right for the kernel the header came from, so on that kernel libbpf writes the same number back. Suppose we copy the object to a server running Ubuntu 20.04's first kernel, 5.4.0-26. libbpf looks up struct task_struct in that kernel's BTF by name and then pid by name, finds it as field 65 at byte 2264, where our 7.2 kernel has field 95, and writes 0x8d8 into slots 2 and 3. Because libbpf matches by name, the field can move without anything breaking.

Asking about another kernelUbuntu 20.04's first kernels shipped without BTF. BTFHub, kept by Aqua Security, publishes BTF files for kernels like that, and libbpf can read one in place of /sys/kernel/btf/vmlinux through its btf_custom_path option. uses one to ask libbpf what it would do there.

In an ordinary libbpf load the kernel never sees the record, and as the field note says, it receives a plain load with the right offset. When the running kernel has no field of that name, libbpf replaces the instruction with a call to a helper that does not exist, number 195896080, and the load fails with failed to resolve CO-RE relocation. That loud failure is what CO-RE offers in place of silence, because the fixed-offset build would have loaded and read the wrong four bytes.

The silence comes back when a build loses -g. Without debug information clang writes no BTF and no relocations, yet the fork tracer still compiles with the same 0xb38 in both loads. libbpf opens and loads it without a warning, since the tracer defines no map that would need BTF. We loaded such a build in a VM running our 7.2.15 kernel on 2026-11-12, and its instructions reached the kernel with 2872 fixed in them, which is right for this kernel and wrong for the 5.4 one.

Inside libbpf and the kernel: who answers the record

The matching we have followed lives in two files of the v7.2 tree. In tools/lib/bpf/libbpf.c, bpf_object__relocate_core() walks the CO-RE records of every program and hands each to bpf_core_resolve_relo(). That function collects the candidates, every type in the kernel's BTF and in its modules' BTF, whose name matches the record's struct once any suffix that starts with three underscores is ignored (bpf_core_essential_name_len()). That rule lets a second definition such as task_struct___old stand for the same kernel struct.

bpf_core_calc_relo_insn() in tools/lib/bpf/relo_core.c then works out the answer for each candidate and stops with field offset ambiguity when two of them disagree, and bpf_core_patch_insn() writes the answer into the instruction. When nothing matches, bpf_core_poison_insn() writes the call to helper 195896080 instead, a number that its comment in the source spells out as 0xbad2310, "bad relo".

The kernel compiles the same matching code, since kernel/bpf/relo_core.c is one line that includes ../../tools/lib/bpf/relo_core.c. check_core_relo() in kernel/bpf/check_btf.c applies records that arrive in the core_relos array of BPF_PROG_LOAD, through bpf_core_apply() in kernel/bpf/btf.c. libbpf takes that path when it writes the whole load as a small BPF program that makes the bpf() calls itself (tools/lib/bpf/gen_loader.c), since such a loader has no copy of libbpf in user space to do the matching for it. In an ordinary load, as for both of our programs, the records stay in user space.

The kernel's own BTF reaches user space through a short file. CONFIG_DEBUG_INFO_BTF builds kernel/bpf/sysfs_btf.c, which publishes the bytes between __start_BTF and __stop_BTF, the section that pahole wrote into the kernel image during the link, as the read-only file /sys/kernel/btf/vmlinux. That file has an mmap handler, btf_sysfs_vmlinux_mmap(), so libbpf 1.8 maps the 6.5 MB instead of copying them (btf_parse_raw_mmap() in tools/lib/bpf/btf.c) and reads the file only when mapping fails.

libbpf opens that file only for an object that needs it. obj_needs_vmlinux_btf() in libbpf.c asks for kernel BTF when the object has CO-RE records or typed kernel symbols, or a program that attaches through the kernel's BTF, as the fork tracer's tp_btf program does and the counter's program does not. We traced both loads with strace in a VM running our 7.2.15 kernel on 2026-11-12. The counter's loader never opened /sys/kernel/btf/vmlinux, while bpftool prog load of the fork tracer opened it once, mapped all 6,532,544 bytes and logged patched insn #2 (LDX/ST/STX) off 2872 -> 2872.

The object's own BTF goes into the kernel and stays there. libbpf hands .BTF over with BPF_BTF_LOAD, and the kernel checks it in btf_parse() before it returns a descriptor. That descriptor goes with each map, so that the map's key and value have types. It also goes with each program, together with the func info and line info from .BTF.ext, which check_btf_func() and check_btf_line() in check_btf.c check against the program's instructions. None of this has happened yet, because everything in this chapter took place before the first bpf() call, and follows the loader through those calls.

What it costs

CPU
Each slot becomes one or a few x86 instructions (), so slots are a fair measure of run time: -O0 spends 38 slots on what -O2 does in 27, the extra ones mostly stack stores and reloads, and v4 saves one more. CO-RE is paid at load only. libbpf reads the running kernel's BTF, 6,532,544 bytes and 147,680 types on our 7.2 kernel, in about 10 ms (btf__load_vmlinux_btf(), timed three times), then makes one lookup by name per relocation; a run pays nothing, and the counter, which needs no kernel BTF, skips the 10 ms as well.
Memory
The object is 8,112 bytes, of which 216 are code. The kernel keeps the 1,502 bytes of BTF and the func and line info for the program's life; the 4.5 KB of DWARF stays in the file, and llvm-strip -g removes it while keeping .BTF and .BTF.ext (3,624 bytes left). During a load that needs kernel BTF, libbpf 1.8 maps the file read-only, which grew our process by about 1.1 MB, and frees it when the load ends.
Switches
None per event. Per load, an openat() and an mmap() of /sys/kernel/btf/vmlinux when the object needs kernel BTF, and neither for the counter (strace in the VM, kernel 7.2.15).
Locking
Slot 11 is a locked read-modify-write, lock xadd in x86, although its target is the program's own stack, which no other CPU can see; updated_val += *curr_val would be a plain add.

Build with -O2 -g and the default v3, or v4 when every target kernel is 6.6 or newer, and never drop -g, which takes the BTF, the map definition and every CO-RE record with it. Use CO-RE for any program that reads kernel structs, since it costs milliseconds once per load and nothing per event, and keep atomics for memory that other CPUs share.

When it goes wrong

Problems at this stage show up at three moments: while clang builds, while libbpf opens the object, and while the load runs on a kernel other than the one the header came from. The first two are loud, and the message usually names its cause. The quiet failure is a program that loads and runs on the wrong offsets, and the fourth row of is the reason to keep -g in every build. The table gathers the failures met in this chapter and its labs, each with a command that tells its cause apart from the others. Recap

Clang's front end writes the counter as LLVM IR, in which a helper call is a call through a constant pointer and the atomic add is an atomicrmw; the BPF back end selects instructions for the chosen -mcpu version, allocates r0 to r9 with r10 as the frame pointer, and refuses frames of 512 bytes or more before the kernel sees anything. Map references become wide instructions with R_BPF_64_64 relocations, and BTFDebug writes .BTF and .BTF.ext from the debug information, so the map definition, the line info and every CO-RE record exist only when the build has -g. A read of a kernel struct field cannot keep a fixed offset, because offsets differ between kernel builds, so vmlinux.h, the kernel's BTF printed as C, makes clang record each such read as a CO-RE relocation. libbpf answers each record at load, by name, from the running kernel's BTF, fails the load loudly when the field is missing, and hands the kernel plain instructions, which follows through bpf().

Byte 32, r1 = *(u64 *)(r6 + 0x20), with the access string 0:2:2. struct trace_event_raw_sys_enter starts with an 8-byte struct trace_entry and an 8-byte long id, so args begins at 16, and element 2 of an array of 8-byte longs adds 16 more. The string reads as the pointer itself (0), member 2 (args), element 2; BPFAbstractMemberAccess names its global llvm.trace_event_raw_sys_enter:0:32$0:2:2, and llvm-objdump -dr prints CO-RE <byte_off> [16] struct trace_event_raw_sys_enter::args[2] (0:2:2) under the load. It is tempting to answer 16 by forgetting trace_entry; and 32 holds only for this vmlinux.h, because libbpf rewrites it at load when the running kernel's BTF says otherwise.

The BPF back end in clang refused, while it laid out the frame. BPFRegisterInfo::eliminateFrameIndex() calls WarnSize(), which reports this error for any offset 512 bytes or more below r10; 512 is the default of the hidden option -bpf-stack-size and matches MAX_BPF_STACK in include/linux/filter.h, which the verifier enforces as well. No object is written, so the kernel never sees the program. Move the buffer into a per-CPU array with one entry and look it up at the start of the program. Raising -mllvm -bpf-stack-size silences clang but only moves the rejection to the verifier.

On v1 and v2 the only atomic add is BPF_ATOMIC | BPF_ADD without the fetch bit, XADDD in BPFInstrInfo.td, which writes memory and returns nothing. When the program reads the old value, instruction selection still picks that instruction, and BPFMIPreEmitChecking in BPFMIChecking.cpp finds its result in use and stops the build. Build for v3, where atomicrmw becomes XFADDD with the fetch bit, or stop using the result. A common mistake is to blame the kernel; the message comes from clang, and the same source compiles unchanged once the version is v3.

0x8d8. BTF gives field offsets in bits while the instruction's offset field counts bytes, so 18112 / 8 = 2264 = 0x8d8, and libbpf's matching line in the lab agrees: (0:65 @ offset 2264). Only the 16-bit offset field changes, since the kernel's "BPF LLVM Relocations" page says that for loads it is the offset field that gets patched. Forgetting the division gives 0x46c0, the bit offset written in hex.

The server's task_struct has no field named __state, because before Linux 5.14 it was called state (commit 2f064a59a11f, "sched: Change task_struct::state"). The 5.4 BTF from the lab shows it, with 'state' at bit 128 and no __state. libbpf found no match by name and replaced the instruction with a call to helper 195896080; the kernel refused that call, and libbpf rewrote the kernel's message into the line in the log. The fix is in Nakryiko's CO-RE reference guide: a second definition, task_struct___old with the old name, chosen at run time with bpf_core_field_exists(). A server without BTF is a reasonable suspect, but that fails earlier and with a different message, failed to find valid kernel BTF.

The write counter never reads a field through a struct from vmlinux.h: its tracepoint argument goes unused, and the rest is helper calls and map access. llvm-objdump -dr on maps/02-hash-map/hashmap.bpf.o shows three R_BPF_64_64 lines, the map and string relocations from , and no CO-RE line. So no change of struct layout can break it, although a kernel without the sys_enter_write tracepoint, or without a helper it calls, can. Including vmlinux.h does not by itself tie an object to one kernel, because only field reads create relocations.

The fork tracer is worse off. Without -g clang writes no .BTF and no .BTF.ext, so the counter's map, which exists only as BTF, cannot be read and libbpf stops at open. The tracer defines no map, so it opens and loads, but it has lost its CO-RE records as well: llvm-objdump -dr shows the same 0xb38 loads with no CO-RE line under them, and on Ubuntu's 5.4 kernel they would read the wrong four bytes without a word. To shrink an object, keep -g and run llvm-strip -g afterwards, which removes the DWARF and keeps both BTF sections, taking the counter from 8,112 bytes to 3,624. It is tempting to call the counter the casualty, because its load stops and the tracer's does not, but a failure that stops the load is the safe kind.

Clang and LLVM inside the tool, and the kernel's headers installed from the right kernel-devel package, because BCC compiled the program at start-up on each host. "The problem of BPF portability" lists the costs: large binaries, a resource-heavy compile at every start that can take minutes on a busy host, a bet that headers are present, which fails on one-off kernels, and compile errors that appear only at run time. CO-RE moves all of that to the build machine. BCC never got the offsets wrong, which is easy to assume after this chapter; it got them right, at that price.

BTF, the compiler, the loader and the kernel, of which the kernel changed least. In "High-level BPF CO-RE mechanics", BTF carries the types, clang records the relocations, and libbpf matches the program's types to the kernel's and patches the code. The kernel "doesn't need many changes", because after libbpf the program looks like any other, as the field note in this chapter quotes. It would be easy to picture the kernel doing the patching, since the kernel runs the program, but in the post's design libbpf does it in user space.

Because BTF, like DWARF, records types and has no place for macros, so a header printed from BTF has no kernel #define lines. The post says so in "Getting rid of kernel header dependency" and points to libbpf's bpf_helpers.h for the most common ones; the rest have to be defined by hand. grep -c '#define' vmlinux.h in book/program prints 5, and all five are bpftool's own lines at the top, the include guard and attribute shorthands. An old or broken header would be the wrong thing to blame, since regenerating it changes nothing.

back end
the target-specific part of LLVM; for BPF, llvm/lib/Target/BPF
BTF
BPF Type Format: a compact description of structs, fields, offsets and function signatures, written by clang for a program and by pahole for the kernel
CO-RE
compile once, run everywhere: field offsets recorded at build and corrected by libbpf at load
CO-RE relocation
a record in .BTF.ext that names a struct and field by name and says which instruction to patch
front end
the part of clang that parses C and writes LLVM IR
func info
a .BTF.ext record giving the BTF type of a function that starts at a slot
instruction selection
the back-end step that matches IR operations to BPF instructions
libbpf
the C library that reads an object file, creates its maps and programs, and attaches them
line info
a .BTF.ext record tying a slot to a source line, with the line's text
LLVM IR
the typed intermediate code that all LLVM targets share, with unlimited virtual registers each assigned once
register allocation
the back-end step that maps virtual registers onto r0 to r9, spilling to the stack when needed
tracepoint
a fixed, named hook that kernel developers placed in the source, such as sys_enter_write
