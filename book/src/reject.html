Reading a rejection, from log line to source line

A refused load comes with a log, and every line of that log was printed by one call in the kernel source. This chapter reads three logs from the write counter, each changed in one line, from the bottom up, and then follows one of them to the line of verifier.c that printed it, to the test that pins it and to the road a change to it would take.

Three logs from one program

We made three copies of the write counter, changed one line in each and loaded them on kernel 7.2.15, in a throwaway virtual machine on 12 November 2026. shows the last lines the kernel wrote for each. That text is the verifier log, which the verifier writes as it walks, one line per instruction, followed by the reason it stopped and a line of statistics. Every log in the figure ends with the statistics, and the reason sits just above them.

The log never reaches the kernel's own message buffer. The load call carries a buffer, its size and a level, the fields log_buf, log_size and log_level in include/uapi/linux/bpf.h, and the verifier writes only there. libbpf first loads with no log at all, and only if that fails does it load again with one and print the result between BEGIN PROG LOAD LOG and END PROG LOAD LOG.

Tracing bpftool prog load of log (a)'s copy with strace -e trace=bpf in the same VM shows both loads, after six small programs with which libbpf probes the kernel's features. The copy goes in with log_level=0 and comes back EACCES, then again with log_level=1 and a buffer of 16,777,215 bytes. The counter's loader sets no print function of its own, so the log lands on standard error, just above the loader's "Failed to open and load BPF skeleton".

How much the verifier writes is set by the log level. Level 1, which libbpf asks for after a failure, prints each instruction walked and the registers it changed; level 2 prints the full state at every instruction, 4 adds the statistics, and bpftool -d asks for 1, 2 and 4 together. Level 1 also forgets, because each time a path is proved safe and the walk goes back for another, the verifier rewinds the log to where that path began, so that what remains is the path that failed. shows the lines of source that do the rewinding.

Three error codesThe two rule breaks fail with -EACCES and the loop with -E2BIG, and libbpf prints the code on its "failed to load" line. A helper the program type does not allow gives -EINVAL, so the code alone says which kind of no it was.

Reading one log from the bottom

We read a log from the bottom up, as does with log (b). The last line is statistics, printed even when the load fails, and it matters only when the reason is the limit. Above it is the reason, and above the reason is the instruction the walk stopped at, with its slot and opcode. Above that is the walk itself, interleaved with the C lines that the kernel takes from the object's BTF.

The reason names a rule and usually a register, and from there the search goes upward until it finds where that register took on the state the rule refused. In log (b) the entry at slot 9 already holds half of the answer, vs=8, and the reason supplies the other half with off=8 size=8. Eight bytes read from offset eight end past the end of an eight-byte value. There is a second reason to start at the bottom, which we meet in the source: a log too long for the loader's buffer keeps its end and drops its beginning.

"However, when the verifier rejects a program, the unclear error makes repair challenging: the error reports where verification stopped, not where the program lost the proof the verifier required."

One log line, one source line

The reason of log (a), R0 invalid mem access 'map_value_or_null', was printed by a single verbose() call, and the code around that call holds the condition that sent the walk there, which the message leaves out. Searching the v7.2 tree for the fixed middle of that message, as in , brings back two lines of kernel/bpf/verifier.c.

We read upward from each hit to the branch around it. Line 6164 sits in the branch for a different kind of pointer. Line 6322 is the last else of check_mem_access(), the function that checks every load and store through a pointer, and it catches every pointer type that no earlier branch accepted.

Line 6106 says why r0 was not accepted. The map-value branch compares the type with ==, so it takes only a plain map value, and r0 still carried the maybe-NULL flag from the lookup, which log.c prints as the suffix _or_null. The kernel never says that the program forgot a check; what it says is that this type may not be read through here.

How a log line reaches the loader

Every line of a log, the walk as well as the reason, passes through the same two functions. verbose(), at line 327 of verifier.c, returns at once when the loader asked for no log and otherwise hands its format to bpf_verifier_vlog() in log.c. That function formats the line into a 1,024-byte buffer inside the kernel and copies it into the loader's buffer with copy_to_user(). Each line therefore crosses into user space as it is written, and none waits for the end of the walk.

The parts of come from separate calls in do_check(), made for each instruction before its checker runs. verbose_linfo() prints the C line that the object's BTF ties to the slot, and bpf_verbose_insn() prints the instruction itself through disasm.c. The register state after the semicolon arrives one round later, because only when the next instruction comes up does do_check() know which registers the last one changed. print_insn_state() then rewinds the log by one byte, over the newline, and appends the state to the line above. That is why the instruction where a walk stopped, such as slot 10 of log (a), never has a state after it.

The loader's buffer has a fixed size, and a long walk writes more than fits. In v7.2 the kernel treats the buffer as a ring unless told otherwise. Once it is full, each new line overwrites the oldest bytes, so what is left when the walk stops is its last stretch, the reason and the statistics included. A loader that adds BPF_LOG_FIXED, the value 8, to the level keeps the start of the log instead and loses everything after the buffer fills, which for a rejection means losing the reason. shows both on log (a) with a 256-byte buffer.

Either way the load then fails with -ENOSPC, which bpf_check() returns in place of the verifier's own error (line 19985). The kernel also writes the size the whole log needed into log_true_size, a field of the load call's attributes. libbpf's low-level bpf_prog_load() hands that size back, yet its object loader ignores it and doubles its own buffer instead, walking the program once more each time.

The size the kernel compares is the longest the log ever grew, before any rewinding, so the unchanged counter, which the verifier accepts, fails to load with a 64-byte buffer, the third block of the figure. The ring also costs time on a long walk. With a 64 KB buffer the unbounded copy of log (c) failed in 3.7 to 4.2 s, three runs in the same VM, against 2.8 s with BPF_LOG_FIXED, which stops copying once the buffer is full.

The forgetting of level 1 lives in the same code. When the walk finishes a path and takes the next branch from its stack, pop_stack() (line 1705) calls bpf_vlog_reset() with the log position saved alongside that branch, unless the level includes 2. When a whole walk at level 1 succeeds, line 18499 resets the log to its start, and the counter, accepted, leaves 98 bytes, its statistics line and no walk at all.

The map around that line

check_mem_access() is one stop on a longer trip, which draws. Each load runs bpf_check() once, and it checks the program's shape, walks every path and then rewrites the program for running. In v7.2 those phases live in separate files, with the shape check in cfg.c, the state comparison behind pruning in states.c, the rewrites in fixups.c and the log's wording and copying in log.c. Of the rejection, only what log.c does comes from outside verifier.c.

The walk itself stays in verifier.c. Its loop, do_check(), hands each instruction to do_check_insn(), which picks a checker by the kind of instruction: arithmetic, load, store, call or jump. The counter's call, its test and its load therefore go to three different checkers.

follows them. At the call, check_helper_call() resets r1 to r5 at line 10414 and gives r0 the map-value type, flag and all, at line 10455, so the doubt about NULL is recorded before any test is seen. At the test, check_cond_jmp_op() splits the state in two, making r0 a plain map value on one branch and the number 0 on the other, which removes that doubt without adding any check of its own. At the load, line 6106 accepts only the first of the two.

"When type PTR_TO_MAP_VALUE_OR_NULL passes through 'if (reg != 0) goto +off' insn, the register holding that pointer in the true branch changes state to PTR_TO_MAP_VALUE and the same register changes state to CONST_IMM in the false branch. See check_cond_jmp_op()."

The test that pins the message, and the road upstream

A message that users can hit is pinned by a selftest, a test kept in the kernel tree under tools/testing/selftests/bpf. Searching the v7.2 selftests for the full message brings back six files under progs/. One of them, verifier_map_ret_val.c, holds a test called "don't check return value before access", whose body is the counter's bug in BPF assembly: r2 = r10, a call to the lookup, then a write through r0 with no test.

The test annotations above it, __failure and __msg("R0 invalid mem access 'map_value_or_null'"), tell the test runner to load the program, expect a rejection and find that text in the log. A patch that rewords the message in check_mem_access() makes this test fail, which is what the test is for. The BPF maintainers' guide asks for a test with every change to verifier behaviour, because behaviour that no test tracks "could potentially be subject to change".

The runner, test_loader.c, gets its log the way the counter's loader does. It gives each program a 2 MB buffer of its own with bpf_program__set_log_buf() and leaves the level at 0 unless the test asks for more with __log_level() or test_progs runs with -v. libbpf therefore loads the program once without a log and, on the failure the test expects, again at level 1 into that buffer. Each __msg() is then searched for in the log starting where the previous one matched, so a test with several messages expects them in the order the walk prints them.

What it costs

CPU
Kernel 7.2.15 in a throwaway VM, November 2026. Verification time follows the instructions walked: the counter's 36 took 107 µs of a 146 µs load (), and the unbounded copy reached the one-million limit in 3.9 s. A refused load is walked again for the log, because libbpf retries at level 1 with its own 16 MB buffer (BPF_LOG_BUF_SIZE) and doubles it on each ENOSPC: that copy failed after 36 s, about 8 s at each of 16, 32, 64 and 128 MB (strace -T). Level 2 slowed verification of the counter from 221 to 591 µs and of the bounded copy from 586 to 2,844 µs.
Memory
53,728 bytes for struct bpf_verifier_env, 136 per instruction for its side data and at least 1,288 per saved state (BTF of 7.2.15), charged to the loader's memory cgroup and freed when the load ends. The log buffer is the loader's, capped at UINT_MAX >> 2 bytes, about 1 GB (kernel/bpf/log.c); level 2 wrote 6.7 KB for the counter and 62 KB for the bounded copy.
Switches
One bpf() call per load and one per retry. Inside it each log line is its own copy_to_user(), so with a 64 KB buffer the unbounded copy failed in 3.7 to 4.2 s with the ring and 2.8 s with BPF_LOG_FIXED. Between instructions do_check() gives up the CPU when another task needs it and stops with EAGAIN on a signal (line 17402).
Locking
None for loaders with CAP_BPF; the others share bpf_verifier_lock ().

Load without a log first, as libbpf does, keep level 2 for small programs, and keep a program's paths few so that its load stays in microseconds. For a program near the limit, a buffer set with bpf_program__set_log_buf() stops libbpf's retries, and the ring still keeps the reason. Before sending a verifier change, run the 1,860 or so test programs in the 121 progs/verifier_*.c files and compare processed instructions and states before and after with veristat.

When it goes wrong

Most of what goes wrong with a rejection goes wrong in the reading, and collects the cases this chapter met, from the three logs, the three copies of the lab below, the measurements and the source. The first six rows are reason lines. For each of them the confirming command is the load that printed the reason, and the evidence is a line above it, found by reading upward as in . Before any reading, the error code already sorts most failed loads: -EACCES for the broken rules of this chapter, -EINVAL for a helper the program type may not call, -E2BIG for the instruction limit and -ENOSPC for a log that did not fit.

The next four rows are about the log rather than the program. A log that shows one side of a branch, starts in the middle of a line or arrives after half a minute is still telling the truth. The level, the size of the buffer and libbpf's retries decide how much of it reaches the screen, and when. The last two rows are about the source, whose line numbers change from release to release, so that a search for the fixed words of a message finds the code in any release while a search for a function's name can come back empty.

The row about accepted programs matters most for loaders that run in production. A loader that always passes a log buffer, so as to keep the log for its own error reports, turns any program whose log once grew past that buffer into a failed load, even though the verifier accepted it. Such a loader should load without a log first and ask for one only after a failure, as libbpf does, or size its buffer from log_true_size.

Two of the rows rest on numbers the verifier keeps for every register, the smax=8 of the lab's third copy and the r7 that climbs in log (c). Where those bounds come from, and why the kernel may trust them, is the subject of .

Recap

A refused load returns a verifier log, which libbpf asks for at level 1 only after a failure and which level 1 trims to the path that failed. Read from the bottom, the reason names a rule and a register, and the walk above shows where that register lost what the rule needed; of the three broken copies, only the bounds fix sat on the line where the walk stopped. Each line is one verbose() call copied into the loader's buffer, which in v7.2 is a ring, so that a log too long for it keeps its end and the load fails with -ENOSPC. The reason of log (a) is line 6322 of verifier.c, the last branch of check_mem_access(), reached because line 6106 accepts only a plain map value and only a test of r0 clears the lookup's maybe-NULL flag. A selftest pins that message, and a change to verifier behaviour goes upstream with a test, to bpf for fixes and bpf-next for everything else.

About eight: 1,000,001 ÷ 124,993 ≈ 8.0. Seven are the loop body, slots 16 to 23 with the wide load at 16 counted once, and the eighth is the exit side of slot 23's test. The walk follows the fall-through first, out of the loop to slot 24, finds a saved state there that covers it, because r7 is never read after the loop, and prunes it on the spot before coming back for the next round. The accepted copy with the cap shows this directly, since at log level 2 its exit side is pruned once per round. Seven, the loop body alone, leaves out the way out that every round also checks.

A type rule: the instruction reads memory through r1, and r1 holds a scalar, a plain number, which may never be used as an address. The search climbs the log to the last line whose entry after the ; changed R1, because that line is where r1 became a number, often a load from a map value or a helper's return value, such as the counter's slot 10, r1 = *(u64 *)(r0 +0), which leaves R1=scalar(). The fix is wherever the program meant to keep a pointer and kept a number instead. Adjusting the offset on the stopping line misses the cause, because the address was never an address.

The verifier erased them. At log level 1, which libbpf asks for after a failure, each finished path is wound back out of the log: when the walk returns for a kept branch, pop_stack() in kernel/bpf/verifier.c resets the log to where that branch was saved, and only at level 2 are the lines kept. What remains is the path that failed, while sudo bpftool -d prog load, which asks for levels 1, 2 and 4, shows every path. The missing lines do not mean the other side went unchecked; it was checked, accepted and then removed from the text.

Class, mode and size, and the four-byte read shows (61). The opcode byte of a load is the three fields added together: class LDX is 0x01, mode MEM is 0x60 and size DW, eight bytes, is 0x18, so 0x01 + 0x60 + 0x18 = 0x79. Size W, four bytes, is 0x00, which leaves 0x61. The values are in include/uapi/linux/bpf_common.h, with BPF_DW in bpf.h, and kernel/bpf/disasm.c prints the line with "(%02x) r%d = *(%s *)(r%d %+d)". Reading the size as the number of bytes, 8 or 4, gives a wrong byte, because the field holds a code for the size.

In v7.2 the shape check is bpf_check_cfg() in kernel/bpf/cfg.c, still called from bpf_check() before the walk, still a depth-first search that reports jumps out of range, unreachable instructions and back-edges. Search for a message instead of the function name: grep -rn "unreachable insn" kernel/bpf finds the code in cfg.c, and otherwise only the design comment. Trusting the old name leads to the conclusion that the check is gone, when function names and files drift between releases and the two-pass design has stayed the same since 2014.

The test still expects the old wording. Its __msg(...) annotation names the text it wants, the runner searched the new log and did not find it, and test_loader.c reports that as expect_msg. That is the test doing its job, because the message is behaviour and someone depends on it. If the rewording is worth making, the same patch series must update every test that pins the old text, which grep -rln over the selftests finds. The failure can look like a broken kernel, but the program was rejected as before, only in different words.

bpf-next, with PATCH bpf-next in the subject. The guide sends fixes to the bpf tree and "features, cleanups or other kind of improvements" to bpf-next, and a comment correction is a cleanup. It gives the command, git format-patch --subject-prefix='PATCH bpf-next'. A Fixes: tag is required only for fixes. Before writing the patch, it is worth checking that the comment is still wrong in today's bpf-next and that nobody has sent the same patch to the list. Sending it to bpf because it "fixes" something would misplace it, since the code was never wrong, only its description.

Test cases in the BPF selftests. The guide says that for a change to verifier behaviour "it is absolutely necessary to add test cases", and that the maintainers "might ask for them before accepting any changes". The reason is in the same answer: behaviour that no test tracks "could potentially be subject to change", because the next person to touch the verifier has nothing to tell them it mattered. In practice the patch adds a function with __success or __failure and __msg(...) to a progs/verifier_*.c file. Small changes get no exemption, and they are the verifier changes most likely to break an existing program.

The selftests from the 7.2 tree. The guide's rule is "If you run a kernel xyz, then always run the BPF kernel selftests from that kernel xyz as well." Newer selftests are adapted to a newer verifier, which tracks more and accepts programs an older one refuses, so they can fail on 7.2 for reasons that have nothing to do with the change under test. The tag cloned for this chapter, v7.2, already has the matching selftests. Fetching the newest bpf-next tests and reading their failures as bugs in the running kernel is the mistake that rule prevents.

Redirect: each program type allows its own list of helpers, and the write counter's type may not redirect packets, which breaks the first half of the fifth row, lost at the call itself. Var: the bounds rule again, fourth row. Here the offset is 0 or 8, so the smallest access fits and the largest does not, which is why the reason says max where log (b), with a fixed offset of 8, said min. The proof was lost at slot 13, where the offset joined the pointer.

Common wrong turn. Reading the long expected= list as a list of things to try, when it lists every pointer type the key may be and the fix is to pass &pid again.
