A promise written as a claim

drew the verifier's promise as six things a loaded program never does. Written so that it can be checked, a promise becomes a specification, a claim about every possible input that a program either meets or breaks. For 's copy it reads: for every descriptor the copy can receive, the eight bytes read at slot 13 lie inside the 64-byte map value. No finite set of tests can settle "for every".

sets out the two ways a verifier can fail such a claim. It is sound, in 's sense now applied to the whole verdict, when it never loads a program that breaks the specification on some input. It is complete when it never refuses a program that meets it, a property called completeness, and each refusal of a safe program is a false alarm.

Linux keeps the soundness bug's cell empty and pays in the false alarm's. A verifier without false alarms would need to know every value at every instruction without any loss, far more than a load can spend. A loaded unsafe program is therefore a bug, to be fixed and backported, while a false alarm is a limit, and the kernel's source documents one of its own.

"This is a conservative heuristic that allows to verify wide range of programs, however it precludes verification of programs that conjure an imprecise value on the first loop iteration and use it as precise on a second."

Abstract values, formally

The papers relate two kinds of value. Concrete values are the numbers a register really holds, and abstract values are the tnums and ranges of . The bridge between them is concretization, written γ (gamma), which maps an abstract value to the set of numbers it stands for: on four bits γ(00x1) = {1, 3}, and γ([2, 5]) = {2, 3, 4, 5}.

An abstract operation is sound when its answer holds every concrete result. With ∀ read as "for every" and ∈ as "is in", the claim for an abstract addition ⊕ and any two abstract values A and B is the line below.

∀x ∈ γ(A),  ∀y ∈ γ(B) :  x + y ∈ γ(A ⊕ B)

checks one case. The real sums of 00x1 and 0x10 are 3, 5, 7 and 9, while tnum_add() answers xxx1, the eight odd numbers, and interval addition answers [3, 9]. Both answers are sound and imprecise, and together they allow only the real sums.

Where two paths meet, an analysis may merge their abstract values with a join, the smallest abstract value that holds both. [0, 2] joined with [5, 6] is [0, 6], and tnum_union() in tnum.c joins two tnums. A loop is a path that meets itself, so a joining analysis repeats until the value at the loop's top stops changing: 16 rounds on four bits in , and 264 on a register. Widening ends the climb by moving any bound that grew to the end of the number line, and the loop settles in two rounds.

PREVAIL, read in , joins wherever paths meet and widens at loops. Linux never joins paths. It walks each round as a separate verifier state and prunes a path only when, for every scalar whose range matters, the new γ lies inside the saved one (regsafe() in states.c, with range_within() and tnum_in()), so a loop it cannot prune runs into the instruction limit. For iterator loops and bpf_loop(), widen_imprecise_scalars() forgets the range of every scalar whose range has not yet mattered, a widening straight to "any value" and the cause of the false alarm quoted above.

Three ways to know, and what a solver is asked

Trying every case, the first column of , is a proof when the cases can be listed: on four bits there are 81 tnums, so 6,561 pairs for a two-input operation. The work grows sixteenfold with each bit. A claim about every width therefore needs a proof on paper, by algebra or by induction over the bit positions, as the tnum paper gives for tnum_add() and writes out for a smaller case.

The third way hands the question to an SMT solver, a program that decides whether a formula over numbers, bits and other theories can be made true. Its answer is satisfiable, printed sat, with a model that gives every variable a value, or unsat when no such assignment exists. asserts the claim's negation. A sat answer is then a counterexample, inputs that break the claim, and unsat proves that none exists at that width.

The width matters because the variables are bit-vectors, fixed-width words whose arithmetic wraps round. RFC 9669 §4.1 requires the same of every BPF register, so on four bits 15 + 1 is 0.

Recap

A specification is a claim about every input; a sound verifier never loads a program that breaks it, a complete one never refuses one that meets it, and Linux chooses soundness and accepts false alarms. An abstract operation is sound when every concrete result lies in γ of its answer. PREVAIL joins paths and widens loops, while Linux walks every round until the instruction limit. Soundness is shown by every case at a small width, a proof for every width, or a solver's search for a counterexample over bit-vectors.

member(x, P) holds when x agrees with P on every known bit, x & ~P.m = P.v; wellformed(P) holds when no bit is both unknown and 1 in the value, P.v & P.m = 0. For 01x0 the mask is 0010 and the value 0100, so γ(01x0) = {x : x & 1101 = 0100} = {0100, 0110} = {4, 6}. What this shows.
