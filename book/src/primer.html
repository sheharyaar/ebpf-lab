A contract between code and processor

An instruction set architecture (ISA) is the contract between compiled code and the processor that runs it. It fixes the registers, the processor's own named storage slots, the ways of addressing memory, the instructions that exist and the bytes that encode each one. Caches and pipelines stay outside it, so one x86-64 binary runs on old and new chips alike.

Each instruction has an opcode, the number that selects the operation, and operands, the registers, memory addresses or constants it works on. A constant stored inside the instruction is an immediate, like the 4 in eBPF's r1 += 4. Rules that the hardware leaves open, such as which register carries a function's first argument, make up the ABI, the application binary interface that compilers agree on.

One expression, three machines

computes one expression on three kinds of machine. A stack machine names no registers. Each of its instructions pops operands from an operand stack and pushes the result back, so i64.add has no operand fields, and the JVM, WebAssembly and CSPF, the 1980 filter that the 1993 paper replaced, all work this way.

Classic BPF, in the middle, is the prologue's accumulator machine. Its arithmetic always writes A and takes the second operand from X or from the instruction, so b, c and d wait in scratch memory. eBPF, on the right, is a register machine whose instructions name any of eleven registers, so its inputs arrive in r1, r2 and r3 and never leave the processor.

Counted the way the 1993 paper counts a stack machine run in software, the three columns make 12, 3 and 0 memory accesses. That was the paper's case for registers, since memory was already the bottleneck of the SPARCstation 2 it measured on.

"The operand stack must be simulated. On most modern machines this means generating add and subtract operations to maintain a simulated stack pointer and actually doing loads and stores to memory to simulate the stack."

McCanne and Jacobson, The BSD Packet Filter, section 3.1, USENIX Winter 1993
Why one address in 1993The paper also says why it stopped at an accumulator. When software runs the filter one instruction at a time, it decodes each operand field in turn, so "a single address instruction format minimizes the decode" (section 3.2.2). eBPF was designed to be translated into processor instructions before it runs, which removes that cost.

Arithmetic in registers, memory through loads

In a load/store architecture, arithmetic works only on registers and memory is reached only through loads and stores. RISC-V and eBPF are built this way. x86-64 is not, since its arithmetic may name a memory operand, so in one x86-64 instruction does the work of three. The processor still loads, adds and stores inside that instruction, and the saving is in code size. In eBPF only loads, stores and atomic operations touch memory, which relies on.

Reading AT&T syntaxThe x86-64 listings in this book use AT&T syntax, as clang, objdump and the kernel's documentation do. The destination comes last, % marks a register, $ an immediate and parentheses a memory address, so addq %rsi, (%rdi) adds rsi to the eight bytes at the address in rdi. eBPF assembly reads like C, destination on the left.

The stack and the frame pointer

A value goes on the stack, the memory where each running function keeps a frame for its locals, when live values outnumber registers or a variable needs an address. A frame pointer is a register holding a fixed address in the frame, so that each local is named as that register plus a constant. Storing a register on the stack to free it is a spill, and loading it back is a fill.

eBPF's stack is 512 bytes (MAX_BPF_STACK in include/linux/filter.h) below r10 (, right). A program can read r10 but never write it, so r10 − 8 names the same eight bytes throughout a function. On x86-64, rbp is a frame pointer only by convention, and clang drops it at -O2.

Calls: who keeps which register

A calling convention is the part of the ABI that says where a call's arguments and result go and which registers the call may overwrite. Those are caller-saved, since a caller that still needs their values must save them first, while the registers that a called function must hand back unchanged are callee-saved. Linux's System V ABI for x86-64 passes six integer arguments in rdi, rsi, rdx, rcx, r8 and r9, returns in rax, and keeps rbx, rbp and r12 to r15 callee-saved.

eBPF passes arguments in r1 to r5, returns in r0 and keeps r6 to r9 callee-saved, and the kernel's classic_vs_extended.rst pairs each register with the x86-64 register that already does its job (, left), so a call into a kernel function moves nothing first.

Instructions as bytes

eBPF encodes every instruction in eight bytes: an opcode byte, a byte holding two four-bit register numbers, a 16-bit offset and a 32-bit immediate. Only the load of a 64-bit constant takes two slots. RISC-V's base instructions are four bytes, while an x86-64 instruction takes from 1 to 15 (MAX_INSN_SIZE in the kernel's arch/x86/include/asm/insn.h).

With a fixed width, slot n starts at byte 8n and a hex dump splits by eye. The eBPF bytes 79 13 in are opcode 0x79, a 64-bit load, then a register byte with the destination in its low four bits and the source in its high four, so they read r3 = *(u64 *)(r1 + 0).

One function, compiled twice

compiles a three-line function for both targets, row by row. The x86-64 code adds the word at p straight into rbx, where eBPF first loads it into r6, and both compilers keep t in a callee-saved register because t is needed again after next() returns.

The two differ at entry and exit. The x86-64 code pushes rbx on entry and pops it before retq, since step() owes its own caller an unchanged rbx. The eBPF code has no such pair, because the kernel itself saves whichever of r6 to r9 an eBPF function uses, as shows.

Where r6 to r9 are keptWhen the kernel turns an eBPF function into x86-64 code, do_jit() in arch/x86/net/bpf_jit_comp.c starts it with push_callee_regs(), which pushes rbx, r13, r14 or r15 for each of r6 to r9 that the function uses, and the exit path pops them again.

Hint 1 · direction

1 · A stack-machine instruction touches memory for every value it pushes or pops; an accumulator machine has two registers and parks everything else.

2 · Work one slot at a time; a jump's offset counts from the slot after the jump.

3 · a and b are each needed twice, so decide which value you can afford to overwrite first.

4 · Cut the eight bytes into their four fields before you look anything up.

5 · For each register read after slot 1, ask whether the convention promises that it comes back from a call.

Hint 2 · mechanism

1 · In classic BPF, A holds one sum and X the next operand, so the other sum needs somewhere to wait.

2 · 25 − 30 is −5, which read as an unsigned 64-bit number is 264 − 5.

3 · Put a − b in r0 first; after that, a is no longer needed in r1.

4 · f8 ff read little-endian is 0xfff8, and as a signed 16-bit number that is 0xfff8 − 0x10000.

5 · r1 to r5 are caller-saved and r6 to r9 callee-saved.

Hint 3 · nearly there

1 · In classic BPF, compute d + e, store it with st M[5], compute b + c, then ldx M[5] and mul x.

2 · The jump at slot 5 is taken, so slot 6 never runs.

3 · Start with r0 = r1 and r0 -= r2; two more instructions finish it.

4 · In the first, the destination is r10 and the source r1.

5 · Copy r1 into r6 before the call, and load the field into r7 instead of r2.

What it costs

CPU
On this book's machine, an AMD Ryzen 7 8845HS (Zen 4) at about 5 GHz, a chain of dependent register adds runs at one cycle, 0.2 ns, per add. A dependent load took 4–5 cycles from the L1 cache, about 14 from L2, 50–60 from L3 and about 110 ns, some 550 cycles, from main memory, measured with a pointer chase through 16 KiB, 192 KiB, 6 MiB and 256 MiB buffers on one pinned core.
Spills
A spill and its fill add two instructions and an 8-byte slot. In the same test the pair added about one cycle of delay when the store and the load named the same register and offset, as stack slots do, and about seven cycles when the same address came through two different registers.
Calls
A call costs the call, the return and any moves that put arguments in place. eBPF's r1 to r5 already sit in the x86-64 argument registers, so a call into the kernel adds no moves, and a value kept in r6 to r9 needs no spill around it.

Count memory accesses before instructions: a register operand costs nothing extra, a cache hit a few cycles and a miss hundreds. Build with -O2 so that values stay in registers, and keep a value that must outlive a call in r6 to r9.

Recap

An ISA fixes a processor's registers, memory addressing, instructions and their encoding, and the ABI's calling convention adds where arguments and results go and which registers a call may overwrite. A stack machine keeps its operands in memory, an accumulator machine in one register and scratch memory, and a register machine in named registers, which for a = (b + c) * d means 12, 3 and 0 memory accesses. eBPF is a load/store register machine with r0 to r9, a read-only frame pointer r10 over a 512-byte stack, and a convention shaped like x86-64's: arguments in r1 to r5, the result in r0, r6 to r9 kept across calls. Its instructions are eight bytes each, where x86-64's take 1 to 15.

Hack does its work with two registers and memory, so the exercise shows from the inside why the middle column of needs so many loads; an evening.

The instruction is movq 8(%rsp), %rax, so the seventh argument sits at rsp + 8. The System V convention has six integer argument registers, rdi, rsi, rdx, rcx, r8 and r9, so the caller stores the seventh on its own stack, and callq then pushes the eight-byte return address below it. At entry rsp points at that return address and the argument is one slot above. Compile long seventh(long a, long b, long c, long d, long e, long f, long g) { return g; } with clang -O2 -S to see it. A common slip is to answer 0(%rsp), which forgets the return address; eBPF has only five argument registers, and shows what clang does beyond them.

rbx is callee-saved under the System V ABI, and scramble() broke its promise to hand it back unchanged. At -O2 clang unrolls the loop and keeps the running partial sums in rbx and r14 across the calls (movq %rax, %rbx, callq scramble, addq %rax, %rbx), so each call overwrites a partial sum with 12345. At -O0 the sum and i live on the stack, which hides the bug. Fix it with pushq %rbx on entry and popq %rbx before retq, or by using a caller-saved register such as rcx or r11. It is tempting to blame the optimiser, but -O2 only relied on a rule that the assembly broke.

At -O0 clang gives every argument and local its own slot below r10 and writes each value back as soon as it changes, so t lives at r10 − 24 and is read back from memory after the call. The slot keeps its value because the called function gets a frame of its own and r10 comes back unchanged. At -O2, t stays in r6, which the calling convention promises to return intact, so the store and both reloads disappear. Check with clang -O0 -target bpf -c and llvm-objdump -d. A common misreading is that the convention demands the store; it only forbids keeping t in r0 to r5, and r6 and the stack both satisfy it.

1 · Count. The stack machine needs 7 instructions and 17 memory accesses: local.get 0, local.get 1, i64.add, local.get 2, local.get 3, i64.add, i64.mul. Each local.get reads a local and pushes it, two accesses, and each arithmetic instruction pops two values and pushes one, three accesses, so 4 × 2 + 3 × 3 = 17; clang writes the same seven, starting with d + e.

Classic BPF needs 9 instructions and 6 accesses: ld M[3], ldx M[4], add x, st M[5], ld M[1], ldx M[2], add x, ldx M[5], mul x. Both sums are live at once and only A and X can hold values, so one sum is spilled to M[5] and filled back into X. eBPF needs four instructions and no access; clang writes r0 = r4, r2 += r1, r0 += r3, r0 *= r2.

3 · Translate. Four instructions and three registers are enough, and a = 7, b = 3 gives 40:

r0 = r1        ; a
r0 -= r2       ; a - b
r1 += r2       ; a + b; a is no longer needed
r0 *= r1

Clang 23.1.4 at -O2 writes five, r0 = r1, r1 = r2, r1 += r0, r0 -= r2, r0 *= r1, with the same registers and one copy more, so a compiler's output is a good answer but not always the shortest. The wrong turn is to compute a + b first into r1, which destroys a before a − b needs it and forces a fourth register or a spill.

4 · Decode. 7b 1a f8 ff 00 00 00 00 is *(u64 *)(r10 - 8) = r1: opcode 0x7b stores 64 bits, the register byte 0x1a gives destination 0xa, which is r10, and source 1, and f8 ff is 0xfff8, which is −8. It is a spill of r1 into the first stack slot, and it is the first instruction of 's step() at -O0. 07 01 00 00 f0 ff ff ff is r1 += -16, since 0x07 adds an immediate to destination r1 and 0xfffffff0 is −16. llvm-mc --disassemble -triple=bpfel prints both lines the same way. The wrong turns are reading the register byte high half first, which gives *(u64 *)(r1 - 8) = r10, and reading f8 ff as 0xf8ff.

5 · Find the bug. Slot 2 reads r2 and slot 3 reads r1 after the call, and both are caller-saved, so the call may have overwritten them. One added instruction fixes it; any of r6 to r9 will do:

0: r6 = r1
1: r7 = *(u64 *)(r6 + 0)
2: call 5
3: r0 -= r7
4: *(u64 *)(r6 + 8) = r0
5: r0 = 0
6: exit

On x86-64 the same mistake would run and read whatever the callee left in rdi and rsi. eBPF never runs it, because the kernel refuses to load a program that reads r1 to r5 after a call ("After the call the registers R1-R5 contain junk values and cannot be read", classic_vs_extended.rst), as shows. The common wrong turn is to move r1 and leave r2, because r2 was never an argument to the call.

What this shows. Registers are where a machine does its work, memory is where values wait, and the calling convention decides which registers keep their values across a call; every eBPF listing in this book can be read with these five habits.
