The JIT, and tail calls as patched jumps

The kernel this book runs on cannot execute bytecode, so every program it accepts is translated into x86 before it runs: the write counter's 29 checked instructions become 152 bytes of machine code in 7 to 17 µs, and a jump from one program into another becomes five bytes that the kernel rewrites whenever the target changes.

What the kernel shows of the counter's machine code

We load the write counter and ask the kernel about it in . bpftool reports two sizes, 232 bytes of instructions after the kernel's rewrites, which makes 29 slots of 8 bytes, and 152 bytes of x86. The x86 also has a name in /proc/kallsyms: bpf_prog_, then the program's tag, a hash of its instructions, then its own name. Every tool that reads kernel symbols therefore sees the counter as one more function of the kernel.

perf is one of those tools. While dd made its writes with the counter attached, 1.31% of the samples fell inside the counter's own code. The functions it calls took more, 5.65% in htab_map_update_elem() alone and several percent in the machinery behind bpf_printk(), so the program's own instructions are a small part of what it costs. perf could name the program but could not show its instructions, because the perf of this distribution is built without the disassembler that annotating BPF code needs. bpftool prog dump jited prints them instead, and the rest of this chapter reads that dump.

A kernel with no interpreter

In we ask the kernel how it runs programs. The switch bpf_jit_enable reads 1, and even root cannot set it to 0, because this kernel was built with CONFIG_BPF_JIT_ALWAYS_ON. Nor can root set it to 2, the value that prints every image to the kernel log on kernels that allow it. Its symbol table holds no interpreter at all, so every program is translated when it loads or the load fails.

An interpreter runs bytecode by reading one instruction at a time and doing what it says. Linux has one, ___bpf_prog_run() in kernel/bpf/core.c, but that build option leaves it out. A JIT compiler, named for working just in time, instead translates the whole program into native code, the CPU's own instructions, once and at load time. sets the two approaches side by side.

"Enables BPF JIT and removes BPF interpreter to avoid speculative execution of BPF instructions by the interpreter."

Help text of CONFIG_BPF_JIT_ALWAYS_ON, kernel/bpf/Kconfig, Linux v7.2

Speculative execution, which met as the CPU running ahead on a guessed branch, can be steered by an attacker. An interpreter in kernel memory is a ready-made machine for running bytecode in that state, which is why this kernel has none. When the JIT cannot translate a program, the load fails with -ENOTSUPP, error 524, in __bpf_prog_select_runtime() in core.c, which bpf_check() calls as its last step (verifier.c line 20036 in v7.2).

Without the option the interpreter is built, and it has limits of its own. bpf_prog_select_interpreter() picks one of sixteen copies of it, one for each 32-byte step of stack up to 512 bytes. For a program the JIT did not take, bpf_fixup_call_args() refuses calls to kernel functions, callbacks, and bpf-to-bpf calls in a program that also makes tail calls. With the option set, bpf_prog_select_interpreter() stores a placeholder that returns 0 and warns, and it should never run.

What the kernel changes before the JIT

The JIT does not see the program clang wrote. Between the end of the walk and the call to the JIT, bpf_check() runs the passes of over the instructions. The verification time printed with the log's statistics stops after them, before the JIT starts (verifier.c line 19980). One pass ran before the walk. Each 64-bit load that named a map by its descriptor now holds the map's address, and the load of the bpf_printk() format string holds the address of those bytes inside the .rodata map.

We follow four of the counter's instructions through both steps in . The map load at slot 6 now carries the map itself. The call 0x1 at slot 8 has become a direct call to __htab_map_lookup_elem(), the hash map's own lookup, followed by two instructions that move r0 from the map's entry to the value inside it. htab_map_gen_lookup() in kernel/bpf/hashtab.c writes those three, and the JIT later turns them into four x86 instructions.

The other three calls changed only their immediate, which now holds the distance of the helper or the map function from __bpf_call_base, so that the JIT can write a plain x86 call. follows a helper call from both sides.

Every rewrite that turns one instruction into several goes through bpf_patch_insn_data() in fixups.c. It copies the program with the new instructions in place, corrects the jumps that cross the patched spot, and moves the verifier's record of every later instruction along. For the counter that happens once, at slot 8, and costs nothing worth measuring; we meet it again where it happens once for every instruction.

The counter in x86, and the frame around it

The JIT in arch/x86/net/bpf_jit_comp.c then turns each instruction into x86. Each bytecode register lives in one x86 register for the whole program. These are the pairs of , which the JIT keeps in its table reg2hex[]: r0 in rax, r1 in rdi, r2 in rsi and r10 in rbp. So r2 = r10 becomes the three bytes 48 89 ee, which bpftool prints source first as movq %rbp, %rsi. A helper call becomes a plain x86 call with its arguments already in place, because r1 to r5 sit in the registers that the x86-64 calling convention uses for a function's first five arguments.

shows the 27 bytes the JIT writes before slot 0. An endbr64 comes first, because this kernel is built with indirect branch tracking (CONFIG_X86_KERNEL_IBT=y), and a CPU that enforces it faults when an indirect call lands anywhere else. A five-byte no-op follows as room for a call that may be patched in later.

Then come a three-byte no-op, which becomes xorq %rax, %rax in a program that makes tail calls, the usual frame setup, a second endbr64 at offset 0x10, and room for the counter's 16 bytes of stack. No register is saved, since the counter never uses r6 to r9. A program that does gets a push of rbx, r13, r14 or r15 for each one it uses, which is the saving said the kernel does on a program's behalf.

At the end, w0 = 0 becomes xorl %eax, %eax, and exit becomes leave and a jump to the kernel's return thunk. emit_return() writes that jump in place of ret on CPUs where the kernel sends every return through the thunk as a defence against speculation. Altogether, 232 bytes of bytecode became 152 bytes of x86. The image is smaller even though one instruction may become several, because most x86 instructions take fewer than the eight bytes of a BPF slot. The counter averages 5.2 bytes a slot, and a long run of additions of 32-bit constants takes 6.

Who checks the translatorJitterbug (OSDI 2020) wrote down what a correct BPF JIT must do and checked JITs against it automatically. With it the authors built a verified JIT for 32-bit RISC-V, and found and fixed 16 bugs in five other JITs, all upstream.

The five-byte no-op serves a trick that the kernel's own functions use too. When a program is attached to the entry of a kernel function, the kernel writes a trampoline, a short piece of x86 that saves the function's arguments, calls the program and then lets the function run. It patches a call to the trampoline over a five-byte no-op at the start of that function, and the no-op at the start of a BPF program lets another program attach to it in the same way. The JIT's source explains it with a network function, eth_type_trans(). attaches programs this way and follows a trampoline as the kernel builds it and patches it in ().

"eth_type_trans has 5 byte nop at the beginning. These 5 bytes will be replaced with 'call generated_bpf_trampoline'. When it returns eth_type_trans will continue executing with original skb and dev pointers."

Comment before the trampoline code in arch/x86/net/bpf_jit_comp.c, Linux v7.2

Passes until the length settles

x86 instructions have different lengths, and the length of a jump depends on how far it goes: a conditional jump to a place within 127 bytes takes two bytes, a farther one six. The JIT cannot know a distance before it knows the length of everything in between. So bpf_int_jit_compile() starts from a guess of 64 bytes for every instruction and translates the whole program again and again, each pass working from the addresses the previous one produced, until the length stops changing.

follows the counter through those passes. In the first, the test at slot 11, which skips two instructions, seems by the guess to aim 128 bytes ahead and gets the six-byte form. In the second the real distance is known, and the test shrinks to two bytes. The third pass gives the same 152 bytes, so the JIT asks for memory for the image and runs a fourth pass that writes into it. A program with no such jumps has its final length after the first pass and needs three in all.

Lengths can only shrink from one pass to the next, so the loop ends, but the code does not rely on that alone. After 15 passes (PADDING_PASSES) do_jit() pads every jump that would shrink with no-ops up to its previous length. After 20 (MAX_PASSES) without an image the program is left untranslated, which on this kernel fails the load with error 524.

Where the image lives

The 152 bytes cannot go just anywhere, because kernel code must be executable and should never be writable at the same time. The JIT's last pass writes into an ordinary, writable copy, and bpf_jit_binary_pack_finalize() then copies the image with text_poke_copy() into memory that is mapped read-only and executable. That memory comes from a program pack, a 2 MB block of executable memory that the images of many programs share. bpf_prog_pack_alloc() in core.c hands it out in 64-byte chunks.

The counter asks for its 152 bytes of code, an 8-byte header and 16 spare bytes, rounded up to three chunks, 192 bytes. Its code starts at a random offset inside the spare bytes, and every byte of the pack that holds no code is 0xcc, the x86 breakpoint instruction int3. Before our loads, /proc/vmallocinfo in the VM listed one pack, at 2,101,248 bytes, 2 MB and a guard page. Loading 1,000 small programs of 146 bytes each added 192,000 bytes to the kernel's running total, bpf_jit_current, and no pack. Twenty programs of 300,026 bytes each needed three more packs, and all three were freed with the programs (step 4 of book/labs/jit-root.sh, 12 November 2026).

Until 2022 every image had whole pages of its own. Song Liu's commit that brought the pack, in February 2022, gives the reason. Most programs are small but took a page each, and many of them put pressure on the instruction TLB, the CPU's cache of address translations for code, which slows the whole machine.

Every image is also charged against net.core.bpf_jit_limit, which the kernel sets at boot to half the range of addresses that x86-64 keeps for modules and BPF code, 528,482,304 bytes in the VM (bpf_jit_charge_init()). A loader with CAP_BPF may go past it. For any other, bpf_jit_charge_modmem() refuses, the JIT treats the refusal as a failed allocation, and the load fails with error 524 because the program was not translated. That includes an ordinary user's classic socket filter and seccomp filter, which the kernel converts to eBPF and gives to the same JIT. With the limit set to 1, both failed for the user nobody and worked for root.

Constant blinding

Every constant in a program becomes bytes in executable memory, and the loader chooses those bytes. JIT spraying is an attack that loads programs whose constants, read from the middle of an instruction, are themselves x86 code, and then uses some other kernel bug to jump there. The random start and the int3 filling of the previous section were the first answer, after Keegan McAllister published the attack against the BPF JIT. Constant blinding, added by Daniel Borkmann in May 2016, is the second: a rewrite just before the JIT that never puts a loader's constant into the image as it was written.

bpf_jit_blind_constants() in core.c draws a random number for each instruction with a constant and writes the instruction as three. The first moves the constant XORed with the random number into a hidden register, AX, the second XORs AX with the same random number, and the third is the original operation with AX in place of the constant. A 64-bit load of an address becomes seven instructions, and a move of zero becomes an XOR of the register with itself. bpftool prints AX as r12, and the x86 JIT keeps it in r10, as shows for four of the counter's slots.

Blinding is off by default. net.core.bpf_jit_harden at 1 blinds the programs of loaders without CAP_BPF, and at 2 it blinds every program (bpf_jit_blinding_enabled() in include/linux/filter.h). Either value also takes every BPF program out of /proc/kallsyms, because bpf_get_kallsym() lists none while hardening is on, so at 1 bpftool printed the counter's x86 under a bare address although nothing in it was blinded.

At 2 the counter grew from 29 slots and 152 bytes to 60 slots and 333 or 334 bytes, the length changing from load to load with the random constants. It ran in the same 499 to 509 ns as with hardening off. The counter without bpf_printk(), measured in an earlier session the same day, doubled to 48 slots, grew from 129 to 269 bytes and kept its 155 ns a run.

The price is paid at load time, and it grows fast. Each rewrite goes through bpf_patch_insn_data(), which moves everything after the patched instruction, so the work grows with the square of the program's length. Blinding took 11 to 12 µs for the counter, 4.2 ms for 1,000 additions, 0.39 s for 10,000, 5.1 s for 30,000 and 58 s for 100,000 (bpftrace on bpf_jit_blind_constants(), same VM).

Tail calls, and the count the JIT keeps

A tail call ends one program by jumping into another, which reuses the first one's stack frame and never returns to it. The programs to jump to sit in a program array, a map whose values are programs, and the call names a slot by number. User space fills a slot with a program's descriptor, and prog_fd_array_get_ptr() in arraymap.c takes a reference on the program. It then asks bpf_prog_map_compatible() in core.c whether the program matches the array's owner, the first program to use the array, in type, in having been translated by the JIT, in its sleepable flag and in its expected_attach_type, among other properties. A socket filter offered to the array of a tracepoint program was refused with ‑EINVAL.

"The kernel stack is precious, so this helper reuses the current stack frame and jumps into another BPF program without adding extra call frame."

Alexei Starovoitov, commit message of 04fd61ab36ec, "bpf: allow bpf programs to tail-call other bpf programs", Linux 4.2

, redrawn from a Cloudflare post that read the x86 the JIT writes for a tail call, shows what happens at run time. Before the jump, the JIT's code checks that the slot exists, that the chain has made fewer than 33 tail calls, and that the slot holds a program. If any check fails, the program goes on at its next instruction. The limit is MAX_TAIL_CALL_CNT in include/linux/bpf.h, and it is counted while the program runs, because the array can change after the verifier has finished. The jump lands 16 bytes into the target, at the second endbr64 of , past the target's own frame setup, because the target keeps the caller's frame.

2022 and nowThe Cloudflare post shows the tail-call count passed between programs in rax. In v7.2, rax carries a pointer to the count, which lives on the first program's stack. The three checks have not changed.

The jump itself goes through a register that holds the target's address. On the VM's CPU, which has enhanced IBRS, emit_indirect_jump() writes a plain jmpq *%rcx. Where the kernel uses retpolines, it writes a jump to a retpoline instead, a sequence that keeps the CPU from speculating through the jump.

We split the counter into count_writes, which only calls bpf_tail_call(ctx, &jmp_table, 0), and count_update, which counts. The x86 JIT pops the first program's saved registers, frees its stack and jumps past the second's frame setup. Only r1, the program's argument, is passed on, so count_update must call bpf_get_current_pid_tgid() again. A program that tail-called itself ran 34 times for one event, its first run and 33 tail calls.

The direct form, patched in place

Because the counter's slot is a constant, record_func_key() in verifier.c remembers it. For a loader with CAP_BPF and constant blinding off, bpf_do_misc_fixups() gives the call a poke descriptor, a record of where the jump for that map and slot lies in the program's code. The JIT writes a direct tail call there, a five-byte jump pointed at the target or turned into a no-op (), and bpf_tail_call_direct_fixup() fills it in from the slot as the image is finished. Only the check on the count remains, because the slot is known and whether it is empty is written into the code.

The direct form costs almost nothing to run. A socket filter's test run took 19 to 21 ns with or without a direct tail call, against 25 to 27 ns with the slot computed from the packet (bpftool prog run, two sessions on kernel 7.2.15 in the VM, 12 November 2026). The split counter cost 157 to 158 ns a run against 155 to 158 for the whole counter (16 virtual CPUs). Reading the slot from a global, which keeps the three checks of , raised it to 161 to 162.

The price moves to the update, drawn in . The array lists the programs whose poke descriptors name it, and smp_text_poke_single() rewrites each matching site, writing an int3 first and interrupting every CPU three times. With 16 virtual CPUs a replacement took 0.05 to 1.1 ms for each program with a direct tail call to the slot, and 9 to 30 µs with two virtual CPUs. Emptying the slot took 5 to 7 ms a program, most of it a wait for a grace period.

Two habits of the pair surprised us. bpftool reported run_cnt 0 for count_update, because the statistics are kept around the program the hook calls, whose time then includes the second half. And when the loader exited with only the link pinned, the array lost its last user reference and was emptied, count_update and the counter's map were freed, and count_writes fell through on every write.

Inside the v7.2 source

lists the code this chapter has read, in the order a load reaches it. bpf_check() resolves map descriptors before the walk, runs the rewrites after it, stops its clock and hands the program to __bpf_prog_select_runtime() in core.c. That function decides whether a JIT is required, has bpf_prog_jit_compile() blind a copy of the program if hardening asks for it, and calls bpf_int_jit_compile(), the entry of the x86 JIT.

bpf_int_jit_compile() is the loop of . It allocates addrs[], one entry per instruction holding the offset where that instruction's x86 ends, fills it with the guess, and calls do_jit() until two passes agree. do_jit() writes the prologue with emit_prologue() and then switches on each instruction's opcode; the case for BPF_JMP | BPF_TAIL_CALL calls emit_bpf_tail_call_direct() when the instruction's immediate names a poke descriptor and emit_bpf_tail_call_indirect() otherwise.

When two passes agree, bpf_jit_binary_pack_alloc() charges the size against the limit and takes chunks from a pack. After the last pass, bpf_jit_binary_pack_finalize() copies the image into place and bpf_tail_call_direct_fixup() points each direct tail call at its slot's program. Back in __bpf_prog_select_runtime(), a program left untranslated fails with -ENOTSUPP, and bpf_check_tail_call() runs the owner check against every program array the program uses, which is why a mismatch is reported after a verifier log that ended cleanly.

What it costs

CPU
The JIT took 6.9 to 16.6 µs for the counter, median 8.2 over ten loads, against 100 to 414 µs of verification, median 157; for long generated programs it took 38 to 62 ns a slot against 3 to 4.5 µs of verification (bpftrace on bpf_int_jit_compile(), kernel 7.2.15 VM, 12 November 2026). At run time a direct tail call cost nothing measurable and an indirect one 6 ns. Blinding left run time alone and took 11 to 12 µs to load the counter and 58 s for 100,000 instructions.
Memory
About 5 to 7.5 bytes of x86 a slot, 2.2 to 2.75 times that when blinded, in 64-byte chunks of shared 2 MB packs: 192 bytes for the counter, charged against bpf_jit_limit (528,482,304 bytes in the VM). A program array takes 8 bytes a slot and a 304-byte header.
Switches
None at run time: a tail call is a jump inside the kernel. One bpf() call changes a slot: 0.8 to 3.7 µs, plus 0.05 to 1.1 ms for each direct tail call naming it, or 5 to 7 ms each when emptying it.
Locking
None when the program runs. Loading takes pack_mutex to allocate the image; a slot update takes poke_mutex and, for each call site, text_mutex and interrupts to every CPU.

Keep the JIT's defaults unless untrusted users load programs; at bpf_jit_harden=2 expect lost symbols, no direct tail calls and load times that grow with the square of program size. Give tail calls a constant slot, keep a user reference on every program array while its programs run, and replace programs rather than emptying slots.

When it goes wrong

Most failures in this chapter happen after the verifier has accepted the program, so its log is no help: it ends cleanly, and the load still fails, or the program loads and does less than expected. pairs each symptom we met with its usual cause and the command that tells it apart. The first three rows are error 524 in its three forms, each a program the JIT did not translate on a kernel with nothing else to run it. An ordinary user is most likely to meet the third, through a seccomp filter.

The middle rows belong to tail calls, which fail quietly by design: a failed check sends the program on to its next instruction, so a count placed after the call is the cheapest way to see it. The last rows are about reading the machine code. Hardening hides every program's name and changes the code at every load. The perf of this distribution can count samples in a program but cannot disassemble it, which leaves bpftool's dump as the view that always works.

Recap

The kernel used in this book has no interpreter, so a program the JIT cannot translate does not load, and the error, 524, comes after a verifier log that ended cleanly. Between the walk and the JIT the kernel rewrites the program, giving maps and helpers their addresses and writing some map lookups in place, and the JIT then turns each instruction into a few x86 instructions, pass after pass until the length repeats, into 64-byte chunks of a shared pack that is read-only and executable. Constant blinding hides every constant behind a random XOR, three instructions for one, at a cost paid at load time that grows with the square of the program's length. A tail call reuses the caller's frame, at most 33 times in a chain, and with a constant slot the JIT writes a direct jump that costs nothing to run and that the kernel rewrites at every call site whenever the slot changes. The counter is now 152 bytes of x86 with a name in /proc/kallsyms, and nothing calls it yet.

JIT
just-in-time compiler: translates a whole program into native code once, when it loads
native code
instructions of the CPU itself, here x86-64
trampoline
a short piece of x86 the kernel writes so that a kernel function's entry can call a program and continue
program pack
a 2 MB block of read-only executable memory that the JIT shares out among programs' images in 64-byte chunks
JIT spraying
an attack that hides machine code in a program's constants and jumps into the middle of an instruction to run it
constant blinding
a rewrite before the JIT that replaces each constant with two random values whose XOR is the constant
tail call
a jump from the end of one program into another, which reuses the first one's stack frame
program array
a map whose values are programs, indexed by slot for tail calls
poke descriptor
a record of where in a program's machine code the jump for one program-array slot lies, so that the kernel can rewrite it
direct tail call
a tail call to a constant slot, compiled to a five-byte jump that the kernel points at the slot's program or turns into a no-op

Two slots, both after the map lookup. 232 bytes are 232 / 8 = 29 slots, and 29 − 27 = 2. htab_map_gen_lookup() in kernel/bpf/hashtab.c replaces call 0x1 with a call to __htab_map_lookup_elem() followed by if r0 == 0x0 goto pc+1 and r0 += 56, which moves r0 past the entry's header and key to the value. Check it with bpftool prog dump xlated: slots 9 and 10. Counting the map update as well would suggest more, but the update became a direct call to htab_map_update_elem() in the same single slot.

Six bytes in the first pass, two in the second, and four passes in all. By the guess the two skipped instructions take 2 × 64 = 128 bytes, one more than a two-byte jump can reach, so do_jit() writes the six-byte form and the first pass gives 156 bytes. The second pass works from real addresses, the jump shrinks by 4 to two bytes, and the image is 152 bytes; the third pass agrees, so the JIT takes memory for the image and writes it in a fourth. bpftrace on the return value of do_jit() showed 156, 152, 152, 152 on all ten loads. An answer of three passes stops at the first pass that agrees, but the image is written in the pass after it.

3,002 slots. Each of the 1,000 additions becomes three instructions, a move of the constant XORed with a random number into AX, an XOR with the same number, and the addition from AX; r0 = 0 has a zero constant, which bpf_jit_blind_insn() turns into one XOR of r0 with itself, and exit has none, so 3 × 1,000 + 1 + 1 = 3,002, as measured in step 5 of book/labs/jit-root.sh. The x86 length changes because the random values change the encoding: a non-negative value fits the shorter 32-bit move and a negative one needs the sign-extended 64-bit form (emit_mov_imm32()), so 100,000 blinded additions came out at 1,649,911 to 1,650,097 bytes. It is tempting to answer 2,002, two slots for each constant, but the original instruction stays as the third, now reading AX.

The verifier accepted the program and the JIT could not translate it. Error 524 is ENOTSUPP, a kernel-internal code, and __bpf_prog_select_runtime() in kernel/bpf/core.c, the last step of bpf_check(), returns it when a program was not translated and a JIT is required. With no interpreter to fall back to, the load fails after a clean verifier log. JITs for smaller architectures lack some instructions, such as some atomics. Suspicion falls first on the verifier, yet its log ends without a reason because it found none.

net.core.bpf_jit_limit. The kernel turns a classic seccomp filter into eBPF and gives it to the JIT, which charges the image against the limit in bpf_jit_charge_modmem(); past the limit that function refuses any caller without CAP_BPF, so the image is never allocated and the program is not translated. With no interpreter, __bpf_prog_select_runtime() reports -ENOTSUPP, and that is the errno the user sees. Root passes because CAP_BPF lets it go past the limit. Step 8 of book/labs/jit-root.sh set the limit to 1 and saw both a seccomp filter and a socket filter fail for nobody. Expecting EPERM is natural, since the refusal inside the kernel is -EPERM, but the JIT treats it as a failed allocation and the caller receives -ENOTSUPP, the error for any program left untranslated.

net.core.bpf_jit_harden at 1 or 2, or net.core.bpf_jit_kallsyms at 0. bpf_get_kallsym() in core.c lists no BPF program while bpf_jit_kallsyms_enabled() is false, and that function returns false whenever hardening is on or the kallsyms switch is off; sysctl net.core.bpf_jit_harden net.core.bpf_jit_kallsyms tells which. The kallsyms switch changes no code. Hardening at 1 changes none either for a root loader, whose programs are not blinded, although their names vanish; at 2 every program is blinded as well. The likely wrong conclusion is that the programs were never JIT-compiled, but bpftool still prints jited sizes and dumps the x86, only under a bare address.

34 times: the first run and 33 tail calls. The JIT's code compares the count with MAX_TAIL_CALL_CNT, 33, before each jump and adds 1 after the checks pass. The 34th attempt finds the count at 33, fails the check, and the program goes on after the call, so it ends normally. The check is in emit_bpf_tail_call_indirect() in arch/x86/net/bpf_jit_comp.c. An answer of 33 counts the jumps and forgets the first run, which was not a tail call.

About 0.18 seconds: 32 grace periods of about 5.6 ms. Emptying the slot makes bpf_arch_poke_desc_update() patch each call site twice and call synchronize_rcu() between the patches, so that no CPU is left inside a half-rewritten site, and it does this once for every program in the array's poke list whose descriptor names slot 0. Step 6 of book/labs/ch16-root.sh measured 180 to 195 ms. Filling the slot again patches two places per site too, but waits for no grace period, which took 57 to 64 ms here, about 1 ms a site for the interrupts to 16 virtual CPUs. Expecting microseconds, as for an ordinary array, is the usual mistake; that holds only while no direct tail call names the slot.

It runs on every write; its time is counted under count_writes. The statistics are taken in __bpf_prog_run() (include/linux/filter.h), which adds to run_cnt and run_time_ns of the program the hook called. A tail call jumps into count_update's machine code past its frame setup and never passes through that wrapper, so the 157 to 158 ns that count_writes reports cover both halves. It is tempting to conclude that the slot is empty, but then fell_through in the counter's .bss would count the writes, and the map total would stop; in step 4 it stayed at 0.

The owner check refused it after verification. When bpf_check() has finished, __bpf_prog_select_runtime() in core.c calls bpf_check_tail_call(), which runs __bpf_prog_map_compatible() against every map in the program's used_maps that holds programs. The array's owner is count_writes, a tracepoint program, so a socket filter does not match and the load returns ‑EINVAL with the verifier's log already complete; step 5 printed that log followed by libbpf: prog 'caller': failed to load: -EINVAL. Searching the log for a verifier error finds nothing, because the verifier accepted the program. The same check refuses the filter when user space tries to put it into a slot.

Common wrong turn. Looking for call 0x1 or for helper names in the jited dump. The kernel renamed the call before the JIT ran, and the jited dump shows only addresses; the xlated dump is where the names are.

What this shows. The JIT costs about 40 to 60 ns a slot and the verifier 3 to 4 µs for these programs, so translation is about a seventieth of the load; both grow in step with the program. Blinding does not: it took 4.2 ms at 1,000 instructions, 388 ms at 10,000 and, in the same step, 5.1 s at 30,000 and 58 s at 100,000, about ten times as long for each tripling, because every patch moves the rest of the program.

Reading the first lines bpftrace prints as the generated program's. libbpf and bpftool load small probe programs of their own, which jit.bt reports too; take the lines that carry the program's name. Common wrong turn. Pinning only write_counts. The counts stay readable, but the array still loses its last user reference, so the counter stops counting while its map looks healthy.
