Reading PREVAIL: a verifier built on abstract interpretation

PREVAIL checks an eBPF program the way the textbooks of the refresher describe: it joins the states of paths where they meet, widens at loops, and keeps relations between a packet pointer and the packet's end, so that a loop costs it the same at any bound. We read its PLDI 2019 paper in the paper's own notation, set a toy of its fixpoint beside a toy of Linux's walk on one packet loop, and weigh what each design buys, what it costs and where PREVAIL runs today.

One loop, two verifiers

The paper is Simple and Precise Static Analysis of Untrusted Linux Kernel Extensions by Elazar Gershuni, Nadav Amit, Arie Gurfinkel, Nina Narodytska, Jorge A. Navas, Noam Rinetzky, Leonid Ryzhyk and Mooly Sagiv, presented at PLDI in Phoenix in June 2019. We read the copy that the project's site links, dated 5 May 2019 and paginated as in the proceedings, and the repository of its tool, PREVAIL, at commit 97093b5b3264 of 13 November 2026. Its argument begins with loops, and so does ours, with a loop small enough to follow by hand through both verifiers.

An XDP program adds up the first N bytes of a packet, in two versions. sum_once checks once that N bytes are there and then loops, while sum_each checks in every round that the byte it is about to read lies before the end. We compiled both with clang 23 at four bounds and loaded them in a VM running Linux 7.2.15, reading the verifier's statistics as in .

Linux walks the loop once per round. Each round runs the seven slots from 8 to 14 with r3 known to the last bit. So sum_once costs seven instructions of walking per byte, 7N + 12 in all, and sum_each about ten. Verification took 0.13 ms at 16 bytes and 3.2 ms at 1,024 for sum_once, and 6.4 ms at 1,024 for sum_each, medians of three loads. The checkpoints grew from 4 to 105, about one every ten rounds, because inside a loop the walk saves a new one only after 20 jumps or 100 instructions (kernel/bpf/states.c, line 1397).

The last two lines of the figure show how the walk keeps the fact that makes the read in sum_each safe. After the check at slot 8, r0 prints as pkt(r=1) in the first round and pkt(r=2) in the second, since every packet pointer carries the number of bytes known to lie before the end (). That number changes every round, so no round's state falls within another's and the walk cannot stop early.

We did not build PREVAIL. In its place, book/labs/prevail/toy.py reads the same slots twice. Its abstract interpreter keeps one interval per register on the schedule PREVAIL uses at loop heads, and its walk follows one path at a time, as Linux does. The walk counts 124, 460, 1,804 and 7,180 instructions for sum_once and 168, 654, 2,568 and 10,254 for sum_each, the kernel's numbers to the instruction. The fixpoint evaluates 47 and 53 at every bound, and plots both.

The program as a graph of states

PREVAIL reads bytecode, as Linux does, because the compiler is no part of the trusted computing base (§2 of the paper). It turns the program into a control-flow graph over a core language, eBPFPL (§4.1). The commands are assignments, loads and stores of 1 to 8 bytes, a request for a shared region, and assume(B), which lets through only the states in which B holds. They sit on the graph's edges, so the two edges out of a conditional jump carry the assume of its test and of its negation. A value is a number or a pointer, and a pointer pairs a region (the context, the stack, the packet or a shared region such as a map value) with an offset.

The packet's start and end live in the context, yet the model keeps them in two registers that never change, data_start and data_end, which no instruction names. Such a register is a ghost variable, one that the analysis adds to describe the program and that the program never reads or writes. With it the pointer data + 8 of the paper's Table 2 becomes the pair (pkt, 8), and the packet check compares 8 with the end's offset, which is at most 64 KB, the bound Linux assumes (§6.1).

The analysis keeps one abstract state for each point of the graph, and a point's state is the join of the states its incoming edges bring. shows the states the toy keeps for sum_once at N = 16, with its test rewritten as r3 >= 16 for reasons the next section gives. The read at slot 10 is checked once, against a head state that holds r3 anywhere from 0 to 15, where the walk checked it sixteen times against one value each time.

An analysis is path-sensitive when it keeps a separate state for each path that reaches a point, as Linux's walk does until pruning shows that one path's state covers another's. PREVAIL is not, so its cost depends on the size of the graph and the price of the domain's operations. The number of paths does not enter, although on a loop with branches inside it multiplies with every round. The paper's bet, stated in §8, is that eBPF programs can be proved safe without path sensitivity.

Join, widen and narrow at the loop head

A loop head is the point where a back-edge lands, slot 8 in sum_once. Its state must hold for the first round and for every later one, so the analysis starts from what the entry brings, runs the body, joins what comes back and repeats until a round adds nothing. A state that one more round leaves unchanged is a fixpoint of the loop. Joining alone climbs one round at a time, as showed on four bits, and on our loop it would not end in practice. The sum in w2 grows by up to 255 a round, so its interval reaches the 32-bit ceiling only after about 16.8 million rounds; the toy, run with --widen-after 0, gives up after 100,000.

PREVAIL's schedule is in Extrapolator::compute_fixpoint() (src/crab/extrapolator.cpp, line 13), and the toy copies it. The first round back is joined, and from the second on the new state is widened against the old (widening_delay_ is 2). At the first widening it is also met with limits, registers within 32-bit ranges and offsets within their regions (calculate_constant_limits(), src/crab/ebpf_domain.cpp, line 164), a guess that later rounds keep only if the loop respects it. The climb stops on the first round whose result lies within the current state, and keeps that round's result. A descending phase follows, a meet with the next round and then narrowing, for at most 2,000,000 rounds.

A narrowing operator lowers a bound that widening raised to infinity to the value the next round gives it, and never raises one, so the descending phase can only gain precision. follows r3 at the head of sum_once. The join of round 1 gives [0, 1], and the widening of round 2 sends the upper bound to infinity. In round 3 the back-edge passes only the states where r3 >= 16 failed, so it brings [1, 15]. The round's result, [0, 15], lies within [0, +∞], and the climb stops there, which makes the read at slot 10 safe.

Two changes undo that. With --no-narrow the toy keeps the widened state, as the textbook widening of does, and the head stays at [0, +∞]. With the test as clang compiled it, r3 == 16, the back-edge carries the states where r3 is not 16. An interval cannot hold "any number but 16", since it is one unbroken stretch of the number line, so the round brings [1, +∞] and the read is refused. Both refusals are false alarms, and Linux raises neither, because in each round it knows r3 to the bit and decides the test.

The precision lost on the way shows elsewhere too. After the fixpoint the sum in w2 lies anywhere in [0, 232 − 1], where the walk leaves the loop knowing [0, 4,080]; no check reads the sum, so nothing is refused because of it. Linux has meanwhile borrowed a little of the idea. v7.2 compares a loop's state with the previous round's at the next call of an iterator, the return from a bpf_loop() callback and a may_goto (). There widen_imprecise_scalars() (kernel/bpf/verifier.c, line 7494) forgets the range of every scalar that no check has needed yet, a widening straight to "any value".

Four domains in one state

Intervals alone were not enough for the authors either. §3 of the paper draws three observations from the programs they studied: the analysis must track relations between pairs of registers, it must track values spilled to the stack as if they were registers, and enumerating paths is becoming infeasible as programs grow. A relational domain is one whose abstract values relate two or more variables, and the paper tried three, from cheapest to most expressive: Zone, Octagon and Polyhedra.

The zone domain keeps constraints of the form x − y ≤ c for pairs of variables, and a bound for each variable alone. It stores them as a matrix, or as a graph whose edges carry the constants. New constraints come from adding the constants along a path and keeping the smallest sum, a shortest-path closure whose cost is at worst cubic in the number of variables. On the check of sum_each in , slots 5 to 8 give three constraints, and their sum along the path from r5's offset to the packet's length is r5.off − len ≤ −1. That is the condition of the read at slot 9, in every round and whatever widening has done to r3.

Zone and Octagon proved 191 of the paper's 192 programs and intervals 128 (§7.2). Polyhedra proved 21 fewer than Zone, because its implementation stores coefficients in 64 bits and gives up when they do not fit, and Octagon cost more than Zone and proved nothing more, so Zone was chosen. Table 3 of the paper shows why a relation is needed at all. With a variable offset in r5, the safety condition data + r5 + 8 ≤ data_end has three variables; the offset encoding removes data, and the two that remain form a difference constraint.

A whole abstract state of the paper is a product domain, as in , with four components (§5.2), and lists them with their counterparts in today's code. Two components say what may hold: the tag of each register and stack cell, and the numbers, in the chosen numeric domain. The other two say what must hold, namely the stack bytes that hold only numbers and the cells that hold a whole stored value, so a join intersects them and keeps what both sides guarantee. Each stack cell is a variable of the numeric domain, which is how a value spilled to the stack keeps its relations.

The memory model is where PREVAIL's rules on information flow live. A store to the stack removes every cell it overlaps. A load of bytes that no single store wrote yields a number only if every byte held one, and an invalid value otherwise, so a program cannot read a pointer back a byte at a time (§4.2). Shared regions such as map values are tracked by size alone, since another program may change them at any moment (§5.1).

What it checks, and what its proof covers

The paper asks three things of a program (§2). Memory safety means that every access lies within its region. Information-flow security means that a program run for an unprivileged user cannot learn a kernel address. Reading an uninitialised register or stack byte therefore counts as a violation, a pointer may be compared only with one into the same region or with zero, and it may be stored only to the stack. Termination means that every run ends, and the tool of 2019 did not check it: "For programs with loops, our algorithm verifies safety, but not termination."

Today's PREVAIL checks termination when asked (--termination; by default it ignores it). It adds a ghost counter at each loop head, incremented every round, and asserts that the fixpoint bounds it by 100,000 (BoundedLoopCount, src/ir/syntax.hpp, line 500, checked in src/crab/ebpf_checker.cpp, line 281). The counter can be bounded only through its relation to a variable the loop tests, which the zone domain keeps. The repository's test of a loop of 1,000,001 rounds ends with r0 equal to the counter, and fails for passing the limit (test-data/loop.yaml). The toy, which has no relations, widens its counter to infinity and reports that each of our loops may not end.

The soundness argument is Theorem 5.6: if a program is verified safe, it is safe. It rests on three steps, from the concrete semantics of eBPFPL over mathematical integers, through a semantics in which each shared region is replaced by its size (Lemma 5.4), to the abstract transformers (Lemma 5.5). Machine integers enter only in §6.1, where a result that does not fit in 64 bits becomes an arbitrary value and pointer comparisons that might pass the 64 KB packet bound are refused. In 2019 unsigned comparisons could go either way, and bitwise operations were over-approximated. The theorem covers the model of §4, while the C++ code is tested, on files of small programs and the benchmark set.

The namePREVAIL's README spells it out as "a Polynomial-Runtime EBPF Verifier using an Abstract Interpretation Layer".

The gap between model and code has shown itself in advisory GHSA-65rv-h458-cq99 (CVE-2026-53671, published in September 2026) reports that before release 0.2.4 a store through a pointer to the context was modelled as doing nothing. A program could overwrite ctx->data, load it back as a packet pointer and read any address while PREVAIL answered PASS. In the paper's model the packet's bounds sit in ghost registers that no store reaches, so the proof could not see the case. Release 0.2.4 of 1 June 2026 fixed it with two other soundness bugs, and release 0.2.6 of 3 August lists fifteen more, most of them programs that passed while making an unsafe access. The lesson of holds here too: a proof covers its model.

The evaluation, read critically

The benchmark set has 192 programs from six projects: 86 from the Linux tree, 23 from linux-prototype, 18 from Open vSwitch, 5 from Suricata, 24 from Cilium and 36 from Cilium's tests (§7.1). The introduction counts 111 used during development and 81 more for the final evaluation, while §7.1 names Linux, Open vSwitch and Suricata as the projects that guided the design, which together make 109. Every program had passed the Linux verifier, so the set cannot show a safe program that Linux refuses, and Chaignon's summary adds that it is small and networking-heavy, with no large tracing program. collects the results.

On cost, PREVAIL verified each program in 5.2 seconds or less, at about 1,500 instructions a second. The Linux verifier was faster on every benchmark, which the authors expected, since the programs had been shaped to fit its limits (§7.3.1). Memory is the weak point: read from the paper's Figure 10, the zone domain used up to about 1.5 GB for the largest programs, of some 3,400 instructions. The authors call that "still unacceptable for an in-kernel verifier" and propose to compute the fixpoint in user space, leaving only a final check to the kernel. Alexei Starovoitov's commit c04c0d2b968a of April 2019 gives a scale for comparison: a non-debug kernel walked its whole budget of 1,000,000 instructions in a tenth of a second on a typical x86 machine.

One program of the 192 stayed unproved, and the paper does not say which or why. Nine commits in the projects' histories had reshaped code to pass the Linux verifier, and PREVAIL proved the original version of each. In one of them the kernel recognised data + X > data_end but not data + X <= data_end, which the authors read as a sign of "syntactic pattern matching and ad hoc case analysis". Six more commits had cut loop bounds or moved branches to fit the complexity limit, and PREVAIL proved each earlier version without taking longer. Cilium, for one, had capped a loop over IPv6 extension headers at four rounds (Figure 12).

The experiments ran on 4.19, which refused every back-edge, and Linux has changed since. 5.2 raised the budget to 1,000,000 instructions, 5.3 added bounded loops by walking every round (commit 2589726d12a1), and bpf_loop() in 5.17, bpf_for() in 6.4 and then may_goto gave loops a place where the walk can stop going round. Those forms proved the hash loop of in 63 to 91 instructions at any bound, may_goto only with its counter kept in a map value (). A plain loop such as ours or the paper's is still walked once a round. We did not re-run the 192 programs or Figure 11 on v7.2, so the comparison of verdicts stands for 4.19 alone.

Where PREVAIL runs

The repository is github.com/vbpf/prevail. The paper's link, github.com/vbpf/ebpf-verifier, now redirects there, and the README names commit d29fd26345c3 as the version the paper describes. The code is C++23, has 2,431 commits on its main branch and builds on Linux, Windows and macOS, and its latest release, 0.2.6, is of 3 August 2026.

Its main user is eBPF for Windows, whose README of 13 November 2026 describes three ways to run a program, listed in . In the preferred one, the bpf2c tool passes the bytecode to PREVAIL and, if it passes, translates each instruction into C, which is built into a Windows driver. The JIT mode verifies in a user-mode service, eBPFSvc, and compiles with uBPF's JIT, so in both modes PREVAIL runs in user space, where the paper's memory figures said it belonged. uBPF, the user-space library behind that JIT, has no static verifier of its own. It offers instead an interpreter-only profile that checks pointers at run time.

The project does not aim to agree with Linux on every program. Its parity notes, written against Linux 6.18, list the instructions, helpers and map types still missing. They put "complete precision parity with the Linux verifier" among the non-goals, since the two use "fundamentally different analysis strategies with different precision profiles", and they do not plan to unroll loops as the walk in effect does. A pass from one verifier therefore shows a program safe under that verifier's model of its platform, and only a load on the other platform gives the other's verdict.

The instruction set both read is the one standardised in RFC 9669 (October 2024), whose read-with card is in . PREVAIL's options take the RFC's conformance groups by name, from base32 to packet, plus a callx group that the RFC does not list. The RFC's §6 names Linux and PREVAIL as the verifiers that "provide many details" of what a verifier checks, and leaves those details to future IETF work. The standard thus fixes what an instruction means, while what a program may do stays each verifier's decision.

Research has continued from PREVAIL's design. VeRefine (OOPSLA 2025, by Hamza, Zavalía, Gurfinkel, Navas and Fedyukovich) replaces the fixpoint with a flow-sensitive refinement type system. Its types are inferred in user space as a proof certificate, so that only a checker must run in the trusted environment, the split the 2019 paper proposed for its memory problem. Its authors report it faster than PREVAIL on most of their industrial benchmarks; we read its abstract and introduction only.

Why Linux kept its walk

Linux answered the loop problem in the month the paper was presented, and in its own way. Alexei Starovoitov's commit 2589726d12a1, "bpf: introduce bounded loops", of 15 June 2019, lets "the verifier simulate all iterations of the loop" and credits the key idea to an earlier approach of Edward Cree's. It adds that "additional state pruning heuristics make such brute force loop walk practical even for large loops". The walk of is that decision, grown since.

"Our conclusion was that the best use we could make of PREVAIL was to incorporate some of its detail ideas, while rejecting the overall architecture."

Comment by ecree on "Bounded loops in BPF for the 5.3 kernel", LWN.net, 5 August 2019

The most direct account we found of why the design was not adopted is that comment, posted as ecree in reply to one by anadav that had pointed to the paper. Its writer gives the analysis as their own and believes the other developers broadly agree. The comment lists four obstacles. The zone domain cannot hold difference constraints together with the congruences that alignment checks need, and the paper does not explain how a fixpoint would prove termination. The defences against speculative execution may have no abstract semantics, and the memory use is large.

What the writer wanted to take was the proposal of §7.3, a proof supplied from user space and only checked by the kernel. We found no later statement, and two obstacles have moved since: PREVAIL now proves termination with its loop counter, and v7.2 widens imprecise scalars at three loop forms.

What it costs

CPU
PREVAIL with Zone, 2019: 5.2 s or less a program, about 1,500 instructions a second, roughly linear in size (Core i7 at 3.4 GHz, Linux 4.19). Linux v7.2 on our loop (7.2.15 VM, 16 vCPUs, 13 November 2026, medians of three loads): 0.13 to 3.2 ms for 124 to 7,180 instructions of sum_once, 0.15 to 6.4 ms for 168 to 10,254 of sum_each; its whole budget of 1,000,000 instructions took a tenth of a second in 2019 (c04c0d2b968a). The toy, Python 3.14 on a Ryzen 7 8845HS: the fixpoint's 47 or 53 transfers in 0.3 to 0.5 ms at any bound, the walk 0.5 to 30 ms.
Memory
PREVAIL: up to about 1.5 GB resident at 3,400 instructions (Figure 10 of the paper). Linux: 4 to 106 checkpoints on our loop. The toy: 16 MB, the interpreter's own.
False alarms
Zone and Octagon 1 program in 192, intervals 64, Polyhedra 21 more than Zone (§7.2). The toy's intervals: 2 of our 3 loop programs, and no loop proved to end. Linux 4.19: 9 programs reshaped to pass it, all 9 proved by PREVAIL.
Upkeep
PREVAIL: 2,431 commits; three soundness fixes in release 0.2.4 (June 2026) and fifteen in 0.2.6 (August 2026); parity with Linux 6.18 tracked by hand. The toy: about 600 lines.

On Linux, write loops in a form the walk can stop early, bpf_loop(), bpf_for() or a small constant bound, and otherwise expect it to cost about the body's length per round. PREVAIL's design is the better trade when loops have large or variable bounds and verification runs outside the kernel, at build time or in a user-mode service, where seconds and hundreds of megabytes are affordable; for a fixpoint verifier, keep each length check next to the read it guards. Treat a pass from either verifier as evidence about that verifier alone.

When it goes wrong

The first five rows of are costs of abstraction, facts that a joined and widened state cannot hold, and the toy shows each in a second; PREVAIL's answers are a relation, a descending phase and a counter tied to the loop. The last three compare a verifier with something outside it, the other verifier or its own proof, and only the source, the changelog or a load on the other platform settles them.

The walk goes round once per byte; the fixpoint goes round until a round adds nothing. Only one of them can depend on how many bytes there are.

The back-edge leaves slot 13 only when r3 >= N failed, so it carries r3 in [1, N − 1]. Join that with the entry's [0, 0], and compare the result with what the read needs.

Recap

PREVAIL keeps one abstract state per point of a program's control-flow graph, joins where paths meet, widens at loop heads from the second round and then narrows, so on our loop its toy settled in four rounds at every bound while Linux v7.2 walked 7N + 12 instructions. Its state combines tags, numbers in the zone domain and two sets about the stack, and the zone domain keeps facts such as r5 + 1 ≤ end that intervals lose. Theorem 5.6 makes the method sound for a model of eBPF, the code is tested, and a 2026 advisory showed the gap between the two. On Linux 4.19 and 192 programs that Linux had passed, the paper found one false alarm and used up to about 1.5 GB. PREVAIL now runs in user space under eBPF for Windows, Linux kept its walk and borrowed a widening for its loop forms, and the epilogue looks back at the limits of all of this.

About 28,684 instructions for Linux and 47 transfers for the fixpoint. The walk costs seven instructions a round plus twelve outside the loop, 7N + 12, which held at all four measured bounds, and the toy's walk, which matched those, counts 28,684 at 4,096; the kernel was not run at that bound. The fixpoint evaluates the eight slots before the loop and the four after it once, and the seven of the loop five times, for the four rounds of the climb and the descent and a last pass that records the states, whatever N is. It is tempting to scale the fixpoint's count with N as well, but N enters only as a constant in the exit test, and the climb ends after the same rounds.

Slot 13's r3 == 0x10 becomes r3 >= 0x10. The back-edge carries the states in which the test failed: "r3 is not 16" in the first form, which an interval cannot express, so the widened [0, +∞] survives, and "r3 is below 16" in the second, which cuts the back-edge to [1, 15] and the head to [0, 15]. Linux decides the test in every round from r3's known value, so either form ends its walk after sixteen rounds. A common mistake is to blame the widening alone; with the second form the same widening happens and the climb still ends at a safe state.

Nothing that can be relied on for Linux. PREVAIL proved the program safe under its own model of Windows' program types and helpers, with a different precision profile, and its parity notes say outright that matching Linux's decisions on every program is not a goal; Linux may refuse the program, as it refused the nine in the paper that PREVAIL proved, or need a different loop form. The team should load the object on each Linux kernel they support, with the verifier's log level set as in , in CI. Reading a Windows pass as a portable proof would be a mistake.

The theorem is about eBPFPL, the model of §4, and the advisory is about the C++ code. In the model the packet's start and end are ghost registers that no store can reach, and a store outside the stack has no visible effect, so overwriting ctx->data and reloading it as a packet pointer is not a run the model contains. The code read those fields from the context while treating stores to it as no-ops, and release 0.2.4 now refuses such stores. The lesson, as with Agni, is to ask of any proof which model it covers and how the code was matched to it; "proved sound" says nothing about the matching.

Memory, first: the paper measured up to about 1.5 GB for its largest programs and called that unacceptable in the kernel, while Linux's walk keeps a few checkpoints. Precision, second: a fixpoint loses facts the walk keeps, such as a loop that ends on an equality test, and the 2019 developers also doubted that alignment checks and the defences against speculative execution fit the zone domain. What Linux took instead is a narrow widening, widen_imprecise_scalars() at iterator, callback and may_goto loops. Claiming that the move would cost nothing because the asymptotic complexity is better overlooks the constant factors the paper itself reports.

A pointer is a region and an offset, and the packet's start has offset 0, so data + r5 + 8 ≤ data_end becomes r5 + 8 ≤ the end's offset, a relation between r5 and one ghost variable. The interval domain keeps a range for each variable alone; from r5 in [0, 100] and the end in [0, 65,535] it cannot say that r5 + 8 lies below the end on every run, even when a check just established it. Only a domain with constraints on pairs, Zone among them, keeps r5 − end ≤ −8. One might think a narrower interval for r5 would do, but the end's lower bound would then have to rise with it.

The tags θ and the numbers d are may information, over-approximating what registers and cells can hold, so their join is the domains' own join. The set ζ of stack bytes holding only numbers and the set δ of cells holding a whole valid value are must information, true on every run that reaches the point. After paths meet, a byte is surely numeric, or a cell surely valid, only if it was on both paths, so the join intersects them. Taking the union would be the mistake: a pointer stored on one path could then be read back a byte at a time as a number.

Every program in the set had already passed the Linux verifier, and their authors had shaped them to fit its limits, unrolling loops and cutting bounds, so the set favours the walk; the authors say so. The experiments that escape the bias are those built from programs the kernel refused: the nine commits that reshaped code after false alarms, the six that cut loops or moved branches to fit the complexity limit, the two strncmp loops of Figure 11, and the six loops with variable bounds. Reading the speed result as a verdict on the two designs would ignore that selection.

What this shows. The walk's instructions and checkpoints, 124, 460 and 1,804 with 4, 9 and 28, equal the kernel's at each bound and grow with N, because each round is a new state. The fixpoint's 4 rounds and 47 transfers do not. The runs part in round 3: the back-edge brings [1, 15], the round's result [0, 15] lies within the widened [0, +∞], and the first run keeps it, which bounds the read at slot 10 by offset 15 against a packet of at least 16 bytes; --no-narrow keeps [0, +∞], and the read is refused.

Common wrong turn. Reading the alarm as a fault of widening alone. The widening is the same in both runs; what differs is whether the analysis takes the next round's narrower result, and the narrower result exists only because the test r3 >= 16 cuts the back-edge.
