A scheduler loaded like a program

A scheduling class is a set of functions through which the Linux scheduler core asks one policy what to run. Each task belongs to one class: the fair class for ordinary tasks, the real-time and deadline classes above it, and since 6.12 an extensible class, sched_ext, whose policy is a BPF program set. Its smallest example is scx_simple. We build it with the tree's own makefile, which compiles libbpf and bpftool from tools/ and dumps vmlinux.h from the running kernel's BTF. The host needs nothing beyond clang, gcc, make, Python and the libelf and zlib headers, although the sparse clone this book uses needed more of tools/ and scripts/bpf_doc.py checked out first; book/labs/schedext-root.sh lists the paths.

Started as root, the loader prints two counters a second and the kernel logs one line. shows the rest of what changed. /sys/kernel/sched_ext/state went from disabled to enabled, and the scheduler's name sits in root/ops. The shell that typed the commands reports ext.enabled 1, so the scheduling decisions for that shell, for the loader and for every other ordinary task in the VM are now made by BPF programs.

bpftool sees an object of a kind we have not met, a map of type struct_ops named after the scheduler. Its dump lists the members of a C structure, some holding a program's ID and the rest holding zero, and beside it are eight programs of type struct_ops, one per filled member. The link of type struct_ops belongs to the loader's process.

The page lagssched-ext.rst in v7.2 shows the per-scheduler counters in /sys/kernel/sched_ext/simple/events. The kernel names the root scheduler's directory root (ext.c line 6958), and the counters were in /sys/kernel/sched_ext/root/events.

The counter of the earlier chapters keeps working as before. We loaded it with bpftool prog load … autoattach and made 200,000 one-byte writes with dd, once under the fair class and once under scx_simple. Both times the map held 200,003 writes for the dd process, and count_writes took 533 ns a run under the fair class and 543 ns under scx_simple, with its bpf_printk() still in place. That is what we should expect, because the counter runs inside the write() system call of whichever task is on the CPU, and the scheduler only decides which task that is.

A table of function pointers, filled by programs

A struct_ops map is a map with a single entry whose value is a kernel structure of function pointers, filled with BPF programs instead of kernel functions, so that a subsystem written to call a table of operations calls the programs. follows the loader through the four system calls that build one. In the object file the table is a global variable of type struct sched_ext_ops in a section called .struct_ops.link, and each program sits in a section named struct_ops/ followed by its name. The macros SCX_OPS_DEFINE() and BPF_STRUCT_OPS() in the tree's headers write both. libbpf matches the variable's type against the kernel's BTF and creates the map from the BTF ID of a wrapper structure that the kernel declares for each table, bpf_struct_ops_ followed by the table's name; then it loads one program per filled member.

The verifier needs to know which member a program is for, because a member's prototype decides what the program may read and what it must return. The loader says so in two fields of BPF_PROG_LOAD, the table's BTF ID and the member's index, which travels in expected_attach_type. strace decodes that field as an attach type, so it printed BPF_CGROUP_INET_INGRESS for select_cpu at index 0 and BPF_XDP_DEVMAP for init at index 33.

check_struct_ops_btf_id() in the verifier then refuses a program without a GPL-compatible licence, checks that the member is a function pointer, asks the subsystem's check_member() whether this program may fill it, and keeps the member's prototype as the program's own. From then on every read of an argument goes through btf_ctx_access(), which gives argument n the type of the prototype's nth parameter. In simple_enqueue, p is therefore a pointer to struct task_struct and enq_flags a scalar.

The map update makes the table callable: bpf_struct_ops_map_update_elem() walks the members of the structure in BTF order. A data member such as name or timeout_ms goes to the subsystem's init_member(), which checks it and copies it. A function pointer holding a program descriptor gets a trampoline, a short piece of machine code of the kind showed for fentry, which saves the arguments where a BPF program expects them and calls the program. The member in the kernel's copy then points at the trampoline. shows the result for scx_simple, with eight trampolines of 172 to 188 bytes in one page of executable memory (a map may use up to eight pages) and 29 members left NULL, which the subsystem treats as "not implemented".

The scheduler core does not know any of this. It calls sch->ops.enqueue(p, enq_flags), an indirect call through a structure, as it would call into a table compiled into the kernel, and lands in the trampoline. A map created with BPF_F_LINK stops at the state READY after the update; registration waits for BPF_LINK_CREATE, which calls the subsystem's reg() and returns a link whose release calls unreg(). A map without that flag, written in a section called plain .struct_ops, registers during the update and stays registered until the entry is deleted. sched_ext's reg() is where the scheduler starts, and its unreg() is where it ends, which is why the scheduler disappears when the loader's last reference to the link goes.

Other tables in v7.2

TCP congestion control was the first struct_ops table, added by Martin KaFai Lau in January 2020 for Linux 5.6 together with the map type. It shows how differently two subsystems can use the same mechanism. Its reg() calls tcp_register_congestion_control(), which adds the algorithm to the list of choices and changes nothing else, since a socket uses it only after asking for it by name, through setsockopt(TCP_CONGESTION) or the system-wide default. Its validate() refuses a table without ssthresh, undo_cwnd and one of cong_avoid or cong_control, because TCP has no fallback for those. Its update() swaps a registered algorithm for a new version under the same link.

sched_ext sits at the other end. It asks only for a name, because every callback has a default, and its reg() takes over every ordinary task at once. bpf_scx_update() refuses replacement in place, since enabling a scheduler runs its init() and init_task(), which may fail.

lists the tables in the 7.2.15 kernel's BTF. A BPF queueing discipline, fix-ups for one HID device and a step of an io_uring event loop all use the same map type, trampolines and link. This chapter does not teach them. Each file named in the table holds its bpf_struct_ops definition, whose callbacks say what the subsystem lets a program decide.

sched_ext: a scheduling class in eight programs

The table sched_ext asks schedulers to fill, struct sched_ext_ops, has 37 function pointers and eight data members in v7.2, and shows how little of it a working scheduler needs. The core callbacks follow a task through its life as runnable. select_cpu runs when the task wakes, and enqueue when it needs a place in a queue. dispatch runs when a CPU has nothing to run, running and stopping around each stretch on a CPU, and tick on every timer tick while the task runs.

Other callbacks report events the scheduler may track, such as a task joining or leaving the class (enable, disable), a change of weight or of allowed CPUs, a CPU going on- or offline, cgroup moves, and the start and end of the whole scheduler (init, exit). The kernel needs none of them. A missing select_cpu or enqueue gets the built-in behaviour, and the documentation notes that scx_simple's own versions of those two behave like the defaults.

A dispatch queue, or DSQ, is a queue of runnable tasks that sched_ext keeps on behalf of the BPF scheduler, ordered first in, first out or by a key the scheduler gives each task. Through these queues a BPF scheduler hands tasks to CPUs without touching the kernel's runqueues. Every CPU has a local DSQ, from which it always takes its next task, and the whole system has one global DSQ. A scheduler may create its own with IDs below 263, and scx_simple makes one, SHARED_DSQ, in its sleepable init.

The scheduler acts through kfuncs. scx_bpf_dsq_insert() puts a task at the tail of a queue with a time slice, the stretch it may run before it must give the CPU back, here the default of 20 ms. scx_bpf_dsq_insert_vtime() orders it by virtual time instead, a per-task clock that advances more slowly for tasks of greater weight, so that the task furthest behind runs next. scx_bpf_dsq_move_to_local() moves the first task of a queue to the calling CPU's local DSQ. v7.2 registers 69 kfuncs for sched_ext, 64 of them named scx_bpf_; in 6.13 the kfuncs whose names used the verb "dispatch" were renamed, as a comment in the tree's compat.bpf.h records, and that header still maps scx_bpf_consume() and the scx_bpf_dispatch_from_dsq() family to the new names for older kernels.

puts these pieces in the order a waking task meets them. simple_select_cpu calls scx_bpf_select_cpu_dfl(), the kernel's own search for an idle CPU. When it finds one, it inserts the task into that CPU's local DSQ at once, which tells the kernel to skip ops.enqueue(). Otherwise simple_enqueue puts the task in SHARED_DSQ, ordered by virtual time unless the loader was started with -f. When a CPU looks for its next task, the kernel takes the first one in its local DSQ, then tries the global DSQ, and only when both are empty calls ops.dispatch(), where simple_dispatch moves one task from SHARED_DSQ.

The kernel repeats that call while it keeps yielding tasks, at most 32 rounds in one pass. simple_running and simple_stopping keep the virtual-time clock, charging each task for the part of its slice it used, scaled by its weight.

A task enters the class when the scheduler is enabled. The reg() call runs the scheduler's init and calls init_task for every task in the system. It then moves each task whose policy is SCHED_NORMAL, SCHED_BATCH, SCHED_IDLE or SCHED_EXT into the ext class, unless the table's flags ask for SCX_OPS_SWITCH_PARTIAL, which moves only tasks that chose SCHED_EXT. During the switch the kernel schedules in bypass mode, ignoring the BPF scheduler and running tasks from simple queues of its own; the events file of the run in counted one bypass of 13.9 ms while scx_simple was being enabled. Real-time and deadline tasks never leave their classes, which sit above sched_ext.

Taking the CPU back

A scheduler decides whether other tasks run at all, so a wrong one can stop the machine. sched_ext was merged with a promise, in its documentation, that "the system integrity is maintained no matter what the BPF scheduler does". The verifier keeps part of it, since every program is checked like any other. bpf_scx_check_member() refuses a sleepable program in all members except init, exit, init_task, the two CPU hotplug callbacks, three cgroup callbacks and the two sub-scheduler callbacks, because the others are called where sleeping is not allowed, most of them under a runqueue lock. A program may write to a task only in p->scx.disallow, apart from two fields kept for old schedulers, and a scheduler that is safe in the verifier's sense can still make bad decisions; for those the kernel keeps three ways to end it and one way back.

The scheduler may give up by itself by calling scx_bpf_error(), which records a message and starts the exit. The kernel may end it, and the case it watches for is a task that is runnable and never runs; it also gives up the scheduler when a soft or hard lockup or an RCU stall is reported (ext.c lines 5186 to 5241). Each runnable task carries the time it became runnable. The watchdog, a work item that sched_ext queues every half timeout, walks every CPU's list of runnable tasks and ends the scheduler with "runnable task stall" when one has waited longer than the timeout. That timeout is the table's timeout_ms, or 30 seconds when the field is zero, and init_member() refuses anything longer.

A check in the scheduler tick ends the scheduler too if the watchdog itself has not run within the timeout. Finally, an administrator can press SysRq-S, or write S to /proc/sysrq-trigger. Every one of these, and the release of the link, ends in the same kernel work, scx_disable_workfn() and scx_root_disable(), which enters bypass mode, moves every task back to the fair class, calls the scheduler's exit with the reason, and logs it.

We broke scx_simple on purpose to watch the watchdog work. The change replaces the single line of simple_dispatch with a comment, so that tasks enter SHARED_DSQ and nothing takes them out again. shows what followed. For half a minute the VM went on working, because most wake-ups found an idle CPU and took the shortcut of . A task allowed on one CPU only never takes it, since the scheduler core calls a class's select_task_rq() only for a task that may move (core.c line 3618), so such a task always reaches ops.enqueue().

The first such task the watchdog found was a kernel worker bound to CPU 0, waiting in queue 0 while CPU 0 itself sat idle. After 30.336 seconds the watchdog ended the scheduler, and the kernel moved every task back to the fair class. The loader then printed the dump that sched_ext had collected at the moment of the exit.

Arenas in schedulers

A scheduler keeps state per task, per CPU and per group, and the maps of give it fixed tables with keyed lookups. The arenas of let it build the structures schedulers are usually made of, lists, trees and pools of per-task records linked by pointers, in memory that the loader can read as well. At the 2025 LSFMM+BPF summit, as LWN reported, Emil Tsalapatis said that his team had been happy with arenas in several scheduler experiments. He also named the limits they met. A kernel pointer cannot be stored in an arena, data headed for a kernel function has to be copied to the BPF stack first, and because the verifier types arena and stack pointers differently, a helper written for one cannot take the other, so such helpers are duplicated or inlined.

Alexei Starovoitov answered that work on these was in progress and that mixing the two kinds of pointer in the verifier was a hard problem. The v7.2 tree shows how far schedulers have gone since. scx_sdt, by Tsalapatis and Tejun Heo, is scx_simple with its per-task data allocated from an arena when a task enters the scheduler and freed when it leaves. The documentation describes scx_qmap as a five-level FIFO built on arena-backed doubly linked lists.

v7.2 also adds a second table, sched_ext_ops_cid, in which CPUs go by a sched_ext numbering built from the cache and node topology (kernel/sched/ext/cid.c) and CPU masks are a sched_ext type of their own. bpf_scx_reg_cid() refuses a scheduler of that kind unless all its programs share a single arena. The kernel then carves its own per-CPU scratch masks from that arena (kernel/sched/ext/arena.c), so that the scheduler reads them as ordinary arena memory, and scx_qmap is written to this table. The limit LWN reported is still visible here, since what the kernel places in the arena in v7.2 are CPU masks, never pointers to its own objects. The next chapter, the capstone, starts from this point: it builds one data structure on an arena and then builds it again as a new map type inside the kernel.

Inside v7.2: from the map update to a task on a CPU

lists the steps with their places in the source. Two details explain behaviour we see from outside. The enable work runs in a kernel thread that scx_enable() creates once and gives a real-time policy. The switch moves the calling thread itself into the ext class, which ranks below the fair class, and a comment in ext.c (line 6787) explains that a thread switched halfway could wait forever behind fair tasks not yet moved. The system call that created the link waits for that thread, so BPF_LINK_CREATE returns the scheduler's own errors, such as the -EBUSY of a second scheduler.

The class switch is a loop over every task in the system under the fork lock, each move made inside a sched_change guard that takes the task out of its old class and puts it into the new one. The disable path in scx_root_disable() runs the same loop in the other direction (ext.c line 6149).

On the wake-up path the line that matters most is 1913 in do_enqueue_task(). If ops.select_cpu() already inserted the task, the kernel finds a dispatch target recorded on the task and inserts it there without calling ops.enqueue(). A task with migration disabled, or one that is exiting, goes to its CPU's local DSQ without the scheduler being asked, unless the table's flags request otherwise, and the events file counts each such case. When ops.enqueue() does not insert the task anywhere, the kernel marks it as being in the BPF scheduler's custody, and from then on only the scheduler can bring it back to a CPU.

What a BPF scheduler costs

On the first two rows of scx_simple and the fair class are within each other's noise. messaging starts 400 processes that pass small messages through sockets and measures the total time. pipe passes one token back and forth between two processes, so each round trip is two wake-ups. A global queue and a search for an idle CPU are enough for both on an otherwise quiet machine with 16 CPUs.

The third row is the same pipe test with a busy loop on every vCPU, so that a waking task never finds an idle CPU. The fair class lets the waking task run soon after it wakes, and the vtime policy usually does the same, because a task that slept carries a virtual time behind the spinners'. In FIFO mode the waking task joins the tail of SHARED_DSQ behind spinners whose 20 ms slices run out one by one. Each round trip took about 1.9 ms, fifty times longer than under the fair class.

In , every switch to a task runs simple_running and simple_stopping. Most of the 112,083 calls to simple_dispatch found SHARED_DSQ empty, since simple_enqueue ran only 36,642 times, and the other wake-ups went straight to an idle CPU from simple_select_cpu. A pass through a task's life on the CPU thus costs a few hundred nanoseconds of BPF. Most of that is spent inside two kfuncs that do work the fair class does in C as well, which is why the first two rows of show no penalty. The statistics add two clock reads to each call, so these figures are slightly high.

What it costs

CPU
Per call of scx_simple's programs, 65 ns (running) to 625 ns (dispatch), kfuncs included; messaging 0.178 s against 0.190 s under the fair class and pipe 2.41 µs against 3.11 µs a round trip, medians of five within the run-to-run spread; with every vCPU busy, FIFO mode took 1.9 ms a round trip against 35 µs (kernel 7.2.15, VM with 16 vCPUs, 13 November 2026).
Memory
Eight programs of 4 KiB memlock each; the struct_ops map 6,288 bytes; five other maps 54,136 bytes, of which 36,864 are the exit dump buffer; one 4 KiB page of trampolines; the loader 4.5 MB resident.
Switches
None per scheduling decision: the callbacks run inside the kernel. The loader took 57 to 76 ms from exec to enabled and 38 to 47 ms from SIGINT to disabled (five runs), with one bypass of 13.9 ms while enabling; it then reads its statistics map once a second.
Locking
enqueue, dispatch, running and stopping run with a runqueue lock held and may not sleep; a custom DSQ is one raw spinlock, so scx_simple's single SHARED_DSQ is a lock every CPU takes.

A BPF scheduler pays for itself when a workload needs a policy the fair class cannot express, such as keeping a latency-critical service's threads on chosen CPUs or running a group's threads together, and the decision costs hundreds of nanoseconds that the policy wins back. For a general mix keep the fair class: scx_simple only matched it, its FIFO mode lost by a factor of fifty under load, and a scheduler is one more program whose failure the watchdog has to catch.

When it goes wrong

The rows of fall into three groups by when they happen. The verifier rows come first, at BPF_PROG_LOAD, and all three came from code that compiled. BPF_STRUCT_OPS() casts whatever argument list it is given onto the context array, so a wrong signature is caught only when the verifier types a read against the member's prototype in the kernel's BTF. The next two rows come at registration, from init_member() during the map update and from scx_root_enable_workfn() during the link's creation, and libbpf reports both as a failed attach with the kernel's error code.

The last group happens while the scheduler runs. Each ends in the same scx_root_disable() and the same return of every task to the fair class, and the reason in the loader's EXIT: line and in dmesg tells them apart. A scheduler that disappears without an error was unregistered, usually because its loader exited and took the link with it. The pinned TCP congestion control of step 7 in book/labs/schedext-root.sh shows the other side: bpftool struct_ops register with a directory pins the link, bpf_mini stayed in tcp_available_congestion_control after bpftool exited, and removing the pin unregistered it. bpftool alone would load scx_simple with its sched_ext constants left at zero, because the tree's loader writes their values into the object before loading it (SCX_ENUM_INIT(), called from SCX_OPS_OPEN() in tools/sched_ext/include/scx/compat.h).

Recap

A struct_ops map holds one kernel table of function pointers: the loader creates it from the table's BTF type, loads one program per filled member with the member's index as its attach type, and fills the map's value with program descriptors, whereupon the kernel checks each program against its member's prototype, writes a trampoline per member and points the member at it. The link created next calls the subsystem's reg(), and its release calls unreg(), so the table lives as long as the link. sched_ext is such a table with 37 callbacks, of which only the name is required; its programs place tasks in dispatch queues with kfuncs, a CPU runs what is in its local DSQ, and ops.dispatch() is asked only when that and the global queue are empty. scx_simple matched the fair class on two benchmarks at a few hundred nanoseconds per callback, its FIFO mode lost by a factor of fifty with every CPU busy, and a scheduler that strands a task is ended by the watchdog after 30 seconds, with every task returned to the fair class.

local DSQ

time slice
how long a task may run before it must give the CPU back

a per-task clock that runs slower for heavier tasks; the task furthest behind runs next

It is tempting to expect 37 trampolines, one per member, but an empty member stays NULL, and /proc/kallsyms listed eight.

A scalar where the program expected a pointer. The verifier types each argument from the member's prototype, and the first parameter of dispatch is s32 cpu, so btf_ctx_access() made the value loaded from offset 0 of the context a scalar; the log shows R1=scalar(), and the load at prev->pid, offset 2872, fails. The code compiled because BPF_STRUCT_OPS() casts each 64-bit slot of the context to whatever type the source declares. The verifier never compares the declared signature with the prototype as a whole; it only types each read, which is why the fix is to copy the parameter order from bpftool btf dump file /sys/kernel/btf/vmlinux format c.

BPF_LINK_CREATE failed with -EBUSY. The link's reg() reached scx_root_enable_workfn(), which refuses when the enable state is not DISABLED (ext.c lines 7127 and 7128), and libbpf's bpf_map__attach_struct_ops() reported the error as a failed attach. Before that the second copy had loaded its eight programs and filled its own struct_ops map, which sat in the state READY until the loader exited and closed its descriptors; nothing of it was registered, and the first scheduler stayed enabled under the name simple. In v7.2 a second scheduler can only join as a sub-scheduler of a cgroup, which needs the cid-form table and CONFIG_EXT_SUB_SCHED.

About 2 ms; the runs took 1.76 to 2.28 ms. A round trip is two wake-ups, and in FIFO mode a woken task joins the tail of SHARED_DSQ and runs only when some CPU's spinner has used up its slice and that CPU calls ops.dispatch(). Sixteen slices of 20 ms that end at scattered times end, on average, one every 20 / 16 = 1.25 ms, so each wake-up waits up to that long and a round trip costs roughly 1.25 to 2.5 ms. A common mistake is to expect 20 ms a wake-up, which forgets that any of the 16 CPUs may pick the task up. Under the fair class the same test took 35 µs, because a woken task does not wait for a slice to end.

The process exit closed the struct_ops link. The loader held the link's only descriptor, so its release ran bpf_struct_ops_map_link_dealloc(), which calls the subsystem's unreg() (bpf_struct_ops.c lines 1254 and 1263), and sched_ext's unreg() disables the scheduler with the same reason as a clean exit; the run measured 3 ms from the signal to disabled. sched_ext never watches the process. To keep a table registered without its loader, pin the link in bpffs, as bpftool struct_ops register does when given a directory: bpf_mini stayed available after bpftool exited and went when the pin was removed. A map made without BPF_F_LINK instead stays registered until its entry is deleted.

Each subsystem decides what it needs in its own validate() and reg(). TCP has no fallback for ssthresh, undo_cwnd, and one of cong_avoid or cong_control, so tcp_validate_congestion_control() logs that message and returns -EINVAL (net/ipv4/tcp_cong.c lines 78 to 85), which the map update passes on. sched_ext has a built-in behaviour for every callback, its bpf_scx_validate() returns 0, and the only data it checks is in bpf_scx_init_member(), which refuses an empty name with -EINVAL (ext.c lines 7959 to 7966), the Invalid argument of our run with .name = "". The struct_ops mechanism itself requires no member at all.

In the kfunc. run_time_ns counts everything between the program's entry and its exit, and scx_bpf_dsq_move_to_local() first flushes the scheduler's pending insertions and then looks at SHARED_DSQ. When the queue is empty it returns after a check without a lock (consume_dispatch_q(), ext.c line 2525); when a task waits it takes the queue's raw spinlock, and a task queued on another CPU's runqueue has to be migrated (line 2552). simple_enqueue ran 36,642 times against 112,083 dispatches, so most dispatches were cheap and the average hides dearer moves. simple_running only compares and stores one number. It would be wrong to blame the BPF code itself, which is one call instruction.

Thirty seconds is SCX_WATCHDOG_MAX_TIMEOUT (kernel/sched/ext/types.h line 20), used when the table's timeout_ms is 0 (ext.c lines 6886 to 6889). The watchdog runs every half timeout and walks each online CPU's runnable list in order, stopping at the first task over the limit (lines 3475 to 3488). kworker/0:1 may run only on CPU 0, so the core never calls ops.select_cpu() for it (core.c line 3618), every wake-up sends it through ops.enqueue() into SHARED_DSQ, and CPU 0 comes first in the walk, before the busy loop pinned to CPU 5. A shorter wait comes from setting .timeout_ms in the table; above 30,000 ms, init_member() refuses it with -E2BIG.

As above, with the timestamps cut, from kernel 7.2.15 in a virtme-ng VM with 16 vCPUs on 13 November 2026: medians of 3.11 µs under the fair class and 2.41 µs under scx_simple, within each other's spread, and an exit 30.4 seconds after the broken scheduler was enabled. Your round trips depend on the host; the 30 seconds do not, since they are the default timeout.

What this shows. A BPF scheduler costs nothing measurable on a quiet machine, and a broken one is contained: the watchdog found a task that had been runnable for longer than the timeout, the kernel moved every task back to the fair class, and the dump named the task, its CPU and the queue it waited in.

Common wrong turn. Compiling the loader with the build's own include directory ahead of the variant's: scx_simple.c then picks up the original scx_simple.bpf.skel.h, the broken scheduler runs as well as the real one, and no watchdog ever fires. Our first runs for this chapter made this mistake; -iquote with the variant's directory, or strings on the binary, settles which object a loader embeds.

bypass mode
sched_ext scheduling without the BPF scheduler, while one is enabled, disabled or failing
dispatch queue
a queue of runnable tasks that sched_ext keeps for a BPF scheduler, FIFO or ordered by a key
local DSQ
the dispatch queue of one CPU, from which that CPU always takes its next task
scheduling class
the set of functions through which the scheduler core asks one policy what to run
struct_ops map
a one-entry map whose value is a kernel table of function pointers, filled with programs
time slice
how long a task may run before it must give the CPU back
virtual time
a per-task clock that runs slower for heavier tasks; the task furthest behind runs next
watchdog
sched_ext's periodic check that ends a BPF scheduler when a runnable task has not run in time
