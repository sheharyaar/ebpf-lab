Hooks, and what attaching writes into the kernel

The write counter's SEC() line names one of thousands of places where the kernel can call a program, and attaching it there changes the kernel itself, from a flag on every thread to a call written over a no-op. An empty program adds 57 ns to a write() at fentry and 127 ns at the write tracepoint, and none of the difference is in the program.

Attaching the counter to its tracepoint

Attach connects a loaded program to its hook so that it runs, and for the counter it comes down to a perf_event_open() and a BPF_LINK_CREATE, which shows under strace beside libbpf's own probe of the kernel. hashmap_bpf__attach() reads the tracepoint's number, 827 in this VM, from /sys/kernel/tracing/events/syscalls/sys_enter_write/id, opens a perf event on it with perf_event_open(), and joins program and event with BPF_LINK_CREATE, attach type BPF_PERF_EVENT. The result is the link that counted among the program's holders, and bpftool link show lists it as a perf_event link on the tracepoint sys_enter_write.

Before linksOn kernels without links for perf events, the program was handed to the event with an ioctl, PERF_EVENT_IOC_SET_BPF, and nothing in the kernel held the attachment as an object. libbpf still falls back to it there (libbpf.c line 11569).

Each attachment is a struct bpf_link, 80 bytes with a reference count, an ID, a type, a table of operations and the program, wrapped in a larger structure with what its hook needs. When the last reference goes, bpf_link_free() calls the table's release, which detaches the program, so the holders counted in also decide when a program stops running. Neither the perf event nor the link shows what attaching changed inside the kernel, which for this tracepoint is a flag on every thread ().

From a section name to a hook

Before the loader can attach anything it must know what kind of program it holds and where the program goes, and both come from one string. In the compiler, SEC("tracepoint/syscalls/sys_enter_write") only names the ELF section, a named block of the object file, that the function's bytecode goes into, and llvm-readelf -S on the counter's object lists a section under that name, 216 bytes long, beside .maps, .rodata and license.

libbpf matches the name against its own table, section_defs in tools/lib/bpf/libbpf.c (116 entries in v7.2), as shows for three of the book's programs. The part before the first slash selects the program type, the kind of program, which fixes what it receives when it runs and which helpers it may call. The part after the slash names the hook. For the write counter that is the tracepoint at the entry to write, while the second program hangs on a kprobe, a hook the kernel inserts at run time on almost any kernel function, found by name, here do_sys_openat2.

Some program types also need an attach type, the variant of a hook the program is for. The fork tracer runs at a tracepoint too, yet its tp_btf prefix brings a different program type, TRACING, with attach type BPF_TRACE_RAW_TP fixed at load. The write counter gets its attach type only when it is attached. A prefix that matches no entry leaves the type unset, and libbpf stops before the kernel sees the program, whereas a misspelling after the slash, such as sys_enter_wrte, still loads and fails only at attach, when libbpf looks the tracepoint up in tracefs.

One write, five stops

A write() passes several places where a program can run, and puts both kinds of hook just met on one call. The tracepoint sys_enter_write fires as the system call enters the kernel, so the counter runs before the kernel has even found the file, and a kprobe on vfs_write() fires a little later, as that function starts. Further in, security_file_permission() asks the security modules whether this write may go ahead, and on the way back out two more hooks see how the call ended.

At each stop r1 points at something different. It holds the program's context, the data the hook hands over in a shape that the program type fixes. For the counter that is the tracepoint's record, whose fields /sys/kernel/tracing/events/syscalls/sys_enter_write/format lists: the system call number, then fd, buf and count.

A fixed hook or any function

The two quotes at the head of this chapter describe the two kinds of hook in the counter's world. The write counter runs at a tracepoint, a call that kernel developers wrote into the source, and the openat tracer in book/program hangs on a kprobe, which the kernel places at attach time on a function the loader names. sets the tracepoint, the only one of the three placed on purpose, beside the two ways to attach to any function. Kernel 7.2.15 has 2,079 tracepoints, whereas a kprobe can go on almost any instruction outside the 751 entries of the kprobe blacklist, code where a breakpoint would trap again.

An fentry program attaches to the entry of a kernel function through a trampoline, the stub of machine code that saw the kernel write. The compiler leaves a five-byte no-op near the start of each function for ftrace, the kernel's function tracer, and attaching rewrites it into a call, so there is no breakpoint to take. Its twin, fexit, runs as the function returns and also sees the return value. A kprobe at a function's entry borrows the same slot, and only a kprobe placed further into the function is a breakpoint, as the next section measures.

A kprobe's context is the saved CPU registers, from which the BPF_KPROBE macro in kprobe.bpf.c reads the arguments back out, whereas an fentry program gets the arguments themselves, typed by BTF.

The fork tracer in book/program sits between the columns. It runs at a raw tracepoint, added in Linux 4.17, which is the same named point with the record left unbuilt, so that the program receives the tracepoint's own arguments. Its section, tp_btf/sched_process_fork, asks for the BTF-typed kind, whose BPF_PROG macro names the two task_struct pointers that the tracepoint passes, and CO-RE fixes the offset of pid inside them.

The bottom row of is what reaching any function costs. Nobody keeps a function's name stable for the programs that attach to it, and the next release may rename the function, split it, or let the compiler inline it into its callers. A kprobe on a missing name fails to attach, but on a function that some callers now inline it misses those calls and says nothing.

What attaching writes into the kernel

The three kinds of hook differ most in the code that runs before the program. Timed per one-byte write() on kernel 7.2.15, an empty program added 57 ns at fentry, 114 ns at a kprobe on vfs_write() and 127 ns at the tracepoint, to a call that takes 320 ns alone, while run_time_ns, which starts at the program's first instruction, gave the program itself 33 to 40 ns at every hook over two sessions. draws the difference from kernel stacks recorded under the counter's map update.

A static key is a branch that the kernel compiles as a no-op and rewrites into a jump when a feature is switched on. A static call is a direct call whose target the kernel rewrites in place. Attaching the counter switched both on for the tracepoint sys_enter, and its registration hook, syscall_regfunc() in kernel/tracepoint.c, set a work flag on every thread. From then on every system call takes the slower entry path into trace_syscall_enter().

There the static call reaches perf_syscall_enter(), which finds the bit for write set in a bitmap of enabled calls. Then perf_call_bpf_enter() builds the record on its own stack, and trace_call_bpf_faultable() passes the record's address to each program attached to the event. On x86 a function's first argument travels in rdi, and the JIT keeps r1 in rdi (reg2hex in arch/x86/net/bpf_jit_comp.c), so the address arrives in r1 without a copy.

The first eight bytesThe format file calls them common_type, common_flags, common_preempt_count and common_pid. For a program, perf_call_bpf_enter() stores there a pointer to registers saved by perf_fetch_caller_regs(), under the comment "bpf prog requires 'regs' to be the first member in the ctx".

The kprobe and the fentry program both start from ftrace's slot, five bytes near the top of each traceable function that ftrace turned into a no-op at boot. A kprobe asked for at vfs_write lands on it, at vfs_write+0x4. The kernel was built with CONFIG_KPROBES_ON_FTRACE, which lets kprobes use ftrace, so check_ftrace_location() in kernel/kprobes.c makes it an ftrace probe, which /sys/kernel/debug/kprobes/list marks [FTRACE]. The slot then calls a trampoline that ftrace made for kprobes (), which saves every register as the struct pt_regs that r1 will point at.

Away from the slot there is nothing to borrow. A kprobe at vfs_write+0x9 writes cc, the x86 breakpoint int3, over the first byte of a sub, and each write takes two traps, one at the probe and one after a copy of the sub has run elsewhere. That cost 387 ns per write. Five jiffies and a grace period after the attach, a kernel thread replaced the breakpoint with a jump to a detour buffer that saves the registers and calls the same handler. With this optimised kprobe the cost fell to 89 ns.

Patching live codeEach change in goes through smp_text_poke_batch_finish() in arch/x86/kernel/alternative.c: an int3 on the first byte, a cross-call to every CPU, the other bytes, another cross-call, the new first byte and a third. A CPU that meets the int3 in between is steered around it.

For fentry the JIT writes a trampoline of its own, the 132 bytes at the bottom of , and the slot calls it directly. It stores the four argument registers, asks __bpf_prog_enter_recur() whether the program may run, points rdi at the stored arguments and calls the program. Saving no full register set, taking no trap and looking nothing up by address, it is the cheapest of the three. For fexit the slot becomes a jump, and the trampoline calls the rest of vfs_write() itself.

Timed per byte of dd instead, which makes one read() and one write() a byte, the same empty programs cost 180 ns at the tracepoint, 120 ns at the kprobe and 65 ns at fentry, over 695 ns with none (VM, medians of ten, book/labs/costs2-root.sh). The tracepoint's share grew most because the read() takes the slow entry path too, which every system call does while the work flag is set. In the session of the costs box below, getppid() took 320 ns with nothing attached, 354 ns with the counter at its tracepoint, and 320 again after the detach.

adds the price of attaching and detaching. A function_graph trace put 0.3 ms of a 3.7 ms fentry attach in building the trampoline and in three rounds of patching; the rest ran in ftrace's own code, which the tracer cannot see. Detaching a tracepoint or kprobe program took 29 to 46 ms, because the detach waits until no task can still be inside the program, in synchronize_rcu_tasks_trace() called from perf_event_detach_bpf_prog().

Inside ftraceftrace finds the call sites to change by walking the records of every patchable function, twice, in ftrace_replace_code() (arch/x86/kernel/ftrace.c). available_filter_functions listed 59,017 of them in the VM of .

Where the program finds itself

A program runs in the context of the event that fired it, with whatever the glue adds (). An NMI, a non-maskable interrupt, can arrive while the CPU holds any lock, even with interrupts disabled, so code in one must never wait. perf_event programs on hardware counters run in one, and on x86 so does a kprobe that fires as a breakpoint, since exc_int3() enters through irqentry_nmi_enter(). A softirq is interrupt work that the kernel completes after the hardware interrupt has returned, and XDP runs in one.

In process context the CPU works on behalf of a task, here the writer that called write(). The kprobe glue disables preemption, but the system-call tracepoint's glue and the trampoline only stop migration and take an RCU read lock, which on this kernel's preemptible RCU lets the scheduler switch tasks in mid-program. There each program keeps a recursion counter for each CPU, so while one task sits switched out inside the counter, every write another task makes on that CPU is skipped and added to recursion_misses. With two writers pinned to one CPU the write counter lost 45 to 55 per cent of its events; with the writers on two CPUs it lost none.

Sleepable programs may fault and wait. can_be_sleepable() in verifier.c decides which programs may be loaded that way: fentry and fexit programs, fmod_ret programs, which may change a function's return value, iterators, LSM programs other than cgroup ones, uprobes, struct_ops, and tracepoint, raw tracepoint and BTF tracepoint programs. The last three may attach only where the tracepoint is allowed to fault, which in v7.2 means a system-call tracepoint. Which maps they may use is decided by check_map_prog_compatibility(), and chooses maps against .

What a program may change

gives, for seven program types, what r1 points at and what the return value does. The top three can only watch, since whatever they return, the write goes on.

An LSM program attaches to a hook of the Linux Security Modules, such as file_permission in , and refuses the operation by returning a negative error. Linux 5.7 added them, and on kernel 7.2.15 /sys/kernel/security/lsm lists bpf.

Two hooks sit on the packet path. XDP, the eXpress Data Path, runs in the network driver as each packet arrives, before the kernel builds its own structure for the packet. Its return value drops the packet, passes it on, sends it back out, or redirects it. tc programs run later, in the traffic-control layer, where that structure exists.

Programs can also call further into the kernel through a kfunc, a kernel function offered to programs by its BTF type instead of a helper ID, whose documentation warns that kfuncs "do not have a stable interface". A struct_ops program set fills a table of function pointers that a subsystem calls, which lets the program make the subsystem's decision. TCP congestion control came first, in 5.6, and sched_ext, a scheduler class whose policy is such a set, arrived in 6.12.

How a new hook gets into the kernel

Often no new hook is needed, because fentry and kprobes reach tens of thousands of functions. A new tracepoint is a patch to the subsystem that owns the code, a TRACE_EVENT() definition and one call to it, reviewed by that subsystem's maintainers.

A hook where a program decides is bigger, as cache_ext shows (). Its authors wanted page-cache eviction written as BPF programs, so they added a struct_ops table of five function pointers, calls to it at five page-cache events, and kfuncs for the lists a policy keeps. Teaching the verifier about both took only 80 lines, because struct_ops and kfuncs carry most of the work.

cache_ext was published at SOSP 2025, and its code is a modified Linux 6.6.8 kept in the authors' repository. The whole change came to about 2,000 lines, and to reach mainline it would take the road of , with patches on the mailing lists, tests, and review by the maintainers of both subsystems. Once a program runs at its hook, every helper and kfunc it calls has been checked against what that hook allows, and follows those calls from the bytecode into the kernel, with how a kfunc is registered.

What it costs

CPU
Per one-byte write(), an empty program cost 57 ns at fentry, 80 at a raw tracepoint or fexit, 89 at an optimised kprobe, 114 at a kprobe on the slot, 127 at the tracepoint and 387 at a breakpoint kprobe, of which 33 to 36 ns ran in the program. The counter itself takes 144 to 162 ns a run without bpf_printk and 0.48 to 0.54 µs with it, and adds 230 to 245 ns to each write() without it and 580 to 620 ns with it (run_time_ns over run_cnt, alike under dd and a write() loop; kernel 7.2.15, VM, 12 November 2026, book/labs/hooks-root.sh).
Memory
A link is an 80-byte struct bpf_link inside its hook's wrapper. An fentry trampoline is 132 bytes of code in a 196-byte request, carved in 64-byte chunks from a shared 2 MB pack, plus about 1.1 KB of bpf_tramp_image, bpf_trampoline and bpf_tracing_link (BTF sizes).
Switches
A perf_event_open() and a BPF_LINK_CREATE to attach the counter and none per event, but a system-call tracepoint in use slows every system call, getppid() from 320 to 354 ns (syscall_regfunc()). Attaching took 0.3 ms (raw tracepoint) to 3.7 ms (fentry); detaching a tracepoint or kprobe program sleeps 29–46 ms in a grace-period wait.
Locking
No lock per event, only recursion counters. System-call tracepoints (trace_call_bpf_faultable()), raw tracepoints and trampolines keep one per program and CPU; kprobes and the other tracepoints share one per CPU, bpf_prog_active in trace_call_bpf(), so a kprobe program that fires while another of them runs on its CPU is skipped as a miss. Each patch of kernel text cross-calls every CPU three times under text_mutex.

Prefer fentry where BTF has the function, a raw tracepoint where one exists, and a tracepoint where the program must outlive upgrades; keep kprobes where the optimiser can replace them, and count a system-call tracepoint against every system call. On a busy preemptible kernel, watch recursion_misses, and if it grows, attach where preemption is off.

When it goes wrong

Most failures at a hook are quiet, because a program that attached to the wrong place, or to a place the event no longer passes, loads and attaches without an error. pairs each symptom this chapter met with its usual cause and the command that tells it apart. The first three rows belong to the section name: a prefix libbpf does not know stops the load before the kernel sees the program, a misspelt hook after the slash loads and fails at attach, and a bare prefix loads and is never attached. Two failures that the counter's tracepoint can cause while loading, tracefs refusing an ordinary user and a program loaded but never attached, stand with the other failures of a load in .

The middle rows are about where a hook sits. A kprobe follows a function's name and address while the work may move elsewhere, and a tracepoint fires before the checks that may fail a write, so a count that is too low, too high or zero sends us to available_filter_functions and to the order in before the program. The last rows are costs and losses: a breakpoint kprobe that the optimiser could not replace, a system-call tracepoint that slows every system call, a detach that waits for a grace period, and recursion misses on a preemptible kernel, which bpftool prints only when there are some.

Recap

The SEC() string is an ELF section name whose prefix picks the program type, and sometimes an attach type, while the rest names the hook, and attaching the counter opens a perf event on its tracepoint and joins the program to it with a link. The program type fixes the context r1 points at and what the return value does; tracepoints, placed in the source on purpose, change rarely, while kprobes and fentry programs reach any function by name and break when it changes. The write tracepoint reaches the counter through a work flag on every thread, a static key, a static call and a record built on the stack; a kprobe at a function's entry rides ftrace's slot into a register-saving trampoline and elsewhere is an int3 until the optimiser replaces it, and an fentry program is called from the slot through a trampoline the JIT wrote, the cheapest path of the three. Where the glue leaves a program preemptible, a task switched out inside it turns the other runs on that CPU into lost events. Tracing programs watch, LSM programs can refuse, XDP and tc programs decide a packet's fate, and struct_ops program sets make a subsystem's decisions, and a new hook of that last kind is a struct_ops table, call sites, kfuncs and verifier rules, sent upstream like any other patch.

A missing tracepoint would fail differently: a wrong name after the slash loads fine and fails later, at attach.

10, 10 and 0. The tracepoint fires as each call enters the kernel, before anything is checked, so the counter runs ten times. ksys_write() finds the file and calls vfs_write(), which fails its first test, FMODE_WRITE, and returns -EBADF, so the fentry on vfs_write() runs ten times. The permission check comes after that test, in rw_verify_area(), so it never runs. Run with bpftrace on kernel 7.2.15 in a virtme-ng VM: @tracepoint_sys_enter_write: 10, @fentry_vfs_write: 10, @fexit_vfs_write_returned[-9]: 10, and no line for the permission check. Expecting 0 from the counter because the writes failed gets the order wrong, since the tracepoint runs before the kernel knows they will fail.

The function still exists, so the kprobe attached, but the path that opens files no longer calls it as a separate function. The compiler may have inlined it into its callers in the new build, or the code may have been reorganised so that open goes another way. A kprobe binds to one address in one function and does not follow inlined copies; the kprobes documentation says so. Check with sudo grep -w do_sys_openat2 /sys/kernel/tracing/available_filter_functions and read the new kernel's fs/open.c. The tracepoint syscalls:sys_enter_openat is kept on purpose. Blaming the load or the verifier gets nowhere, since both succeeded and nothing reported an error.

At 0x60 for the kprobe program and at 0x10 for the fentry program. The kprobe's r1 points at the struct pt_regs that the ftrace trampoline saved; count is the third argument, which x86-64 passes in rdx, and dx is the thirteenth eight-byte field of pt_regs, after r15 to r8, ax and cx, so 12 × 8 = 96. The fentry program's r1 points at the arguments the trampoline stored from rbp − 0x20, eight bytes each, so the third is at 2 × 8 = 16. llvm-objdump -d of the two programs shows r1 = *(u64 *)(r1 + 0x60) and r1 = *(u64 *)(r1 + 0x10). Answering 16 for both is tempting, since the two macros take the same argument list, but BPF_KPROBE hides a PT_REGS_PARM3() read.

Offset 0xc is inside an instruction. vfs_write+0x9 starts the seven-byte sub $0x88,%rsp, which runs to 0xf, so 0xc is its fourth byte, and an int3 there would change the instruction's immediate instead of stopping the CPU. Before arming, arch_prepare_kprobe() calls can_probe() in arch/x86/kernel/kprobes/core.c, which decodes the function from its start and returns false for an address that is not an instruction boundary, and the kprobe is refused with -EILSEQ, "illegal byte sequence". objdump -d on the kernel's vmlinux shows where the instructions start. It is easy to read EILSEQ as a problem with the encoding of the probe's name, but libbpf parsed the name correctly; the error is about the bytes at that address.

On the slow machine the probe is still a breakpoint. Each write traps at vfs_write+0x9, where kprobe_int3_handler() runs the program, and traps again after a copy of the sub has run out of line, because on a preemptible kernel prepare_singlestep() ends the copy with a second int3. The trap enters through irqentry_nmi_enter(), so the program runs as if in an NMI, with in_nmi() true, which limits what it may safely do with locks and buffers. On the fast machine the optimiser replaced the int3 with a jump (e9 in the bytes); the slow one has debug.kprobes-optimization set to 0, or an instruction there that cannot be moved. Suspecting the program or the JIT is a common mistake, as both machines run the same code.

An LSM program, on a hook such as file_permission or file_open, that returns -EPERM when the file matches and 0 otherwise. LSM hooks sit at the points where the kernel asks whether an operation is allowed, and the verifier accepts negative error codes from them. Tracing programs cannot do it, because a tracepoint or kprobe program's return value only decides whether the trace record is kept, and fentry programs must return 0. Check /sys/kernel/security/lsm for bpf, and read the example in the kernel's LSM BPF page. A kprobe program that returns 1 may look like a refusal, yet the write goes on regardless.

The plus means both forms are accepted: the bare word, or the word, a slash and extras that say how to attach automatically. A program in plain SEC("kprobe") still gets program type KPROBE and loads, but it names no function, so the skeleton's attach() skips it and the loader must attach it by hand, for example with bpf_program__attach_kprobe(). The rules are the two bullets at the top of the page, and libbpf's attach_kprobe() has the comment "no auto-attach for SEC("kprobe")". Anyone expecting a load error will be surprised, because the bare form is legal and only fails to attach itself.

BPF_PROG_TYPE_TRACEPOINT, reached by two section names, tp+ and tracepoint+, with the attach type column empty, so SEC("tp/syscalls/sys_enter_write") would give the same program. The attach type the write counter ends up with, BPF_PERF_EVENT, appears only at attach, in BPF_LINK_CREATE, which is why this table does not list it. The empty cell can look like "cannot be attached"; what it means is that nothing has to be chosen at load.

Because they receive different things. tp_btf+ gives BPF_PROG_TYPE_TRACING with attach type BPF_TRACE_RAW_TP, and the program gets the tracepoint's raw arguments, here two task_struct pointers, typed by the kernel's own type information. tracepoint+ gives BPF_PROG_TYPE_TRACEPOINT, and the program gets the tracepoint's formatted record, which is why the write counter's argument is a struct trace_event_raw_sys_enter. The table puts the two prefixes in different rows, and the footnote for tp_btf+ gives its format. Since tp is another spelling of tracepoint, tp_btf looks like a third, and the separate rows show otherwise.

What this shows. Every miss is a write the counter never saw. At the tracepoint and through the trampoline, a writer switched out inside the program leaves the program's counter for that CPU at one, and the other writer's runs on that CPU are skipped until it resumes. The kprobe runs with preemption off, so no task can be switched out inside it.

Common wrong turn. Leaving the writers unpinned: the scheduler puts them on different CPUs and the misses vanish. And bpftool prog show prints recursion_misses only when it is not zero, so a missing field means none.
