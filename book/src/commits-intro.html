Most rows of began as a patch posted to a mailing list, were reviewed there, and were applied as a commit that is still in the kernel's history. This appendix gives both for each row, in date order, so that the lineage can be read as code. The first code beside an entry opens the commit on git.kernel.org, with its message, the files it touched and the diff. The second opens the patch on lore.kernel.org, the archive of the kernel's mailing lists, where the review and the other patches of its series sit in the same thread.

Three habits make a commit quick to read. The message comes first, because in this subsystem it often explains the design and the alternatives at more length than any document does. The list of changed files comes next, since a new file under kernel/bpf/ means a new mechanism and a large change to verifier.c means a new rule that loaded programs must follow. Sizes are worth comparing as well. Attaching to tracepoints in 4.7 took 19 added lines because the kprobe commit of 4.1 had already built the plumbing, while the scheduler class of 6.12 arrived as a new file of 4,256 lines.

The first two entries are older than git and link to the paper and to the release patch instead. Entries marked with an asterisk are not in ; later chapters cite them. Line counts are for the single commit shown, and a feature usually needs the rest of its series as well.
