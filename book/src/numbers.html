How the verifier tracks numbers

The verifier never runs the write counter, yet it knows that a number in it is below 8, because it keeps two descriptions of every number and lets each test narrow them. It also remembers which numbers a check has relied on, and in one program of sixteen tests that memory decided between a walk of 174 instructions and one of 163,929.

What the log says about a number

We load the counter as did, with the small libbpf loader that sets the log level itself, at level 6: every state and the statistics. keeps the lines that hold numbers. After the semicolon the log lists what each instruction changed, one entry per register or stack slot, and each entry is what the verifier knows about that register at that point on that path.

Three kinds of number appear in part (a). A constant prints as its value, as R1=1 does at slot 2, because every bit of it is known. A pointer prints as its kind with what is known of its offset, so R2=fp-4 at slot 5 is the frame pointer minus four, the address of the key. Any other number prints as scalar(…) with the bounds the verifier has worked out. At slot 12 the key read back from the stack lies between 0 and 0xffffffff, since four bytes hold no more, while the bare scalar() that r0 receives at slot 0 is a number about which nothing is known.

Part (b) comes from a copy of the counter that we follow through the rest of the chapter. Suppose the write counter kept eight counters per thread, one for each of the file descriptors 0 to 7, and picked one with the descriptor that write() was called with, as in if (s && fd < 8) s->n[fd]++;. When the kernel loads this per-descriptor copy, the descriptor could be any number at all, as slot 3 says. After the test at slot 10 it has the busiest entry in either log, which takes apart.

The fields are bounds, each the smallest or the largest value the register can hold, read in one of four ways: signed or unsigned, over all 64 bits or only the low 32. print_scalar_ranges() leaves out every bound that says nothing, such as an unsigned minimum of 0. It writes equal minimums once and equal maximums once, joined by equals signs, so eight bounds print as two groups. The last field is of another kind, which the next section explains.

Two descriptions of every number

For each register on each path the verifier keeps an abstract value, a description of every value the register could hold at that point. A scalar's abstract value has two parts, and the log prints both. The range holds the smallest and the largest value possible, which the log calls smin and smax when it reads the bits as signed and umin and umax when it reads them as unsigned. The tnum, short for tristate number, describes each bit as 0, 1 or unknown (written x). It uses two 64-bit words, value and mask, declared in include/linux/tnum.h, and the log prints it as var_off=(value; mask).

shows why neither part is enough alone. After fd < 8 both say 0 to 7. After fd <= 8 the range says 0 to 8 while the tnum can only say that the low four bits are unknown, since no pattern of known and unknown bits stops at 8. After every step, therefore, the verifier corrects each part from the other, in reg_bounds_sync() in kernel/bpf/verifier.c.

In v7.2 that function, at line 2073, makes four moves. It narrows the bounds to what the tnum allows, and lets the 64-bit and 32-bit bounds narrow each other twice. It then intersects the tnum with the unsigned range, so that bits the range rules out become known, and narrows the bounds once more from the new tnum. In the copy, this is what turns the test's bound of 7 into the tnum (0x0; 0x7).

Version 7.2 draws the range on a circle

Up to Linux 7.1 a register carried four ranges, signed and unsigned for all 64 bits and for the low 32, which made eight numbers kept in step by hand. In April 2026 Eduard Zingerman replaced them with two arcs, r64 and r32 in struct bpf_reg_state. Each is a circular range (struct cnum64 in include/linux/cnum.h), a first value and a count read clockwise round a circle on which the largest number is followed by 0. The count leaves out the first value, so that all 264 values still fit (the header's comment, lines 20 to 23).

As shows, one arc answers the signed and the unsigned question together. The arc from 14 to 2 is the signed range −2 to 2, but read as unsigned it wraps past 15, so the unsigned minimum and maximum of those five values span the whole circle, 0 to 15. The log has not changed: accessors such as reg_umin() in include/linux/bpf_verifier.h work each bound out from the arcs when it is read. The commit says that the operations on arcs were checked with the CBMC model checker.

Arithmetic moves both descriptions

Every arithmetic instruction on a scalar reaches adjust_scalar_min_max_vals() (verifier.c line 14591), which rewrites both descriptions of the destination register. For each operator it calls a helper for the two arcs and a function from tnum.c for the tnum, as lists. It ends with reg_bounds_sync(), so that each description can correct the other.

Slot 11 of the copy, a left shift by three, can be followed through both halves. tnum_lshift() moves the value and the mask three places, turning (0x0; 0x7) into (0x0; 0x38). __scalar64_min_max_lsh() shifts the unsigned bounds, so 0 to 7 becomes 0 to 56; had the maximum been able to lose its top bit, it would have allowed every value instead.

Two rules keep the operators simple. A shift, a division or a remainder gets a range only when its second operand is a constant, and a shift only by less than the register's width. Anything else gives an unknown scalar (is_safe_to_compute_dst_reg_range(), line 14508). A 32-bit operation clears the upper half of its destination, as the machine does, and zext_32_to_64() tells both descriptions.

Sound first, then precise

Each helper in may give an abstract value that is too wide, but it must never miss a value the program can really produce. In we add 1 to a register whose tnum is 00x1, which holds 1 or 3, so the real results are 2 and 4. The kernel's tnum_add() answers 0xx0, which allows 0, 2, 4 and 6.

That answer is sound, because every real result lies inside it. It is not precise, because 0 and 6 can never happen, and precision measures how few such extras a description carries. An imprecise verifier refuses some safe programs, which costs their authors an afternoon, whereas an unsound one accepts a program that reads outside its map value, which is a security bug. Running a program on descriptions of its values in this way is called abstract interpretation. writes these definitions as logic and shows how an operator is proved sound; this chapter stays with what the kernel does.

A test narrows both sides of a branch

We follow the copy through the walk in . At slot 3, r6 receives the descriptor as scalar(), a number with no bounds at all. At slot 10, if r6 > 0x7, the walk splits into two paths as it did in , and the side that jumps, where r6 is at least 8, goes straight to the exit. On the side that falls through, r6 is at most 7; the shift at slot 11 makes that an offset of 0 to 56, which slot 12 adds to r0, the pointer into the map value.

In v7.2 one call does the work for both sides. check_cond_jmp_op() (line 15945) copies the two compared registers once for each side and asks is_branch_taken() whether the bounds already decide the test. For two scalars it compares the bounds and then tries the test on the copies. simulate_both_branches_taken() (line 15192) narrows the fall-through copies with the reversed comparison, r6 <= 7 for if r6 > 7, and the jump copies with the comparison itself, each through regs_refine_cond_op() (line 15517) and a sync. An arc that comes out empty is a side that cannot happen; otherwise push_stack() saves the jump side with its narrowed copies (lines 16088 to 16101).

Older kernelsIn v6.12 the narrowing lived in reg_set_min_max(), which check_cond_jmp_op() called after it had decided that both sides could happen and pushed the jump side. v7.2 has no function of that name: the narrowing has moved into the decision itself.

shows what each side gets. An unsigned 64-bit test gives the side that jumps only umin=8. Every number of 263 or more passes that test and is negative when read as signed, so the signed reading learns nothing. The side that falls through gets a maximum in all four readings, and the sync adds the tnum.

A 32-bit test, which clang emits for a u32 index, narrows only the 32-bit arc and the low half of the tnum. When the upper half is already known to be zero, as after the zero-extension in the second row, the sync carries the bound into all 64 bits. When it is not, as in the third row, the 64-bit view learns only that the low half is at most 7. Its largest value becomes 0xffffffff00000007, and it takes the two shifts after the test to bound the whole register.

Copies share what a test learns

Clang often tests a value in one register and uses it from another, and the verifier follows that through ids. When a scalar is copied with a 64-bit move, assign_scalar_id_before_mov() (line 3364) gives the source a fresh id if it has none, and the copy takes the same one. For a loader with CAP_BPF, a store to the stack that keeps all the value's bits, and a load back, do the same for the slot (lines 3502 to 3508). At a conditional jump collect_linked_regs() (line 15852) gathers every live register and spilled slot that carries a compared register's id, and sync_linked_regs() (line 15885) copies the new bounds into each. Registers and stack slots that share an id in this way are linked registers: a bound learned on one reaches all the others.

shows the two common cases. In (a) the barrier_var() of libbpf, an empty asm statement, made clang keep a copy in r1 while the index stayed in r6; the test of r1 at slot 10 narrows r6 as well. In (b) the descriptor is a volatile local, so the test and the index are two loads from fp-8. The test's bound is written into the slot, and the second load takes it from there.

A link also holds across the addition of a constant, which the copy records as a delta, printed after the id as in id=2+1 (log.c line 667), so a test on i + 1 narrows i. Anything else ends it. Other arithmetic on a copy clears its id (line 14911), and so does a 32-bit move of a value that may not fit in 32 bits (line 15029). One refused program of lost its test in this way, when clang tested a masked copy of the index.

A pointer plus a number, checked at the access

The addition at slot 12 of the copy, r0 += r6, adds a scalar to a pointer and goes to adjust_ptr_min_max_vals() (line 13664). Some pointers may not move at all; a pointer-or-NULL is refused with R0 pointer arithmetic on map_value_or_null prohibited, null-check it first. Then check_reg_sane_offset_scalar() (line 13296) looks at the scalar's signed minimum. With no minimum the load fails with math between map_value pointer and register with unbounded min value is not allowed. With one further than 229 below zero (BPF_MAX_VAR_OFF, include/linux/bpf_verifier.h line 17) it fails with value … makes map_value pointer be out of bounds, and both return -EINVAL before any memory is touched.

A scalar that passes becomes the pointer's variable offset. After slot 12 the log prints r0 as map_value(id=1,…,smin=smin32=0,smax=umax=smax32=umax32=56,var_off=(0x0; 0x38)), a pointer somewhere in the first 56 bytes of the value, and no check of size has happened yet. That waits for the access.

At the access check_mem_access() (line 6078) hands the pointer to a checker for its kind of memory, and lists the three this chapter met. For a map value, check_mem_region_access() tries both ends of the offset. It refuses a minimum that could reach below the value, checks the smallest offset, calls an unsigned maximum of 229 or more unbounded, and last checks that the largest offset plus the size of the access ends inside the value. In the copy the largest offset is 56, and eight bytes read from 56 end at 64, the value's size, so the range alone lets the read at slot 13 pass. With fd <= 8 the largest offset becomes 64, and the kernel refuses the copy as it refused the third broken copy of .

A packet is measured differently, since its length is known only when the program runs. A pointer into it carries a range, the r= of the log, which a test against the packet's end sets for every pointer with the same id (find_good_pkt_pointers(), line 15106). After if (data + 1 > end), pkt(r=0) becomes pkt(r=1), and check_packet_access() runs the region check against that range. On the stack, the 512 bytes below r10, an offset that is not a constant is checked by its signed bounds in check_stack_access_within_bounds().

Which numbers must be exact

Pruning, as showed, ends a path where a saved state covers the current one. For scalars that comparison would rarely succeed if every bound counted, because two paths that differ only in a counter or a length would never match. The verifier therefore lets a scalar's bounds count only once some check has relied on them, and records that in a flag, precise, in struct bpf_reg_state. regsafe() in kernel/bpf/states.c (line 551) lets any current value match a saved scalar whose flag is clear. This record of which scalars' bounds a check has relied on is precision tracking, and the log marks a scalar with the flag set by a P, as in R6=Pscalar().

The word is the kernel's, and it means more here than it did in the section on soundness. There a description was precise when it held few values that cannot happen; here a scalar is precise when its bounds must be kept and compared as they are, however wide they may be.

A scalar becomes precise when its value starts to matter for safety. That happens when it is added to a pointer (line 14817), when its bounds decide a conditional jump (line 16035), when it is the size passed to a helper, and when the kernel restricts what a program returns. Every earlier scalar it was computed from must then become precise too, in the saved states along the path, since a checkpoint whose proof rested on those bounds must not cover a state with wider ones. mark_chain_precision() (line 3294) hands the register to bpf_mark_chain_precision() in backtrack.c (line 790). That function works by backtracking, walking back over instructions already verified to find which registers and stack slots the value came from.

Each instruction changes the set still to be marked, in backtrack_insn() (line 267). A copy r1 = r6 passes the mark from r1 to r6, r6 += r2 adds r2, and an operation with a constant, such as r6 <<= 3, keeps r6. A constant moved into the register ends its search, a load from the stack passes the mark to the slot, and a load from other memory ends it. is the walk for r6: back to slot 9, where the current state began, then through the parent state, whose r6 now prints as Pscalar(), to the load at slot 3. The jump history kept with each state says which instruction came before which.

The marks then change what pruning can do. A checkpoint on that path keeps r6 precise, so a later path that reaches it with a different range for r6 is not pruned there. Before each new checkpoint is saved, mark_all_scalars_imprecise() (states.c lines 1213 and 1570) clears the marks it inherited, so that only what a later check proves necessary is kept.

puts numbers on it. The two main programs differ in their last line. In matters, s->n[k & 7] += 1 adds k to a pointer, so k is marked precise back to its start, and paths that left different constants in it no longer prune each other. At sixteen tests the walk took 163,929 instructions and 8,827 states; at twenty it hit the budget of one million. In never, which only stores k, each later path is pruned at the first checkpoint it reaches, and the walk grows by ten instructions a test.

Taking the index out of the path's history removes the cost. A variant that indexes with x & 7, a bound of the input that is the same on every path, walked 185 instructions at sixteen tests. Writing the sum without if helps less, because clang turns each conditional addition into a shift and an AND. v7.2 splits a register that can only be 0 or −1 into two paths at such an AND (maybe_fork_scalars(), line 14558), so matters_flat still walked 14,696 instructions at sixteen tests and failed at twenty-four.

Masking against speculation

Everything so far concerns what the program does. A CPU also does work that no program asked for: it guesses the outcome of a branch and runs ahead on the guess, discarding the results if the guess was wrong. Running ahead in this way is speculative execution. The commit that brought this section's masking, in January 2019, gives a recipe for abusing it. Load an index, compute the limit slowly so that the CPU guesses the outcome of the test against it, read at the untested index, then read again at an address made from the byte that came back.

The kernel calls this Spectre variant 1, and whether the verifier defends against it is decided once per load (verifier.c line 19810). bpf_bypass_spec_v1() (include/linux/bpf.h line 2867) lets the load skip the defence if its loader holds CAP_PERFMON, or CAP_SYS_ADMIN, which passes every BPF capability test (token.c line 14). A kernel booted with mitigations off skips it too. Tracing programs need CAP_PERFMON to load at all (syscall.c line 3045), so the masking falls on socket filters and network programs loaded without it.

The masking is decided during the walk and written after it. When a scalar that is not a constant is added to a pointer, sanitize_ptr_alu() (line 13451) records how far the pointer may move, alu_limit, in the instruction's side data. retrieve_ptr_limit() (line 13356) works it out from the pointer's bounds and the size of what it points into: 56 for r0 += r7 into the 64-byte value. After the walk, bpf_do_misc_fixups() in fixups.c (from line 1703) puts six instructions before the addition.

The walk also takes up one more path, in which the pointer has not moved, as if the masking had made the offset 0, so that what a mispredicting CPU would run is checked too. That is why the second load of walked 23 instructions and saved 2 states, against 17 and 1.

The six compute the offset again without a branch, in r12, the verifier's own register BPF_REG_AX (include/linux/filter.h line 63). Slots 19 to 21 leave the sign bit of r12 clear when the offset lies between 0 and the limit, and set it otherwise. The negation reverses that, and the arithmetic shift spreads the sign bit over all 64 bits. The AND then keeps the offset when the result is all ones and makes it 0 otherwise, so a path the CPU should never have taken still reads inside the value.

The other two instructions come from elsewhere. The array lookup, which the kernel had replaced with its own instructions at slots 6 to 15, gains an AND that keeps the index inside the array (arraymap.c lines 232 to 234). The store of the key gains a nospec barrier, which the comment at fixups.c line 836 calls a mitigation for Spectre v4. Each run then took 25 ns against 20 (bpftool prog run, three runs of twenty million; other VM runs that day gave 26 and 21).

One limit per instruction is also a restriction. If the same addition is reached on two paths with different limits, the rewritten instruction cannot serve both. update_alu_sanitation_state() (line 13393) notices the difference, and the load fails with R0 tried to add from different maps, paths or scalars, pointer arithmetic with it prohibited for !root. The matters program, as a socket filter without CAP_PERFMON, is refused in this way, because its k & 7 differs from path to path; as root it loads.

Inside the v7.2 source

collects the code behind this chapter in the order an instruction reaches it. An arithmetic instruction goes from check_alu_op() (line 14917) to adjust_reg_min_max_vals(), which sends two scalars to adjust_scalar_min_max_vals() and a pointer with a scalar to adjust_ptr_min_max_vals(), after marking the scalar precise. A conditional jump goes to check_cond_jmp_op(), the walk's own code that followed as far as the pending branch, and an access to check_mem_access().

v7.2 has moved two parts of this out of verifier.c. Backtracking lives in backtrack.c, whose comment above bpf_mark_chain_precision() (lines 703 to 789) explains why marks in the current state do not matter and marks in saved states do. The comparison that uses the marks lives in states.c, and the arcs have files of their own, cnum.c and include/linux/cnum.h.

What it costs

CPU
Kernel 7.2.15, VM with 16 vCPUs, 12 November 2026. A proved bound costs one compare and jump per event. At load, sixteen tests whose result became an index cost 163,929 instructions walked and 103 ms, against 174 and 0.39 ms when the result was only stored. Without CAP_PERFMON a socket filter grew from 22 to 30 instructions and from 20 to 25 ns a run.
Memory
Each register state is 88 bytes, 40 of them the tnum and the two arcs (BTF of 7.2.15); the precise walk held up to 89 states at once, against 13.
Switches
None: bounds and marks live inside the bpf() call that loads the program.
Locking
A loader without CAP_BPF, which gets no precision tracking, holds bpf_verifier_lock for its whole walk: 80 ms for the sixteen-test never.

Test an index as an unsigned number, on the value added to the pointer, after the last call that could change it. If the statistics grow with the branches an index passes through, derive it from the input instead. Grant CAP_PERFMON only to a loader trusted with kernel memory; otherwise expect six more instructions for each pointer moved by an unknown offset.

When it goes wrong

The rows of come from copies of the per-descriptor counter, each changed in one line and read from the bottom up, as taught. Most rows ask one question at different places: what bounds did the scalar have when it met the pointer, and which instruction gave it them? The error code sorts them. -EINVAL comes from the addition itself, when the scalar's minimum is missing or absurd, and -EACCES from the access, or from the masking.

Three rows have a test in the source that the log does not honour, for three reasons. In the masked copy the test was on another register, and the AND had ended the link. After the helper call the test was on an earlier load, and memory that other CPUs can write says nothing about the next load. The signed index was tested only from above. In each, the log shows the bound on one line and a register without it on a later one, and the instruction between them is what must change.

Recap

For every register on every path the verifier keeps an abstract value; for a scalar that is a range, stored in v7.2 as two circular arcs, and a tnum, and after each step each description corrects the other. Arithmetic moves both, a test narrows both on each side of its branch, in 32 or 64 bits, and copies that share an id share what a test learns. A scalar added to a pointer must have a sane minimum, and the access checks both ends of the offset against the size of what is read. A description must be sound; precision tracking keeps exact only the scalars a check relied on, found by walking back through the instructions, and that choice decides how well paths prune. A loader without CAP_PERFMON also gets masking against speculation, six instructions for each pointer moved by an unknown offset.

xxx1: every odd number from 1 to 15. The real sums are 4+1, 4+5, 6+1 and 6+5, so 5, 7, 9 and 11; the values 1, 3, 13 and 15 can never happen. The arithmetic of tnum_add() in kernel/bpf/tnum.c: masks add to 0110, values add to 0101, their sum is 1011, which differs from 0101 in 1110; OR the two masks in and the unknown bits are 1110, leaving bit 0 known as 1. Adding the values and ORing the masks looks reasonable and gives 0xx1, but that misses 9 and 11, so it is unsound: it ignores the carries, which spread the unknown bits upward.

From the range: 64 is the largest offset the register can add, plus the instruction's own 0. With fd <= 8 the test proves r6 is at most 8, and the shift by three makes that 64; the log line for slot 12 shows umax=64 on r0. check_mem_region_access() tries the largest offset, and eight bytes read from 64 end at 72, past the 64-byte value. Use fd < 8. It is easy to take off=64 for the instruction's offset field, but that field is zero, and the kernel adds the largest value of the range before it checks.

Because the register holds 64 bits, and the kernel reads them both ways. Without the test, r6 has no bounds, and after r6 <<= 3 the log shows smax=0x7ffffffffffffff8 with no smin printed, which means the signed minimum is the most negative 64-bit number. Adding a number that may be negative could move the pointer before the map value, so check_reg_sane_offset_scalar(), called from adjust_ptr_min_max_vals() in verifier.c, refuses the addition itself, before any read. The C type misleads here, because u64 exists only in the source and the bytecode attaches no signedness to registers.

umax=0xffffffff00000007 and var_off=(0x0; 0xffffffff00000007), the third row of . A 32-bit jump compares only the low half, so regs_refine_cond_op() narrows the 32-bit arc to 0 to 7, and the sync makes bits 3 to 31 of the tnum known zeros; the upper 32 bits stay unknown. The largest 64-bit value is then all ones above bit 31 and 7 below. It is tempting to answer 7, as for a 64-bit test, but that needs the upper half known to be zero, which only the two shifts clang placed after the test provide.

That the slot still holds what the program last stored, with that value's whole state. A 64-bit store of a scalar to the stack keeps its register state in the slot, and a load back links register and slot by id, so the test at slot 11 narrows fp-8 as well and the second load copies the narrowed state (, part b). A map value is memory that user space and other CPUs can write at any time, so every load from it starts as a fresh scalar with the full range of its size. It is tempting to credit volatile, but the verifier never sees it; it sees two loads from a slot it tracks.

It comes close to matters, with the same 8,827 states, because without CAP_BPF every scalar is precise from the start: __mark_reg_unknown() sets the flag to !env->bpf_capable (verifier.c line 2166), and bpf_mark_chain_precision() returns at once (backtrack.c line 805). With k precise, paths that left different constants in it cannot prune each other; 122,185 / 174 is about 700. A common mistake is to blame the extra checks an unprivileged load gets; the states column shows that the walk itself grew, as it does for matters, whose last line makes k precise.

On each path k & 7 is a different constant, so the addition moves the map pointer by a different known amount on each. Without CAP_PERFMON, sanitize_ptr_alu() records one limit and one kind of masking in the instruction's side data, and update_alu_sanitation_state() (verifier.c line 13393) refuses a second path whose record differs, because the rewritten instruction can carry only one. As root bpf_bypass_spec_v1() is true and nothing is recorded. It is easy to read "different maps" and look for a second map; the message covers three causes, and here it is the scalars.

40, and then 0. For 40: 56 − 40 = 16, 16 | 40 = 56, the negation makes it negative, the shift by 63 gives all ones, and the AND leaves 40, so slot 26 reads at offset 40. For 64: 56 − 64 = −8, −8 | 64 is still −8, the negation gives 8, the shift gives 0 and the AND gives 0, so slot 26 reads at offset 0. The test at slot 17 never lets 64 through on a path the CPU should take; the masking matters only when it runs past that test on a wrong guess. Reading the mask as a clamp to 56 is a common mistake: an offset out of range becomes 0, never the limit.

Because slot 3 is where r6 was written, and a test does not write the register it tests. Slot 3 loads r6 from memory that is not the stack, the tracepoint's arguments, and backtrack_insn() (backtrack.c line 267) ends the search at such a load: the value's range came from the size of the load, which no earlier register decided. Had slot 3 loaded r6 from the stack, the mark would have passed to that stack slot, and the walk would have gone on to the instruction that stored there. Stopping at slot 10 is a tempting answer, but a test only narrows a value that some earlier instruction made.

An abstract operator is sound when, for any inputs it is given, every concrete result is inside its abstract result. Equation 1 says it as: for all concrete values inside the input abstract values, the concrete operation's output is a member of the abstract output. The definition is in Section 2 under "Abstract operators", and the SMT form in Section 4.1. Requiring the abstract result to equal the concrete set asks for more than soundness; that is precision, which the paper treats as desirable and the kernel does not promise.

Because the kernel's code mixes them. Figure 2(b) sets the unsigned minimum from the tnum's value, so an operator on one description reads the output of another. The paper calls these abstraction/reduction operators and checks all five descriptions in one formula, which Section 3 calls "one-shot" reasoning. A reader who knows textbook reduced products may expect independent descriptions that can be proved one by one, but the kernel was never written that way.

5.13 to 5.19, under the refined specification. The assumption is that every input has already passed through the shared tail of the operators, reg_bounds_sync() in 5.19, which rules out combinations of descriptions no real program reaches (Section 4.2). Under the general specification every version from 4.14 to 5.19 had violations, as Figure 5(a) shows, and the older kernels held 27 bugs nobody had reported. Answering "all of them" overlooks the general check, which the newest kernels still fail, although no real program can trigger those failures.
