The machine: instruction set and calls

The write counter reaches the kernel as 216 bytes, and every one of them belongs to a field with a fixed place in an eight-byte slot. We read all 27 slots, follow the kernel's copy of them down to 152 bytes of x86, and see what the kernel says about bytes that break the rules.

The counter as 216 bytes

We start from the bytes. Compiled as in and disassembled with llvm-objdump -dr, the write counter is the listing of . Each line is one slot, with its number on the left, its eight bytes in the order they sit in the file, and clang's reading of them on the right. The slots run from 0 to 26, yet the numbers 7, 14 and 22 never appear, because the instructions at 6, 13 and 21 take two slots each. The section that holds the code is 216 bytes long (0xd8 in llvm-readelf -S), which makes 27 slots and 24 instructions.

Slots 6 and 21 load the address of a map, a kernel object of keys and values that programs and user space both read and write. Here it is the table write_counts, in which the counter keeps one count per thread. Slot 13 loads the address of the format string that bpf_printk prints. All three hold zeros in the file, and the line under each, a relocation of type R_BPF_64_64, names what belongs there once the map and the string exist in the kernel, which happens only when the counter is loaded ().

The other slots are complete as they stand, and takes twelve of them apart field by field. Four rules decode every row.

The low three bits of the opcode byte name the instruction's class, and the other five bits mean different things in different classes. The register byte holds the destination in its low four bits and the source in its high four, so a2 in slot 4 is destination 2 and source 10. The offset and the immediate are signed and little-endian, which makes both fc ff and fc ff ff ff read as −4. A field the instruction does not use is zero, a rule the kernel enforces ().

Two rows read differently from the rest. The offset of slot 9 is a distance in slots, counted from the slot after the jump. So goto +2 skips slots 10 and 11 and lands at 12, where the counter goes on whether or not the lookup found an entry. The immediate of slot 11 is no number to add: its 1 names an operation, a fetching add, and the value added comes from r1.

Two machines, twenty-one years apart

The bytes of belong to a machine with a history. The left side of is the 1993 machine from the prologue, with its accumulator A, an index register X, a few words of scratch memory and one packet as input. Linux ran it for years for tcpdump's socket filters and seccomp's system-call filters.

Still runningThe left column has not gone away: tcpdump -d 'tcp port 22' prints the classic program that tcpdump compiles, and Linux rewrites such filters into the new instructions before it runs them.

In 2014 Alexei Starovoitov rebuilt that machine inside the kernel. LWN called the result "internal BPF" at the time, and the kernel documentation now calls it eBPF, extended BPF. Linux 3.15 shipped it in June 2014 and converted every classic filter into the new instructions, so tcpdump never saw a difference.

The conversion still runs, in bpf_convert_filter() in net/core/filter.c, and it shows how the old machine fits inside the new one. A lives in r0 and X in r7 (BPF_REG_A and BPF_REG_X in include/linux/filter.h). Each word k of classic scratch memory becomes four bytes of stack at r10 − (4k + 4), so the new machine needed no scratch memory of its own.

We can read the right column from the top, since each row answers a limit of the left one. Ten 64-bit registers, r0 to r9, match the registers of a modern 64-bit CPU, and r10 is a read-only frame pointer to a small stack. A call instruction reaches into the kernel, and since Linux 3.18 added maps in December 2014 a program can keep state between runs. Both machines still end by handing one value back out.

"The latter expands the set of available registers from two to ten, adds a number of instructions that closely match real hardware instructions, implements 64-bit registers, makes it possible for BPF programs to call a (rigidly controlled) set of kernel functions, and more."

Eight bytes per instruction

Every eBPF instruction is eight bytes, cut into the fields that marks out. The first byte is the opcode, and the next holds two register numbers of four bits each, a source and a destination. After them come a signed 16-bit offset, the field eBPF uses for memory addresses and jump distances, and a signed 32-bit immediate. The counter's instructions, as clang -target bpf writes them into the object file and the kernel receives them, are its bytecode.

The classic layout above it in the figure is also eight bytes, cut differently: a 16-bit opcode, two one-byte jump distances and a 32-bit constant. The new machine kept the size and moved the fields, so a classic filter's bytes read as nonsense to it, as the second row of shows. The kernel declares the new layout in include/uapi/linux/bpf.h at line 80:

struct bpf_insn {
        __u8    code;           /* opcode */
        __u8    dst_reg:4;      /* dest register */
        __u8    src_reg:4;      /* source register */
        __s16   off;            /* signed offset */
        __s32   imm;            /* signed immediate constant */
};

One declaration serves every architecture, and the host's byte order decides where its fields land. On a little-endian host such as x86-64, the destination sits in the low four bits of the register byte, and the offset and the immediate are stored low byte first. A big-endian host swaps the two register numbers and stores the longer fields high byte first, and the RFC prints one instruction both ways.

Eight classes

The low three bits of every opcode name one of eight instruction classes, which lists with the counter's slots in each. Six of the eight come from 1993 with their numbers unchanged, since include/uapi/linux/bpf_common.h still serves classic and extended BPF alike. The classic RET and MISC, 6 and 7, became JMP32 and ALU64 in bpf.h. The counter uses six classes, and most of its 24 instructions are 64-bit arithmetic and jumps.

The other five bits are split in one of two ways. In the arithmetic and jump classes, the top four bits name the operation. Bit 3 says where the second operand comes from, the immediate (K, 0) or the source register (X, 1), so b7 is 1011 0 111, a move from the immediate in ALU64, and bf differs from it only in that bit. In the load and store classes, the top three bits are a mode and the next two a size of 1, 2, 4 or 8 bytes. So 7b is 011 11 011, a plain memory access (MEM) that stores eight bytes (DW) from a register (STX).

ALU and ALU64 hold the same operations at two widths. A 32-bit operation reads the low halves of its registers and writes zeros into the upper half of its destination. Clang gives such operations the w names, so the counter's w2 = 0x1a at slot 15 sets all 64 bits of r2. JMP and JMP32 differ in the same way, except that the calls, the exit and the 16-bit goto live in JMP alone.

Arithmetic, and how far a jump reaches

Arithmetic offers the operations of a small integer CPU, fourteen codes from add (0x0) to byte swap (0xd). Signed division, signed modulo and the sign-extending move reuse the codes of division, modulo and move, and the offset field tells them apart: 1 for the signed operations, and 8, 16 or 32 for the width a move extends from. Division by zero does not trap, since division writes 0 and modulo leaves the destination as it was. The kernel's copy of the document adds one rule that RFC 9669 leaves out, for the most negative number divided by −1, which stays itself and leaves a remainder of 0.

A jump's offset counts slots from the slot after the jump, as slot 9 showed, and sixteen signed bits reach 32,767 slots forward or 32,768 back. For anything farther, the standard defines a goto in the JMP32 class that takes its distance from the 32-bit immediate, which llvm writes gotol. It also suggests turning a long conditional jump into a short one over a long goto. Few programs are long enough to need it, although a loader with CAP_BPF may hand the kernel up to a million instructions (syscall.c line 3034).

Linux v7.2 decodes two jumps that neither RFC 9669 nor its own copy of the document describes. may_goto, opcode 0xe5, is a JMP-class jump with the code JCOND that the kernel itself decides to take, so that a loop the program cannot bound still ends ( of ). gotox, opcode 0x0d, is a goto with the X bit set. It jumps to an address held in a register, read from a jump table that the kernel keeps in a map (kernel/bpf/bpf_insn_array.c), and it came with Linux 6.19.

Memory, and the atomic at slot 11

As the primer put it, only loads, stores and atomic operations touch memory. A load or a store adds the offset to a base register, and the counter reaches its whole stack this way, the key at r10 − 4 and the value at r10 − 16. A load zero-extends what it reads into the 64-bit register. Version 4 of the instruction set, accepted from Linux 6.6, added a mode that sign-extends, MEMSX. A byte loaded with it is opcode 0x91, where clang's default version spends three instructions, a byte load and two shifts.

An atomic operation is a read, a change and a write that no other CPU can come between. eBPF encodes every one of them as a store, the class STX with the mode ATOMIC (0xc0), and names the operation in the immediate. The immediate takes the arithmetic codes for add, or, and and exclusive or, plus 0x01, FETCH, when the old value should come back in the source register. Exchange (0xe1) and compare-and-exchange (0xf1, which compares with r0 and leaves the old value there) always fetch. They come in 32 and 64 bits only, so llvm's assembler and the kernel both refuse lock *(u8 *)(r10 - 8) += r1.

The counter's slot 11, db 1a f0 ff 01 00 00 00, is a 64-bit fetching add into its value on the stack. traces it back to __atomic_fetch_add() in the C source and to the version of the instruction set clang was asked for. Linux 6.15 added two operations under the same class and mode that RFC 9669 predates and v7.2's document does not list. Load-acquire (immediate 0x100) and store-release (0x110) are a load and a store with the memory ordering their names describe, and they alone among the atomics accept 8- and 16-bit widths (bpf.h lines 54 and 55).

The wide instruction

One instruction does not fit the eight-byte mould. A wide instruction takes two slots and sixteen bytes, because it loads a 64-bit value into a register and the immediate holds only 32 bits. Its first half is an LD instruction with the mode IMM and the size DW, opcode 0x18. The second half is a pseudo-instruction whose fields are all zero except the immediate, next_imm in the ISA document, which holds the upper 32 bits. The kernel's C joins the two halves in one line ().

Most of the time the 64 bits are not a constant at all. The first half's source field, of no use to a load from the immediate, says what the immediate means, and lists the seven meanings that Linux v7.2 knows. A map is the commonest. The loader writes the map's file descriptor into the immediate and 1, BPF_PSEUDO_MAP_FD, into the source field. While it checks the program, the kernel swaps the descriptor for the map's address in check_and_resolve_insns(), which writes the address's low half into insn[0].imm and its high half into insn[1].imm.

Form 2 does the same for a place inside a map's value, and that is how the counter's format string arrives, since the loader keeps the object's read-only data in a map of its own. The other forms reach things the kernel already has. Form 3 loads the address of a kernel variable named by its type ID, a number from the kernel's own description of its types that introduces. Form 4 loads the address of one of the program's own functions, for a helper that calls it back, such as bpf_loop() in . Forms 5 and 6 name a map by its index in fd_array, an array of descriptors that the loader passes beside the program, and a load that uses them without one fails with fd_idx without fd_array is invalid.

Calling into the kernel

The write counter calls into the kernel four times, at slots 0, 8, 16 and 24 of . Each call goes to a helper function, a function inside the kernel that a program may call by number. The program names it by a small integer, the helper ID, which clang stores in the call instruction's immediate. Helper 14 returns the process and thread IDs of the running task, and helper 1 looks up a key in a map. The IDs are the values of the BPF_FUNC_ enumeration in vmlinux.h, a header the counter already includes, and names all four.

The counter's slot 1Slot 1 stores w0, the low 32 bits of r0, and every register has a w name for its low half. Helper 14 puts the thread ID in that low half and the process ID in the high half, so the counter's table counts writes per thread, although in a single-threaded process the two numbers are the same.

Linux v7.2 numbers its helpers from 1 to 211, the last being bpf_cgrp_storage_delete(), and the comment under the list in bpf.h says that it "is effectively frozen". New ways into the kernel arrive as the third kind of call in , which follows from the inside. All three kinds use the opcode 0x85, and the source field tells them apart, as it does for the wide instruction. With 1 there, the immediate is a distance in slots to another function of the same program, counted like a jump's, and that function's exit returns to the caller. Linux has accepted such calls since 4.16.

With 2 in the source field, the immediate is the type ID of a function inside the kernel. The offset says whose types to look it up in, 0 for the kernel's own and any other value an index into fd_array for a module (find_kfunc_desc_btf()). These calls came with Linux 5.13. RFC 9669 describes the first and third kinds by their encoding alone, and leaves to each platform what the functions behind the numbers do.

Arguments reach a helper through eBPF's calling convention, which lays out register by register. Registers r1 to r5 carry up to five arguments and r0 carries the answer back, and after the call r1 to r5 cannot be read; in the words of the kernel documentation they are "reset to unreadable". Registers r6 to r9 are callee-saved, in the primer's terms, so they keep their values across the call, and r10 never changes. The rule holds for all three kinds of call, and a comment in kernel/bpf/core.c states it in one line: a call "scratches BPF_R1-BPF_R5 registers, preserves BPF_R6-BPF_R9, and stores return value into BPF_R0".

We can watch the rule at work in the counter's listing, where the map goes into r1 at slot 6 and again at slot 21, because no value in r1 is kept across a call. shows the map gone from r1 after the call, so a value the program needs later has to be parked in r6 to r9. Five argument registers are enough for every helper. Since r1 to r5 sit in the registers where x86-64 already passes arguments (), a call moves nothing before it jumps.

Inside the v7.2 source

lists the files behind everything so far. The two headers under include/uapi are the format itself, shared with user space. filter.h adds the kernel's own names, among them two registers beyond r10. BPF_REG_PARAMS, register 11, may appear only in the 8-byte loads and stores that pass a call's arguments beyond the fifth on the stack (is_stack_arg_ldx() and its two neighbours, filter.h lines 753 to 772), and BPF_REG_AX, register 12, is a spare that no program can name and the kernel uses when it rewrites a program. The rest of the table is code that carries the bytes out.

An interpreter runs a program by reading one instruction at a time and doing what it says. The machine's interpreter is ___bpf_prog_run() in core.c, which came with the machine in 2014, inside net/core/filter.c, and later moved to kernel/bpf. shows its outline, a jump table and a loop.

The jump table has 256 entries, one for every value of an opcode byte, each the address of a label inside the function, a C extension written &&label. Every entry starts as default_label, and BPF_INSN_MAP then overwrites the 121 opcodes the interpreter runs. At select_insn the interpreter looks up the slot's opcode and jumps there. The code at the label does the work, and CONT moves insn to the next slot and jumps back, so every instruction costs a table lookup and an indirect jump before it does anything. LD_IMM_DW steps over a wide instruction's second half with an extra insn++.

A loader may send 129 opcodes, eight more than the interpreter runs. bpf_opcode_in_insntable() adds the six classic packet loads, may_goto and gotox, and the kernel rewrites the packet loads and may_goto into ordinary instructions before the program runs (fixups.c). Any other opcode is refused at load as unknown. default_label should therefore never be reached, and if it is, BUG_ON(1) ends the run with a kernel bug report, since the comment above it warns that returning 0 could let a broken program keep running.

JMP_CALL shows what became of the helper ID. The interpreter calls __bpf_call_base + insn->imm, and the immediate it adds is no longer 14. While the kernel checks the program, it replaces each helper ID with the distance in bytes from __bpf_call_base, a function in core.c that only returns 0, to the helper's code (fixups.c line 2341), so that one addition finds any helper. shows the counter's copy after the load, where slot 0 holds 260,144 in place of 14.

The dump differs from the object in three ways. The calls carry distances, the third one negative because bpf_trace_printk() lies below __bpf_call_base in memory. The wide instructions show source field 1 with map 2, and source field 2 with map 4 and offset 0 for the string.

The kernel holds addresses in those slots, but bpf_insn_prepare_dump() in syscall.c turns each one back into a map ID for the reader, and it shows a call's rewritten immediate only to a reader allowed to see kernel addresses. The lookup at slot 8 has become a direct call into the hash table's own code, followed by two new slots that turn the element it finds into the address of its value. That is why the kernel's copy is 29 slots and 232 bytes where the object held 27 and 216, and explains the two slots.

The tagbpftool prints a tag for every program, 0b348880a0a9dde6 for the counter. It is the first 8 bytes of a SHA-256 over the slots as loaded, with each map descriptor set to zero so that the same bytes give the same tag in every process (bpf_prog_calc_tag(), core.c line 301).

The interpreter is entered through one of sixteen small functions, __bpf_prog_run32 to __bpf_prog_run512, one for each multiple of 32 bytes of stack. Each declares the program's stack as an array on the kernel stack, points r10 at its end and r1 at whatever the hook passed, and calls ___bpf_prog_run() (core.c lines 2400 to 2410). bpf_prog_select_interpreter() picks one by the program's stack depth rounded up to 32, so the counter's 16 bytes would run in __bpf_prog_run32.

None of this runs on the kernel used in this book. Arch Linux builds 7.2.15 with CONFIG_BPF_JIT_ALWAYS_ON=y, which compiles the interpreter out (the #ifndef at core.c line 1833) and has every program translated into x86 when it loads; of shows the evidence. Even a kernel that keeps the interpreter translates a program that calls a kernel function by type ID, since __bpf_prog_select_runtime() marks it jit_needed (core.c line 2679).

The ISA document closes the loop from the other side, because it does not ask every runtime to run every instruction. A conformance group is a named set of instructions that a runtime supports whole or not at all. Every runtime must support base32, and it may add base64 for the 64-bit instructions, atomic32 and atomic64, divmul32 and divmul64 for multiplication, division and modulo, and packet for the legacy packet loads (section 2.4 of RFC 9669). Linux accepts instructions from all seven, the packet loads only in the three kinds of program that are handed a socket buffer. Beyond them it accepts the five additions this chapter has met, may_goto, gotox, load-acquire, store-release and register 11, and a sixth, a cast between address spaces written as a 64-bit move with offset 1 (BPF_ADDR_SPACE_CAST in bpf.h).

What a fixed width costs

The encoding's price and its return are both in . A fixed eight bytes is generous for exit, which uses one byte of them, and a 64-bit constant takes sixteen. The counter's eBPF is therefore larger than its x86, 232 bytes against 152, where x86 spends from one byte (leave) to ten (a movabsq carrying a 64-bit address, one for each wide instruction). What the fixed width buys is a decoder with no state: slot n starts at byte 8n, a jump can be checked by arithmetic on slot numbers, and an interpreter needs one table lookup per instruction. The 26 instructions of the kernel's copy became 36 of x86, one for most slots, two for each conditional jump and for the exit, and seven at the function's entry.

What it costs

CPU
Kernel 7.2.15 in a VM with 16 vCPUs, 12 November 2026. Decoding costs nothing per run, since the counter's 29 slots became 36 x86 instructions when it loaded; an interpreter would spend a table lookup and an indirect jump on every slot, and this kernel has none to measure (CONFIG_BPF_JIT_ALWAYS_ON=y). A run of the counter takes 144 to 162 ns without bpf_printk and 0.48 to 0.54 µs with it (), and a helper call about 4.1 ns ().
Memory
Eight bytes a slot, sixteen for a wide instruction: 216 B in the object, 232 B in the kernel's copy, 152 B of x86. The program and its slots fit one 4 KB page (bpftool's memlock 4096B); the stack is at most 512 B (MAX_BPF_STACK), and the counter uses 16.
Switches
One copy of the slots into the kernel at load (copy_from_bpfptr(), syscall.c line 3123). None at run time: every call is a function call inside the kernel, on the thread that reached the hook.
Locking
None in the encoding. Slot 11, the counter's only atomic, becomes one locked x86 instruction, lock xaddq, 6 bytes.

Count a program in slots and calls: a slot becomes one or two x86 instructions and a helper call costs a few nanoseconds, so a program of a few dozen slots runs in well under a microsecond unless it prints. Build with clang's default version of the instruction set unless every kernel the program must load on is 6.6 or later, and check the object with llvm-objdump -d for opcodes an older kernel lacks.

When it goes wrong

The rows of come from small programs written byte by byte and handed to the kernel by rawload.c, a loader of about a hundred lines that calls bpf() directly, so no compiler or library stands between the bytes and the kernel. Most of them are refused before the kernel walks a single instruction, as the last line of each log, processed 0 insns, says.

bpf_check() runs its passes over the bytes in a fixed order. It first checks that every jump lands inside the program and that the last slot is an exit or a jump. check_and_resolve_insns() then checks every slot's register numbers, opcode and unused fields and turns map descriptors into addresses, and bpf_check_cfg() follows the jumps to find unreachable slots and jumps into a wide instruction's second half. That order explains the second row, where a classic filter's unknown opcode at slot 13 goes unreported because its jump at slot 1 fails first.

The error code sorts the rest. EINVAL marks bytes the machine does not define or a call it cannot resolve. EACCES marks a rule about registers broken on a path the kernel walked, such as reading r1 after a call or writing r10, and and read such logs in full. Two rows are loads that succeed, which only the bytes explain. An immediate written big-endian loads and returns 16,777,216, and a sign-extending load runs on 7.2 but is an unknown opcode to any kernel before 6.6, so a program meant for old kernels should be loaded on the oldest one before it ships.

  9. Your hand-written socket filter, meant to return 1, loads without complaint and returns 16777216. Its first slot is b7 00 00 00 00 00 00 01. What went wrong, and why did the kernel not refuse it?

Answers unfold under each question here; in print they are in the answer key under .

Recap

The write counter is 27 slots of eight bytes, 24 instructions of which three are wide, and every slot splits into an opcode, two four-bit register numbers, a signed 16-bit offset and a signed 32-bit immediate, little-endian on x86-64, with every unused field zero. The opcode's low three bits name one of eight classes, and the other five hold an operation and a source bit in arithmetic and jumps, or a mode and a size in loads and stores; atomics are stores whose immediate names the operation, and a wide instruction's source field says whether its 64 bits are a constant, a map, a value inside a map, a kernel variable or a function. A call carries a helper ID, a distance to a function of the same program or a kernel function's type ID, takes its arguments in r1 to r5 and answers in r0, and leaves r1 to r5 unreadable. The kernel checks every slot's opcode and fields before it walks anything, rewrites helper IDs into distances and map descriptors into addresses, and on the kernel used here translates the result into x86, since its interpreter is compiled out.

24 instructions in 216 bytes. Every slot is eight bytes, so the section holds 27 × 8 = 216 bytes, and three of the slots are the second halves of wide instructions, which leaves 27 − 3 = 24 instructions. llvm-readelf -S /tmp/hashmap.bpf.o confirms it: the section named after the counter's hook has size 0xd8, which is 216. Answering 27 mixes up slots and instructions; the disassembler numbers slots, and so the line after the wide instruction at slot 6 is slot 8.

The program read r1 after a call, and after a call r1 holds nothing readable. A helper call leaves r1 to r5 unreadable whatever the helper did, so after call 1 the map is no longer in r1. The fix is to load the map into r1 again before the next call, as the counter's slot 21 does, or to keep a needed value in r6 to r9. The rule is in the kernel's "Classic BPF vs eBPF" page: after a call, "R1 - R5 are reset to unreadable". One might suspect the helper of overwriting r1 with junk, but the kernel never looks at what the helper did and applies the rule to every call.

No; the zero is a placeholder. The line under it, R_BPF_64_64 write_counts, is a relocation, a note telling the loader that this instruction must point at the map named write_counts, which does not exist yet when clang writes the file. When the loader creates the map, libbpf writes the map's file descriptor into the instruction and marks it as a map reference, and the kernel swaps in the map itself; section 5.4 of the RFC lists that form, and walks through it. Reading 0x0 as NULL would be right for code that runs as written, and nothing runs from this file as written.

29 slots, two more than the object's 27: 232 / 8 = 29. While it checked the counter, the kernel replaced the call to helper 1 at slot 8 with a direct call into the hash table's own lookup, __htab_map_lookup_elem(), and added two slots after it, if r0 == 0x0 goto pc+1 and r0 += 56, which turn the element found into the address of its value. bpftool prog dump xlated shows them as slots 9 and 10, and the old slots from 9 on move down by two. It is tempting to blame the wide instructions for the growth, but they already took sixteen bytes each in the object.

The sign-extending load. Opcode 0x91 is class LDX (1) with the size B (0x10) and the mode MEMSX (0x80): one byte loaded and sign-extended, an instruction of version 4 that Linux accepts from 6.6. A 6.1 kernel has no entry for it in bpf_opcode_in_insntable() and refuses the program before walking it; the v6.5 source has no MEMSX at all. With the default version, clang writes the same load as three instructions, a zero-extending byte load and two shifts, which kernels before 6.6 also run. A missing helper is a natural suspect, but a helper fails with invalid func, never with an opcode.

Slot 12, and slot 32,777. The offset 02 00 is +2, counted from the slot after the jump, so 9 + 1 + 2 = 12. The offset is a signed 16-bit field whose largest value is 32,767, and 9 + 1 + 32,767 = 32,777. A farther jump needs gotol, the goto of the JMP32 class that takes its distance from the 32-bit immediate, and a far conditional jump becomes a short one over a gotol. Counting from the jump itself gives 11 and 32,776, the usual slip; the interpreter's JMP_JA adds the offset to insn, and CONT then adds one more.

From classic BPF's jump bytes read as eBPF's offset. A classic instruction is a 16-bit code, two one-byte jump distances and a 32-bit constant, so the second instruction of tcp port 22, { 0x15, 0, 6, 0x000086dd }, is stored as 15 00 00 06 dd 86 00 00. eBPF reads bytes 2 and 3 as a little-endian offset, 0x0600 = 1,536, and the jump at slot 1 lands at 1 + 1 + 1,536 = 1,538. The kernel checks jumps before opcodes, so this message hides the unknown opcode b1 at slot 13. Classic filters reach the kernel through SO_ATTACH_FILTER, which converts them with bpf_convert_filter(); BPF_PROG_LOAD takes eBPF only.

The three wide instructions, and 18 bytes. Each became a movabsq, the x86-64 move that can carry a full 64-bit constant, two bytes of prefix and opcode (48 bf) and eight of address, so 10 bytes replace 16, six saved each and 18 in all. bpftool prog dump jited ... opcodes shows them at offsets 0x33, 0x5d and 0x7f. The calls are a natural guess, since they reach farthest, but a callq is five bytes, an opcode and a 32-bit distance from the next instruction (e8 and four bytes in the dump).

The immediate was written in big-endian order. On x86-64 the immediate is little-endian, so bytes 4 to 7, 00 00 00 01, read as 0x01000000, which is 16,777,216. The kernel cannot know that 1 was meant, since every 32-bit value is a valid immediate for a move. llvm-objdump -d prints the slot as r0 = 0x1000000, and llvm-mc -triple bpfel -show-encoding gives b7 00 00 00 01 00 00 00 for r0 = 1. A common expectation is that the load step catches such mistakes, but it refuses only fields that must be zero or numbers it does not know.

The jump class, and a call that takes its target from the immediate. The low three bits of 0x85 are 101, which is 0x5, the JMP class in the class table of section 3.3. The top four bits are 1000, which is 0x8, CALL in the jump table of section 4.3, and the bit between them is 0, which section 4 calls K: the operand is the immediate. CALL is easy to look for among the arithmetic instructions, since a call does work, yet CALL and EXIT both live in the jump class.

Because the immediate holds only 32 bits. A 64-bit constant, such as an address, cannot fit in one slot, so the wide encoding of section 3.2 appends a second eight bytes whose immediate carries the upper half, and section 5.4 gives the arithmetic: dst = (next_imm << 32) | imm. The counter's object uses it three times, twice for the map and once for the bpf_printk format string. Long jumps are a natural guess for a reason to need sixteen bytes, but in this standard only the 64-bit immediate loads use the wide form.

An ID, and no other information about the helper. Section 4.3.1 says a helper was identified by a static ID in the immediate, and that platforms with kernel type information may put a type ID there instead. What each helper does, which arguments it takes and what it returns are left to the platform, which on Linux means the kernel's helper documentation and the BPF_FUNC_ list. So helper 1 means "map lookup" on Linux without the standard saying so. Readers who look for a list of helpers in the RFC will not find one, because the standard leaves that to future work.
