Memory you manage: allocated objects, kptrs, lists and trees, arenas

Every map so far was a table the kernel sized before the first event. In this chapter the write counter allocates its own memory, first as one node per thread linked into a red-black tree that the verifier follows object by object, then as a hash table inside an arena, a block of pages that the counter shares with user space and that the verifier no longer follows at all.

The counter keeps its own tree

The counter of the last chapter kept one slot per thread in a hash map, and the kernel made all 1,024 slots when the loader created it. In this version, c_rb.bpf.c in book/labs/memory, the counter makes a node the first time a thread writes. The memory comes from the kernel while the counter runs, and the node goes into a tree ordered by thread ID.

A red-black tree is a binary search tree that recolours and rotates its nodes on every insert. No path from its root to a leaf is then more than twice as long as any other, so a lookup among n nodes takes at most about 2 log₂ n steps. shows the node, the map value that holds the tree's root and its lock, and the lookup that runs on every write.

Three things in the listing are new. The node embeds a struct bpf_rb_node, 32 bytes that the kernel uses to link it. The map value embeds a struct bpf_rb_root, whose __contains tag tells the verifier through BTF which type the tree holds and through which field. Every call that touches the tree sits between bpf_spin_lock() and bpf_spin_unlock() on the lock in the same value. The counter has also moved from the write tracepoint to fentry/vfs_write, because in v7.2 check_map_prog_compatibility() refuses a kprobe, tracepoint, perf-event or raw tracepoint program that names a map holding a bpf_rb_root or a bpf_spin_lock, the second of which lists.

We load it with mbench, a small loader in the same folder that attaches the counter, runs three writer threads of 1,000 writes each, and holds the program loaded while bpftool looks at it (). bpftool finds the program and a map with one 40-byte value and a memlock of 344 bytes. Its dump shows nodes at 7, the three writers and four other threads that wrote meanwhile. The root reads as two zeros. The kernel copies a map value out around its lock and root (bpf_obj_memcpy() in include/linux/bpf.h), and the nodes are not in the map at all.

To read the counts, user space runs a program of its own, drain, a syscall program that takes the nodes out in order, copies thread ID and count into a global array and frees them. All 3,000 writes were counted.

The arena version, c_arena.bpf.c, keeps the same counts in the hash table of the v7.2 selftests, bpf_arena_htab.h with its allocator bpf_arena_alloc.h, whose buckets and elements live in an arena of 1,024 pages. shows what changes from outside. bpftool reports the arena with a memlock of 0 bytes, and the loader has a 4 MiB shared mapping of it. The loader finds the table at an address inside that mapping and follows its pointers as any C program would, reading every count with no system call between the two markers that bracket the read. The same read made eight bpf() calls for the hash and one for the tree.

Two ways to own memory

The two versions sit at the two ends of a trade, and sets them beside the map they replace. An allocated object is memory that a program gets from bpf_obj_new() while it runs, typed by the program's BTF. The verifier knows the type of every pointer to it and who must give it back, so a mistake is a refusal at load time. The price is a lock around every collection, and memory that only programs can reach.

An arena gives the program plain pages to address as C would, and user space maps the same pages. The verifier stops knowing what any byte means, so a mistake becomes a wrong count, or a report in a log, at run time.

What the verifier knows about an object

bpf_obj_new() is a kfunc that takes a type and returns a pointer to an object of that type, or NULL. The program names the type by its ID in its own BTF, and check_special_kfunc() in verifier.c records the type's size. bpf_fixup_kfunc_call() writes that size into the call's first argument, with a pointer to the type's list of special fields in the second. The kernel side, bpf_obj_new() in helpers.c, thus receives a size and never parses BTF.

Only the special fields, the lock, list and tree fields and their kin, are set up (bpf_obj_init()). A reused object keeps old bytes elsewhere, so the counter writes every field it later reads.

A type ID becomes a sizeThe counter's log shows r1 = 0x23 before the call, the BTF ID 35 of struct wnode. The fixup puts three instructions in front of the call: one loads 48, the node's size, into the first argument, and two load the address of its field record into the second.

From the call on, the verifier follows the result down every path. The pointer has type ptr_or_null_wnode with a fresh ID. Once the NULL check passes it is an owning reference, a pointer through which the program may read and write any field without a lock and which it must give away before it exits.

draws the three ways. bpf_obj_drop() frees the object, bpf_kptr_xchg() parks it in a map value, and bpf_rbtree_add() or a list push links it into a collection. If a path reaches the exit while the ID is still held, check_reference_leak() refuses the whole program with "Unreleased reference id=2 alloc_insn=2". The alloc_insn is the instruction that allocated the object.

Linking is the interesting case. When bpf_rbtree_add() returns, check_kfunc_call() turns every register that held the object's ID into a non-owning reference. Through it the program may still read and write the node's ordinary fields, but it can neither free the node nor add it again. shows the change in a log. Register R7 goes from ptr_wnode(id=3) to ptr_wnode(non_own_ref), and the held references drop from refs=3,1, the object and the lock, to refs=1, the lock alone.

When bpf_spin_unlock() runs, process_spin_lock() invalidates every non-owning reference, since from then on another program may remove the node and free it, so a write through R7 after the unlock is refused.

Lists, trees and the lock that guards them

The lock is how the verifier makes a collection safe without knowing what other programs do. At every list or tree call, __process_kf_arg_ptr_to_graph_root() checks that the program holds the bpf_spin_lock in the same allocation as the root. Otherwise it refuses with "bpf_spin_lock at off=0 must be held for bpf_rb_root". While the lock is held the program may call only the collection's own kfuncs, bpf_kptr_xchg() and the unlock. do_check_insn() refuses anything else, bpf_obj_new() included, with "function calls are not allowed while holding a lock", which is why the counter allocates before it locks.

The lock itself turns off interrupts on this CPU and takes a queued spin lock (__bpf_spin_lock_irqsave() in helpers.c). Every other CPU that wants the tree waits.

A tree helps the counter only if it can be searched. bpf_rbtree_add() places a node by calling the program's less() back at each level of the descent. Since Linux 6.16, bpf_rbtree_root(), bpf_rbtree_left() and bpf_rbtree_right() hand out non-owning references with which a program walks down from the root, one kfunc call per level, as the search in does. bpf_rbtree_first() gives the smallest node and bpf_rbtree_remove() takes a node out as an owning reference again. A list works the same way with bpf_list_head and bpf_list_node, pushed and popped at either end.

An object sits in one collection through each node field it has, and after the push the program's pointer to it is non-owning. Sometimes two collections must both own an object, for instance a tree by thread ID and a list of threads to report. Its type then adds a struct bpf_refcount. bpf_refcount_acquire() returns a second owning reference by raising the count, each owner pushes or drops its own, and __bpf_obj_drop_impl() frees the object when the count reaches zero. For a refcounted type the verifier also marks each non-owning reference as protected by RCU, the MEM_RCU flag (ref_set_non_owning()).

The counter never frees a node at fentry, and could not if it tried. In v7.2, check_kfunc_call() refuses bpf_obj_drop() in kprobe, tracepoint, perf-event and raw tracepoint programs, and in fentry and fexit programs that cannot sleep. It does so whenever the type holds a field that is unsafe in an NMI, such as a bpf_rb_node or a bpf_list_node, with the message "bpf_obj_drop cannot be used in tracing programs on types with NMI unsafe fields". The counter's nodes are freed by drain, a syscall program. A thread that exits keeps its node until then.

An object parked in a map value

A kptr is a pointer field in a map value that the map's BTF marks with __kptr, so that the verifier knows which type of object the field holds and that the map owns it. It lets an object outlive a run without joining a collection, and alloc.bpf.c in book/labs/memory parks 100,000 nodes in the slots of an array this way.

A plain store into the field is refused with "store to referenced kptr disallowed" (check_map_kptr_access()). The pointer already there would be lost, and the new one would have two owners. bpf_kptr_xchg() swaps the field and the program's pointer in one atomic exchange. The map owns what went in, and the program owns, and must give away, whatever came out.

struct kslot { struct wnode __kptr *p; };   /* the value of an array */
    ...
    old = bpf_kptr_xchg(&v->p, n);           /* the slot owns n; we own old */
    if (old)
        bpf_obj_drop(old);

The same kind of field can hold an object that the kernel owns, such as a task from the acquire kfunc bpf_task_from_pid() of , under the same rule. What no program takes back out, the map frees. bpf_obj_free_fields() in syscall.c drops each kptr when its value is deleted or the map is freed, and it frees every node of a list or tree whose root sits in the value. The counter's tree goes when counts_tree goes.

Where the objects come from

A program at fentry or a kprobe runs in whatever context the probed function runs in, an NMI included, where calling kmalloc() may not be safe. bpf_obj_new() therefore takes its objects from the BPF memory allocator, kernel/bpf/memalloc.c. For every CPU it keeps a cache of free objects in eleven size classes from 16 bytes to 4 KiB, and it refills them from the kernel's slab caches in the background ().

An allocation turns off interrupts, takes the first object off this CPU's free list for the size class and turns them on again. It takes no lock and makes no call into the slab allocator. Every object carries an 8-byte header in front, so the counter's 48-byte node takes a 64-byte slot.

irq_work on the same CPU keeps each free list between 32 and 96 objects for classes up to 256 bytes. It allocates a batch when the list falls below and gives objects back above. A drop goes through bpf_mem_free_rcu(): the object waits on a list until an RCU grace period has passed, because another program may still be reading it, and only then can it be handed out again.

The measurements show both effects (alloc.txt). Allocating 100,000 nodes in a row cost 128 to 161 ns a node, the refill working all the while, and small batches of 32 took 32 to 520 ns a node, depending on what the free list held. Even 100,000 pairs of bpf_obj_new() and an immediate bpf_obj_drop() grew the kernel's 64-byte slab caches by 59,000 to 98,000 objects during the run.

These objects belong to no loader. The allocator behind bpf_obj_new() serves the whole kernel and was set up at boot (bpf_global_ma_init() in core.c). When the tree counter held 100,000 nodes, the kernel's 64-byte slab caches had grown by 97,440 objects, about 6.2 MB (mem.txt). The memory.current of the loader's cgroup had not moved, and bpftool's memlock for the program and the map counted none of it.

The arena: pages both sides map

An arena is a map of type BPF_MAP_TYPE_ARENA with no key and no value, whose max_entries counts pages, 4 GiB worth at most, and which must be created with BPF_F_MMAPABLE (arena_map_alloc() in arena.c). Creating one allocates almost nothing: the kernel reserves 4 GiB of its own addresses plus a 64 KiB guard, and fills in the page tables above the last level. User space gets a range of its address space when the loader maps the arena, at an address that map_extra may fix in advance. Two more flags change what a user fault and a pointer cast do. arena_map_mem_usage() returns 0, the memlock of 0 bytes that bpftool printed.

Pages arrive one at a time, from either side. A program calls bpf_arena_alloc_pages(), which takes a free range from the arena's range tree, allocates pages and maps them into the kernel's range (arena_alloc_pages()). Or user space touches an address in its mapping, and arena_vm_fault() puts a page there, unless a program reserved the address or the arena was made to fault. Either way the page is charged to the memory cgroup of the process that created the arena.

Since Linux 7.0 the allocation also works in a program that cannot sleep, such as the counter at fentry. The verifier calls bpf_arena_alloc_pages_non_sleepable() instead, and a free from such a program is finished later on a workqueue (commit b8467290edab).

What makes an arena more than shared memory is that one pointer means the same page on both sides. The compiler marks arena pointers with address_space(1), the __arena of bpf_arena_common.h, and every conversion between that space and the kernel's becomes an address space cast, an instruction of its own. A cast into the kernel's space gives the register the type arena (check_alu_op()) and keeps the low 32 bits of the user address. The JIT adds the base of the kernel's range, kept in register r12, to every load and store. A cast back puts the upper 32 bits of the user mapping's address above the low ones.

follows one page. The table that user space found at 0x7f5cac7d3fe8 is 0xac7d3fe8 to the program and kern_vm_start plus 0xac7d3fe8 to the kernel, so a pointer that the program stores in user form is one that user space follows unchanged.

Where the globals golibbpf places a program's __arena globals in the last pages of the arena. A test store to the arena's last page, meant to hit an unallocated page, wrote into bpf_arena_alloc.h's per-CPU state instead, and no fault was reported.

What the verifier gives up in an arena

The verifier's whole view of an arena is one register type. check_mem_access() lets a program load and store through a pointer of type arena at any offset, and adjust_reg_min_max_vals() allows any arithmetic on it. A value loaded from the arena is an unknown scalar, whatever was stored there.

It is the first limit Emil Tsalapatis raised when he reported on arenas in sched_ext schedulers at LSFMM+BPF in May 2025: a kernel pointer stored in an arena cannot be used once it is read back. shows it in v7.2. The store of a trusted task pointer is accepted, the load gives scalar(), and following it is refused.

The second limit follows from the first. A helper that takes memory accepts a pointer to the stack, a map value, a packet and a few other kinds, and an arena pointer is none of them. Given an arena buffer, bpf_get_current_comm() is refused with "R1 type=arena expected=fp, pkt, pkt_meta, map_key, map_value, mem, ringbuf_mem, buf, trusted_ptr_, ctx" (check_reg_type()). Data bound for a helper goes through the stack, the clumsiness Tsalapatis described.

A function written for both kinds of pointer meets the third limit, because the verifier types an arena pointer and a stack pointer differently. The scheduler authors kept two copies of such a function or inlined it, so that the verifier typed each call site on its own. Alexei Starovoitov answered that work was in progress, and that letting the verifier mix the two kinds of pointer was hard.

The rest of an arena's safety is the program's job. The selftests' hash table takes no lock, so two CPUs inserting into one bucket at once could lose an element. The counter's threads fell into different buckets and lost no count in bench.txt, and bpf_arena_spin_lock.h in the selftests' libarena supplies a lock built in arena memory for structures that need one.

A load or store at an address with no page behind it is caught by the JIT's exception table (ex_handler_bpf() in the x86 JIT). The load gives 0, the store is skipped, and the program continues with a wrong value. Since Linux 6.18 the kernel also writes a report into the program's BPF stream, a per-program log that user space reads with bpftool prog tracelog stderr or bpf_prog_stream_read(), as the second half of shows.

Eighteen months after the session, sets each point against v7.2. The two limits on programs stand, and the error stream has landed. What moved is the kernel's side. Since Linux 7.2, kernel code that is handed an arena pointer may read and write through it, because a fault there installs a scratch page and is reported to the program's stream (commit dc11a4dba246). sched_ext uses it to place its own data in a scheduler's arena (kernel/sched/ext/arena.c), and the next chapter, on sched_ext, meets arenas inside schedulers.

Inside the v7.2 source

The mechanisms of this chapter live in four files of kernel/bpf and one of the x86 JIT, and lists them in the order the counter meets them. The kfuncs and the collections are in helpers.c, the allocator in memalloc.c, the rules in verifier.c and the arena in arena.c; where a function holds one of the checks met above, the table also gives the check's own line.

What the counter pays

Each version of the counter ran with one writer pinned to a CPU, making 2,000,000 one-byte writes to /dev/null by the method of . It ran again with 1,000 made-up threads already in the structure, and with eight writers on eight CPUs (). With one writer and a small tree, the tree's lock and kfunc calls cost about 23 ns a run more than the hash. The arena, whose lookup is plain loads and one atomic add, cost 21 ns less. A thousand more nodes made the tree's search deeper and added 45 ns a run, while the hash and the arena did not move.

Eight writers show what one lock per collection means. Each of them takes the tree's single bpf_spin_lock on every write, a lock that costs 31 to 32 ns uncontended (lock_pair in alloc.txt). They queue for it: a run took 817 ns, seven and a half times the single-writer cost, and each write slowed from 418 to 1,298 ns on the clock. The hash updates each count with an atomic add in place and locks a bucket only to insert, and the arena hash takes no lock at all, so both stayed within a few nanoseconds of their single-writer cost. The host's cores also run slower when eight are busy, as measured, which inflates all three eight-writer numbers alike.

Allocation is the other cost, paid once per thread. A tree node came from the BPF allocator in 128 to 161 ns over a long run, and taking one back out of a kptr slot and dropping it took 26 to 32 ns. An arena page cost 0.7 to 3.5 µs to allocate in a syscall program and 5.7 to 6.1 µs to free. Freeing also removes the page from the kernel's range and from every user mapping (arena_free_pages()). A 32-byte element from bpf_arena_alloc.h's page-fragment allocator took 6.5 to 7.7 ns, since a page is needed only once per 127 elements.

What it costs

CPU
Per run at fentry/vfs_write, one writer: hash 85.5 ns, tree 108.1 (153.1 with 1,000 threads in it), arena hash 64.3. A node from bpf_obj_new() 128 to 161 ns, an arena page 0.7 to 3.5 µs, an arena element 6.5 to 7.7 ns (kernel 7.2.15, 16-CPU VM, 13 November 2026; book/labs/memory-root.sh).
Memory
Tree: 64 bytes of slab a thread, charged to no loader's cgroup and absent from memlock. Arena: about 33 bytes a key, charged by the page to the creator's cgroup, memlock 0. Hash: 82 bytes an entry, from creation.
Switches
Reading all counts: a bpf() call per key for the hash, one program run for the tree, none for the arena.
Locking
One spin lock per tree with interrupts off, 31 to 32 ns alone; eight writers took 817 ns a run. The arena hash has no lock, and its inserts race.

Keep a map while a slot per key will do. Allocate objects when the program needs links, order or ownership that the verifier should check, and keep each collection off paths that many CPUs take at once. Use an arena for large, pointer-rich structures that user space reads without system calls, and take on their locking, bounds and stack copies.

When it goes wrong

The first ten rows are refusals at load. The verifier log names the instruction in each, so the work is reading the register types on the lines before it. The first seven concern the hook, ownership and the lock: which program types may hold a tree at all or free a node, who owns an object at each point, and where the lock is held. The next three are the arena's single type showing through. No helper accepts its pointer, a kernel pointer loads back as a number, and a program that never named its arena may not cast.

The last three rows load and run. An arena access with no page behind it passes the verifier and returns 0. The program's stderr stream is the only witness, and bpftool reads it while the program is loaded. A tree that slows down with more CPUs, and memory that no cgroup seems to pay for, are the costs of the previous section seen from outside; run_time_ns, /proc/slabinfo and memory.current tell them apart.

Recap

A program can allocate memory in two ways. bpf_obj_new() gives an object typed by the program's BTF from a per-CPU cache of the BPF memory allocator, and the verifier follows it as an owning reference that every path must drop, park in a kptr field with bpf_kptr_xchg(), or link into a list or red-black tree under the lock in the root's allocation, after which it is a non-owning reference until the unlock. Tracing programs may allocate nodes but not free them, and nodes cost 64 bytes of slab that no loader's cgroup pays for. An arena is a map of pages that the program, the kernel and user space address with one 32-bit offset, so user space reads a structure the program built with no system call; the verifier keeps only the type arena, so kernel pointers load back as numbers, helpers refuse arena pointers, a stray access reads 0 and is reported in the program's stderr stream, and locking is the program's job. For the write counter the arena hash cost 64 ns a run and the hash 86, while the tree, whose every run takes the same lock, cost 108 with one writer and 817 with eight.

About 64,000 bytes, and no loader's cgroup pays. Each node is 48 bytes, a 32-byte bpf_rb_node, the thread ID, padding and the count; the BPF memory allocator puts an 8-byte header in front and serves 56 bytes from its 64-byte class, which the kernel's 64-byte slab cache backs. The allocator behind bpf_obj_new() was set up at boot, so the loader's memory.current does not move: for 100,000 nodes the slab grew by 97,440 objects and the cgroup by nothing (mem.txt). Counting 48 bytes a node, or looking at memlock, misses both the header and where the memory is charged.

A BTF tracepoint is a tracing program that cannot sleep, and v7.2's check_kfunc_call() refuses bpf_obj_drop() there, as at fentry, when the type holds a field that is unsafe in an NMI; a bpf_rb_node is one. The removal itself is allowed, so the program can take the node out under the lock and add it to a second tree of nodes to free in the same map value. A syscall program that user space runs, as the counter's drain is, or a sleepable program then drops them. Moving to the classic tracepoint makes it worse: there the map cannot even be named.

No. When the kernel copies a map value out to user space it copies around the special fields, the lock and the root (bpf_obj_memcpy() in include/linux/bpf.h), so those bytes always read as zeros, and the nodes are separate objects that the map does not contain. The counter's own nodes field, an ordinary u64 it updates under the lock, is what reports seven. To see the counts, run a program that walks or drains the tree, as drain does. Taking the zeros as an empty tree is the mistake here.

The tree took 817 ns a run and the hash 88.5 (bench.txt). Every run of the tree counter takes the tree's single bpf_spin_lock, with interrupts off, so eight CPUs queue for one lock on every write, and the wait is counted in run_time_ns. The hash finds each thread's slot without a lock and adds with an atomic instruction in place, taking a bucket lock only to insert a new thread, so eight writers on eight keys barely touch each other. Expecting the tree's cost to grow with its depth alone misses the lock.

The verifier types arena memory as plain bytes: check_mem_access() marks any value loaded through a pointer of type arena as an unknown scalar, so the task pointer comes back as a number and following it is refused. Storing it was accepted because a privileged program may write a pointer's value anywhere, which gives the colleague a false start. Keep in the arena what the kernel will not need to trust, the thread ID or an index, and keep the referenced task in a kptr field of a map value, found by that index, as the sched_ext authors described doing in 2025.

In the arena's pages, charged to the memory cgroup of the process that created the arena, about 3.3 MB: 100,000 keys cost 3,338,240 bytes of memory.current, 33.4 bytes a key, for 32-byte elements packed 127 to a page (mem.txt). arena_map_mem_usage() in arena.c returns 0, so memlock says nothing about an arena, however full. Reading memlock as the arena's size, as one can for a hash, gives the wrong answer; memory.current of the creator's cgroup, read before and after, gives the right one.

The selftests' hash table picks a bucket by the key's low bits, 1,024 buckets, so the two threads land in one bucket, and htab_update_elem() links a new element at the head of the bucket's list with no lock. Both CPUs can read the same old head and each write its own element in front of it, so one element is lost and its thread is counted again from 1 later. The verifier checks that arena accesses go to the arena and nothing about what they mean, so a race in arena memory loads cleanly. A lock in arena memory, such as the selftests' arena spin lock, would close it.

A drop does not hand the memory back at once. bpf_obj_drop() frees through bpf_mem_free_rcu(), which puts the object on a waiting list until an RCU grace period has passed, since another program may still hold a pointer to it, so the next bpf_obj_new() cannot reuse it and the CPU's free list runs down. irq_work then refills the list with batches from the slab, which grew by 59,000 to 98,000 objects during 100,000 such pairs (alloc.txt). Expecting a free list to recycle the same object, as a simple cache would, is the trap.

address space cast
the instruction that converts a pointer between the arena's user form and the program's 32-bit form
allocated object
memory a program gets from bpf_obj_new() while it runs, typed by the program's BTF
BPF memory allocator
the kernel's per-CPU caches of free objects behind bpf_obj_new(), safe in any context
BPF stream
a per-program log, stdout or stderr, that programs and the kernel write and user space reads
kptr
a pointer field of a map value, marked in BTF, that owns the object it points to
non-owning reference
a pointer to a node in a collection, usable for its ordinary fields until the collection's lock is released
owning reference
a pointer to an allocated object that the program must drop, park or link before it exits
red-black tree
a binary search tree kept balanced by recolouring and rotating nodes, so that a lookup takes about 2 log₂ n steps at most
