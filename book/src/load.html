Into the kernel: bpf(), the load path, and who holds what

The write counter's loader creates two maps and a program through one system call, and the kernel hands back a descriptor for each and counts everyone who holds them. Given only CAP_BPF, the same loader creates both maps and is then refused the program with an empty log, because the line that refuses it runs before the program is checked at all.

What the loader asks the kernel

We start with the loader run without sudo, whose failure in shows the shape of every request. The loader reaches the kernel through a single call, the bpf() system call, whose first argument names a command such as BPF_PROG_LOAD and whose second points to that command's attributes in a union bpf_attr. Linux 3.18 added it, with maps, in December 2014.

The first programs in the trace are not the counter. They are two instructions long, and libbpf loads them first to ask whether this process may load at all. On our test kernel kernel.unprivileged_bpf_disabled is 2, so only a privileged process may load, and each probe comes back with EPERM.

With sudo the probes pass. The trace of the same loader then holds 33 calls before its read loop starts, eight of them BPF_PROG_LOAD and five BPF_MAP_CREATE, and only one and two of those belong to the counter. The rest are libbpf asking what this kernel supports, along with BPF_BTF_LOAD calls that hand over the types described. picks the counter's own calls out of that trace.

Root is more than a loader needs, so we run the counter's loader the way a careful deployment would, as an ordinary user that holds one capability, CAP_BPF, which Linux 5.8 added in 2020 (commit a17b53c4a4b5) so that loading BPF would not need the rest of root's powers. shows the result on kernel 7.2.15 in a virtme-ng VM. Both maps are created, and then the program is refused twice with -EPERM: libbpf loads once without a log and, after the failure, once more with a 16 MB log buffer so that it can print the kernel's reasons.

The buffer comes back empty, and libbpf has nothing to print. Something refused the program before the kernel had begun to check it, and to find the line that did, we first follow a load that succeeds, from the loader's side and then through the kernel's source.

Load: the maps first, then the program

With sudo, the loader calls hashmap_bpf__open_and_load(), as shows, from the skeleton, a header that bpftool gen skeleton wrote from the counter's object, with the object inside it as bytes. Open parses those bytes, and load creates everything in the kernel, each map with BPF_MAP_CREATE and then each program with BPF_PROG_LOAD.

A map is a kernel object of keys and values that programs and user space both read and write, and the loader knows each one by the file descriptor that BPF_MAP_CREATE returned. libbpf writes that number into every wide instruction that named the map, the zeros at slots 6 and 21 of (bpf_object__relocate_data(), libbpf.c line 6434). It also sets the instruction's source-register field to 1, BPF_PSEUDO_MAP_FD, which marks the constant as a descriptor.

Numbers before mapslibbpf 1.8, the version used in this book, picks each map's number before the map exists. At open it reserves a descriptor per map and patches the instructions with it, and when BPF_MAP_CREATE returns, it moves the real map onto that number with dup3().

The object also holds a map the source never declares, the read-only hashmap_.rodata, which holds bpf_printk's format string and which slot 13 points into. BPF_PROG_LOAD then carries the program type, BPF_PROG_TYPE_TRACEPOINT, the kind of program, which fixes what it receives when it runs and which helpers it may call, and all 27 slots. The kernel checks every path through the program, which follows, and swaps each descriptor for the map's address, as the comment above check_and_resolve_insns() promises: "if it accesses map FD, replace it with actual map pointer". It then hands back a descriptor for the program, which is loaded and yet runs nowhere.

"In the load phase, libbpf creates BPF maps, resolves various relocations, and verifies and loads BPF programs into the kernel. At this point, libbpf validates all the parts of a BPF application and loads the BPF program into the kernel, but no BPF program has yet been executed."

libbpf Overview, "BPF App Lifecycle and libbpf APIs", Linux kernel documentation

Running is the second half of . hashmap_bpf__attach() opens a perf event on the tracepoint and joins the program to it with BPF_LINK_CREATE, which returns a link (a bpf_link in the kernel's terms since Linux 5.7), an object whose job is to hold one program on one hook. How the loader finds the hook, and what attaching writes into it, is the subject of , and for the rest of this chapter the link matters as one more holder of the program.

From the system call to a descriptor

The kernel's side begins at SYSCALL_DEFINE5(bpf), line 6534 of kernel/bpf/syscall.c; in v7.2 the call has five arguments, the last two for attributes that every command shares. __sys_bpf() copies the attributes in, returns -E2BIG for any nonzero byte beyond the size this kernel knows, lets each Linux Security Module (LSM) see the command through security_bpf(), and calls bpf_prog_load() at line 2972. lists what that function does next, and the row in bold is where our loader stopped.

After CHECK_ATTR has rejected unknown fields, the capability tests run, in the user namespace of a BPF token if the caller passed one. A token is an object made from a mount of the BPF file system that was set up to delegate chosen commands and kinds of program into a user namespace, and with one, bpf_token_capable() checks capabilities in that namespace instead of the initial one. Every kind of program except socket filters and cgroup skb programs needs CAP_BPF, and a kind that can read kernel memory, a tracepoint program among them, also needs CAP_PERFMON (is_perfmon_prog_type(), line 2871). Our loader stopped at line 3045, the test for CAP_PERFMON.

libbpf asks firstBefore its probes, libbpf tried bpf(BPF_TOKEN_CREATE) on /sys/fs/bpf and got EOPNOTSUPP: token.c line 151 refuses a token in the initial user namespace, where it would add nothing. With no token, every check used the initial namespace.

shows that stop with ftrace's function_graph tracer, which records each function that bpf_prog_load() calls. The refused load asks bpf_token_capable() twice, gets true for CAP_BPF and false for CAP_PERFMON, and returns -1, which is -EPERM, after 3.5 µs. As root, the same load passes both tests and runs to the end in 146 µs.

The steps after the capabilities build the program object. bpf_prog_alloc() takes memory charged to the caller's memory cgroup, the 27 slots and the license string are copied in, and license_is_gpl_compatible() decides whether GPL-only helpers may be called. A signed program, possible since 6.18, has its signature checked here, and security_bpf_prog_load() at line 3192 lets every LSM refuse, including BPF programs that are themselves attached to that security hook.

bpf_check() is the check that walks every path through the program, the subject of , and the first thing it does with the caller's buffer is set up the log, in bpf_vlog_init(), 52 lines into the function. Every refusal before that point reaches user space as an errno with an empty log, which is the symptom of . Inside, the kernel also reads the BTF, func info and line info that clang wrote, replaces map descriptors with map pointers, records the maps the program uses in prog->aux->used_maps, walks the program, and ends by calling __bpf_prog_select_runtime(), which compiles it to x86 code ().

Back in bpf_prog_load(), bpf_prog_alloc_id() gives the program the ID that bpftool prints, and bpf_prog_kallsyms_add() names its machine code in /proc/kallsyms. bpf_prog_new_fd() at line 3227 then returns a descriptor for an anonymous inode, a file with no path that the kernel creates to hand an internal object to a process; /proc/PID/fd shows it as anon_inode:bpf-prog.

Each map took a shorter road through the same file before the program did. BPF_MAP_CREATE reaches map_create() at line 1626, where map_create_alloc() checks the attributes and the capabilities and asks the map's own operations to allocate it. On our kernel, with unprivileged BPF off, every map needs CAP_BPF and the socket and device maps need CAP_NET_ADMIN as well, while no step asks for CAP_PERFMON, which is why the loader of got both of its maps. The LSMs then see the new map in security_bpf_map_create(), bpf_map_alloc_id() gives it an ID, bpf_map_save_memcg() records the memory cgroup it is charged to, and bpf_map_new_fd() returns a descriptor that shows as anon_inode:bpf-map.

Who holds the program, its maps and its link

Every object in counts the references held on it. Each holder is one unit of a reference count, an atomic64_t refcnt in the object, and the object is freed when the count reaches zero. While the counter runs, the program has three: the loader's descriptor, the link, and the perf event, for which bpf_perf_link_attach() takes a reference of its own (bpf_prog_inc(), line 4337, under the comment that perf_event_set_bpf_prog() takes none). Each map has two, the loader's descriptor and the program's used_maps.

Nothing but the loader, or a pin, holds the link. When the loader exits, its descriptors close and the counts fall until the link goes, which detaches the program, and then the program and its maps are freed, in an order that measures step by step.

An object can also outlive every process. Pinning gives it a file name in bpffs, the BPF file system that Linux 4.4 added, which our test machine mounts at /sys/fs/bpf. The file holds a reference of its own, so sudo bpftool link pin id ID /sys/fs/bpf/wc keeps the counter counting after the loader exits, sudo rm /sys/fs/bpf/wc stops it, and bpf_link__pin() does the same from C. In the kernel, BPF_OBJ_PIN reaches bpf_obj_pin_user() in kernel/bpf/inode.c, which takes a reference through the descriptor it is given and leaves it with the new inode until bpf_destroy_inode() gives it back.

Who holds a map, and how two programs share one

shows two programs from two objects, loaded by two bpftool processes, that both name map 2. The second, forget_thread, deletes a thread's count when the thread exits, which keeps 's hash from filling with threads that are gone. After twenty short-lived writers the map held 4 entries, and 25 once forget_thread was unloaded.

Within one object, libbpf creates each map once and writes its descriptor into every program that names it. Across objects, both definitions ask for LIBBPF_PIN_BY_NAME, so the first loader pins the map at /sys/fs/bpf/write_counts and the second reuses it after map_is_reuse_compat() has compared type, key and value sizes, max_entries and flags. At load, bpf_check() records the map in the second program's used_maps through __add_used_map(), at most 64 maps a program, and takes a reference, so that the map now counts two programs among its holders.

lists the holders behind a map's two counts. refcnt counts every holder, while a descriptor or a pin also takes a user reference, counted in usercnt. When the last user reference goes, bpf_map_put_uref() calls the map's map_release_uref, which hashes and arrays use to stop the timers and workqueues in their values. When the last reference of any kind goes, the map is freed.

A second process can also reach a map without loading anything. BPF_OBJ_GET opens a pin and returns a new descriptor, and BPF_MAP_GET_FD_BY_ID turns the ID that bpftool prints into one, for a caller with CAP_SYS_ADMIN (bpf_map_get_fd_by_id()). Either way the new descriptor adds one to both counts. The map then stays until that process closes it, even if every program and pin is gone.

Why one kind of array emptiesAn array whose slots hold programs, which uses to jump from one program into another, empties every slot when its last user reference goes. A slot holds a reference to its program, and that program may hold the array in its used_maps, so programs that jump into each other could hold each other forever. Emptying the slots when user space lets go breaks every such cycle (commit c9da161c6517, Daniel Borkmann, 2015).

What frees each of them

follows the counts when the loader is killed. Closing the link detaches the program from the tracepoint, and perf_event_detach_bpf_prog() sleeps about 25 ms in synchronize_rcu_tasks_trace() before it drops its reference, because a CPU may still be running the program. When the last reference goes, bpf_prog_put_deferred() frees the ID at once and passes the memory to call_rcu(), which frees it only after an RCU grace period, the time it takes every CPU to leave any read-side section that could still see the program.

Freeing the program is what releases the maps. bpf_prog_free_deferred() runs in a kworker and puts each map in used_maps, and a map whose count reaches zero is freed in another kworker, from the work that bpf_map_put() queues; write_counts was gone 34.6 ms after the signal.

A pin moves the start of that chain. With the link pinned, nothing happens when the loader exits, and the same sequence begins only when the pin is removed and bpf_destroy_inode() drops the pin's reference; bpf_link_put() hands a last reference to a workqueue, so the teardown then runs in a kworker. A pinned map outlives its programs in the same way, and write_counts, pinned by name in , stayed while its pin existed after both programs were gone and was freed a second after the pin was removed.

Each kind of object therefore waits for its own last holder. A link goes with its last descriptor or pin and takes the program off its hook as it goes; a program goes once its descriptors, links, perf events and pins have all let go, and only then releases its maps; a map goes when the last of its descriptors, pins and programs has let go.

What it costs

CPU
Kernel 7.2.15 in a throwaway VM, November 2026. The BPF_PROG_LOAD that checks the counter's 27 slots took 0.29 to 0.37 ms of system-call time in five runs and 0.48 ms in another (strace -T), and the whole start-up, 33 calls with libbpf's feature probes, under 3 ms of kernel time. function_graph put 107 µs of a 146 µs load in bpf_check(), which processed 36 instructions (verified_insns in fdinfo); a refused load costs 3.5 µs.
Memory
Charged, with one exception that measures, to the memory cgroup of the process that creates each object (bpf_map_save_memcg(), kernel/bpf/syscall.c): a 4,096-byte page for the program, 83,968 bytes for write_counts, whose 1,024 entries exist from creation, and 336 for .rodata. The object's BTF stays loaded at 1,502 bytes, and the program's x86 code takes 152.
Switches
One system call per command at load and none per event. Teardown runs in the exiting process, an RCU callback and two kworkers, and the exiting loader sleeps about 25 ms in synchronize_rcu_tasks_trace().
Locking
Reference counts are atomic, so a holder comes or goes without a lock. IDs come from an IDR under prog_idr_lock, and bpf_check() takes the global bpf_verifier_lock only for loads without CAP_BPF, so privileged loads are checked in parallel.

Load once at start-up and keep the descriptor or a pin, since every reload pays for a check and a teardown with two grace periods. Count the holders, because any extra one, a pin, a copied descriptor or another map that holds the object as a value, keeps the program running and its memory charged after the loader exits: pin a shared map by name, and remove the pins nothing needs.

When it goes wrong

Most failures of a load show up as an errno and a line from libbpf, and pairs each one this chapter met with its usual cause and the command that tells it apart. The first four rows are about getting in: three refusals, and a trace that hides the counter's own load among libbpf's probes. An -EPERM that arrives with an empty log came from a test in bpf_prog_load() that ran before bpf_check() set up the log, the sysctl or a capability, while a refusal that comes with a log came from the check itself, which the next two chapters read. An -EACCES after the program loaded belongs to attaching, and here to the permissions of tracefs.

The capability rows decide how a loader is deployed. Run in the initial user namespace, a tracing loader needs only CAP_BPF and CAP_PERFMON, and the counter's maps need only CAP_BPF. A loader in a container with its own user namespace holds its capabilities only there, while the tests look in the initial namespace, so it needs a BPF token from a bpffs mount that delegates the commands and kinds of program it uses. A token is no use outside such a namespace, since token.c refuses to create one in the initial namespace.

The other rows are about holders. A program that runs when it should have stopped, or stops while it should still run, raises one question, which reference is left, and the answer is always among the holders of and : a descriptor in some process, a link, a pin or a program's used_maps. bpftool lists the objects, ls /sys/fs/bpf lists the pins, and the probes of show the order in which the kernel lets go.

One step of the load has stayed closed in this chapter. bpf_check() spent 107 of the counter's 146 µs processing 36 instructions on its two paths, and a load that it refuses comes back with a log in place of an empty buffer. opens that step and follows the counter through it.

Recap

Everything the loader does in the kernel goes through the bpf() system call, driven by libbpf: load creates the maps, writes their descriptors into the wide instructions and loads the program, which the kernel checks and rewrites with real map addresses, and attaching then makes a link that holds the program on its hook. BPF_PROG_LOAD enters at SYSCALL_DEFINE5(bpf), and bpf_prog_load() checks the attributes, a token, the capabilities and the expected attachment, allocates and copies the program, checks the license and any signature, and asks the LSMs, all before bpf_check() creates the log, so a refusal there leaves the log empty. bpf_check() records used_maps, walks the program and compiles it; then the program gets an ID, a kallsyms name and an anonymous-inode descriptor. Descriptors, links, perf events, pins and used_maps are reference counts, a map also counts the user references of its descriptors and pins, and libbpf shares a map between objects by pinning it by name and reusing it when the definitions match. The last put frees the ID at once and the memory only after RCU grace periods, the program first and its maps after it.

The two maps are write_counts and hashmap_.rodata, the read-only map that holds bpf_printk's format string, and grep map_name= strace.txt finds them. The other three BPF_MAP_CREATE lines, and seven of the eight BPF_PROG_LOAD lines, are libbpf's feature probes (run on kernel 7.2 with libbpf 1.8). Two slips are common here: answering 24, which counts instructions where the kernel counts slots, and answering one map, because the .rodata map is easy to forget.

Three for the program and two for each map. count_writes is held by the loader's program descriptor, by the link that BPF_LINK_CREATE made, and by the perf event, for which bpf_perf_link_attach() calls bpf_prog_inc() (syscall.c line 4337, under the comment that perf_event_set_bpf_prog() takes none of its own). write_counts is held by the loader's map descriptor and by the program's used_maps. The bpftrace probes of print refcnt 3 on the program and refcnt 2 on each map. It is tempting to say two for the program, one per descriptor; the perf event's hidden reference is why the detach must drop one too.

The program was loaded and never attached, so it has never run. Load only creates the program, which runs once a link holds it on its hook, and sudo bpftool link show lists no link whose prog_id is the ID of count_writes. The usual cause is a loader that calls open_and_load() and skips attach(), or ignores the error attach() returned, for example for a tracepoint name that tracefs does not know. Suspecting a bug in the program leads nowhere, since a program that loaded has passed the kernel's checks and this one updates the map on every run, so an empty map means no run at all.

The program loaded; attach failed, in user space, before any attach call reached the kernel. With CAP_PERFMON the test at line 3045 passes and BPF_PROG_LOAD returns a descriptor. libbpf then needs the tracepoint's number and opens /sys/kernel/tracing/events/syscalls/sys_enter_write/id, and tracefs is mode 0700 for root, so openat() fails with EACCES and perf_event_open() is never called. strace -e trace=bpf,openat shows both: insn_cnt=27 … = 9, then the refused openat. Grant read access to tracefs or attach from a process that has it. A common mistake is to look for a third capability in bpf_prog_load(); the load had already succeeded.

The pin holds the map, and nothing holds the program. When the loader exits, its descriptors close, the link detaches the program, and the program's count reaches zero; freeing it puts each map in used_maps. write_counts drops from three holders (descriptor, used_maps, pin) to one, the pin's inode, which keeps it until bpf_destroy_inode() runs on rm. Nothing writes to it, so the counts stay where they were, and bpftool prog show name count_writes prints nothing. It is easy to assume that pinning the map keeps the program running; for this program only a pinned link does that.

libbpf found the pin and compared the existing map with the new definition, and max_entries differed. map_is_reuse_compat() in tools/lib/bpf/libbpf.c reads the pinned map's info and requires the same type, key size, value size, max_entries, flags and map_extra; any difference refuses the load, since the kernel cannot resize a map. The ways out are to make the definitions agree, or to remove the pin so that the next loader creates a new map, which loses the counts and leaves the running counter on the old one. Suspecting the new program is natural, but libbpf creates or reuses every map before it loads any program, so the kernel never saw forget_thread.

What this shows. Load is the two maps and the 27-slot program, and attach is perf_event_open and then BPF_LINK_CREATE, several calls later. The first BPF_LINK_CREATE, with target_fd=-1, is libbpf checking that this kernel has perf links; the second is the counter's, and returns the link as descriptor 11. After pkill the pin held the link, so the program kept counting, and each bpftool run is a new process whose own writes add a key. Removing the pin dropped the last reference, and the link, the program and both maps went with it.

Common wrong turn. Taking every BPF_PROG_LOAD in the trace for the counter's, when only the load with 27 slots is. The other is pressing Ctrl-C: this loader's read loop never checks the flag its signal handler sets, so it keeps running, and its bpf() calls fill the trace.

Removing the pin starts the chain in a kworker, because bpf_link_put() defers to a workqueue, and the program is freed about 7 ms after its last reference, the maps right after it.

What this shows. The pin's inode is one more reference on the link; while it exists the link holds the program and the program holds its maps, with no process involved. The waits are the same as for the killed loader, a tasks-trace grace period in the detach and an RCU grace period before the free.

Common wrong turn. Pinning the program instead of the link: the program stays loaded but is detached when the loader's link closes, so the counts stop.

anonymous inode
a file with no path that the kernel creates to give a process a descriptor for an internal object
bpf() system call
the single system call through which user space creates and controls BPF objects; its first argument is a command
BPF token
an object made from a delegating bpffs mount that lets a process in a user namespace pass the capability checks for the commands and types the mount allows; since 6.9
bpffs
the BPF file system, mounted at /sys/fs/bpf, where pins live
link
a bpf_link: a kernel object that holds one program on one hook; releasing it detaches the program
program type
the kind of program; it fixes what the program gets and may call
load
creating maps and programs in the kernel; nothing runs yet
pinning
giving a BPF object a file name, which holds a reference without any process
RCU grace period
the time it takes every CPU to leave any read-side section that could still see an object, after which the object can be freed
reference count
a counter in a kernel object with one unit per holder; the object is freed when it reaches zero
skeleton
the header bpftool gen skeleton writes: the object as bytes, plus open, load, attach and destroy functions
user reference
a reference held from user space, by a descriptor or a pin, counted in usercnt beside the map's ordinary reference count
