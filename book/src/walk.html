The verifier walks every path

Before a program runs once, the kernel follows every path through it and refuses it unless each one is safe. For the write counter that walk took 36 instructions and a fraction of a millisecond; a loop written the wrong way can take a million instructions and half a second, and still be refused.

What the kernel reports about its walk

The part of the kernel that follows every path through a program is the verifier, and it runs inside bpf_check(), the call that left unopened. We cannot watch it with a tracer, because it is one long computation inside one system call, but it can write a report. The verifier log is the text the verifier writes into a buffer that the loader passes with the load. The log level, a bit mask in the same request, says how much to write: 1 for each instruction walked, 2 for the full state at each one, 4 for statistics. We load the counter with a twenty-line libbpf loader that sets the level and the buffer itself, and shows what came back.

The last line matters most. processed 36 insns is the number of instructions the walk went through, counted every time it passes one, and the limit beside it is the budget that count may not exceed. total_states 2 says the walk saved its state twice along the way, peak_states 2 is the most it held at once, and max_states_per_insn 0 is the largest number of checkpoints it found at one instruction without a match among them. mark_read is still printed in v7.2, but nothing in the source sets it any more, so it reads 0 for every program.

The lines above it come only with level 4. The verification time, 146 µs here, is the clock of the whole of bpf_check() from its first line to its statistics (lines 19774 and 19980 of verifier.c), so it includes the setup and the rewriting around the walk. In fifteen loads over three VM runs it ranged from 99 to 551 µs, with a median of 156. The stack depth is 16 bytes, the two slots that hold the key and the value, and insns processed repeats the count for each function the walk verified on its own.

verified_insnsThe kernel keeps the count with the loaded program (verifier.c line 19982) and reports it in bpf_prog_info and in the descriptor's /proc/PID/fdinfo entry. bpftool v7.8.0 prints it in neither its plain nor its JSON listing.

The count is the counter's two paths. The level-6 log in ends the first path at the exit in slot 26. It then prints from 9 to 12, walks again from slot 12 and stops at slot 25 with the word safe. The first path is 24 instructions and the second 12, which add up to the 36 of the statistics line; the rest of this chapter explains why the walk went that way.

What the walk proves

The verifier's job is the promise that spells out as six things a loaded program never does, and if it cannot show all six on every path, the load fails and nothing runs. Only the last row is about time, and the check behind it is the plain count of the statistics line. The kernel will walk at most one million instructions, a number kept as BPF_COMPLEXITY_LIMIT_INSNS in include/linux/bpf.h next to the comment "yes. 1M insns". Until Linux 5.2 a program could have at most 4,096 instructions.

The page lagsThe kernel's verifier page still opens by saying that the first step disallows loops, which was true before 5.3. In v7.2, push_insn() in kernel/bpf/cfg.c refuses a backward jump only when the loader lacks CAP_BPF (lines 133 to 139).

The verifier works in two steps. The shape check looks at every jump once, making sure that none leaves the program and that every instruction can be reached. Then the walk starts at the first instruction and follows every path, a route from the start to an exit that takes one side at each branch.

The promise is about safety alone. The counter keys its map by thread ID, as pointed out, and the verifier has no opinion about that, because it checks what the program may touch and leaves what the program counts to its author.

Walking the counter

The counter has one branch, the test of r0 at slot 9, so it has two paths, and we follow both in . At each instruction the verifier updates its verifier state, which records for every register and stack slot what kind of value it holds.

After the lookup at slot 8, r0 is a pointer-or-NULL, a register that points at a map value or holds NULL without the kernel knowing which, so nothing may be read through it. At slot 9 the walk splits. On the fall-through side the test has shown that r0 is not zero, so r0 becomes a plain map value that slot 10 may read. The other side, where r0 is 0, cannot be walked at the same time. The verifier copies the whole state as it stands, notes slot 12 as the place where that side starts, and puts the copy on a stack.

That copy is a pending branch, a side of a conditional jump that the walk has kept for later, together with the state it must start from. The walk is depth first: it follows one path to an exit, then takes the most recent pending branch off the stack and follows it, and it ends when an exit is reached and the stack is empty. lists the counter's walk in those terms.

The second path starts at slot 12 and stops at slot 25, where the verifier saved its state on the first path, so it never reaches slot 26. The verifier compares the two states, finds that the saved one covers the new one in everything the rest of the program still uses, and treats the rest as already proved. Cutting a path short in this way is called pruning. The 36 of the statistics line are therefore 24 instructions on the first path, 11 on the second and one more for slot 25, counted when it is compared.

Why 25 and not 12Slot 12 is a jump target, so it could be compared too, but the first path saved no state there. The verifier saves one only after at least two jumps and eight instructions since the last save (bpf_is_state_visited() in kernel/bpf/states.c, v7.2), which on the counter's first path left slots 9 and 25.

What the kernel knows about one register

At level 1 or 2 the log lists, after each instruction, the registers that changed, in the form takes apart. The first word of an entry is the register type. A scalar is a plain number that may never be used as a pointer, while map_value points into a value inside a map. The second entry in the figure is the first without _or_null, because the test at slot 9 changed that one flag and left the rest of the entry as it was.

The rest of the entry is what the checks need. The value size, vs=8, is what every read through r0 is measured against, and id=1 is shared by every copy of this pointer, so that a test on one copy clears the NULL flag on all of them. A scalar carries bounds instead, which is how the kernel knows that the key read back at slot 12 lies between 0 and 0xffffffff; explains how it works out such bounds.

Checkpoints, and when two states are the same

The walk does not compare states at every instruction. During the shape check, kernel/bpf/cfg.c marks the places where a comparison can pay off, every conditional jump, the target of every jump and the instruction after every call, and only at those does do_check() call bpf_is_state_visited(). A checkpoint is a copy of the verifier state saved at such a place, kept in a list per instruction so that every later path reaching it can be compared with it. draws the three questions the walk asks there.

"For each new branch to analyse, the verifier looks at all the states it's previously been in when at this instruction. If any of them contain the current state as a subset, the branch is 'pruned' - that is, the fact that the previous state was accepted implies the current state would be as well."

Documentation/bpf/verifier.rst, section "Pruning", Linux v7.2

"Equal" is the wrong word for what the first question asks, although the function is called states_equal(). The comment above regsafe(), which compares one register, says it returns true "if (rold safe implies rcur safe)". A saved state covers the current one when it is at least as general, so that whatever the saved path proved for every value it allowed also holds for the narrower set of values the current path brings. A register that was never written in the saved state covers anything, because the path that went on from there never read it.

Only what is still to be read takes part. A register or stack slot is live at an instruction when some path from there may read it before writing it. In v7.2 the verifier works out the live registers of every instruction before the walk starts (bpf_compute_live_registers()), prints them at level 2 and compares only those. shows the counter's: at slots 12 and 25 no register is live, which is why the pending branch could drop r0 and why slot 25 matched whatever the two paths held. At each checkpoint clean_verifier_state() also forgets dead registers and stack slots in the current state, so that they cannot make two states look different.

For a scalar the comparison has a second side. Its range is compared only if some check further on depended on it, and the walk records that dependency as it goes, which is the subject of . A pointer must keep its type, flags included, so a pointer-or-NULL never stands in for a map value, nor the other way round.

The third question decides when to save. Saving a checkpoint at every prune point would cost memory and comparisons for little gain. The walk therefore saves one only when at least two jumps and eight instructions have passed since the last, a rule that the comment beside it credits with saving up to half the memory and a fifth of the time in the kernel's tests. A checkpoint that keeps failing to match is moved out of the list once its misses exceed three times its hits plus three, and a loader without CAP_BPF stops adding checkpoints at an instruction that already has more than 64.

Loops

A loop is a branch that jumps backwards, and the shape check sees it as a back-edge, a jump to an instruction that is still on its own path. Before Linux 5.3 every back-edge was refused. Since then the verifier accepts a bounded loop, one whose last round it can see, by walking it. Each round is a further stretch of the same path, with a new state, until the loop's test is decided as false and the walk goes on past it.

The second question of is the guard against a loop that never ends. When the walk reaches a checkpoint saved earlier on the same path, it may not prune against it, because that path has not reached an exit and has proved nothing yet. If the two states are identical in every register and slot, the loop has made no progress, and the verifier refuses the program with "infinite loop detected"; otherwise it goes round again. A counted loop changes its counter every round, so it is walked once per round, and the statistics grow with its bound.

The plain loop of costs eight instructions of walking per byte, the eight instructions of its body, plus 19 for the rest of the program, so sixteen times the bytes cost sixteen times the walking. Three later additions let a loop be proved without walking every round. Each one gives the walk a place where it may compare a state with one from an earlier round of the same path, and stop going round once the new round brings nothing the earlier one did not cover.

The bpf_loop() helper, added in 5.17, takes a count and a function, and the kernel calls that function once per round. The walk treats the call as a branch into the function that may be taken again. It walks the function, comes back to the call, and stops once the state at the call falls within the state it saw the round before (push_callback_call(), verifier.c line 9276). The round number reaches the function as an unknown number, so the function must check it before using it as an index, and the hash loop's 4 KB are proved in 63 instructions.

An open-coded iterator, added in 6.4, is a loop in the program's own code that asks a kernel function for each next round. For the numbers behind bpf_for() that function is bpf_iter_num_next(), which returns NULL when the rounds run out. The verifier relies on that contract.

At each such call it walks the side where the iterator has run out and keeps the side where it returned a value as a pending branch. It stops going round once the state at the call repeats. To help that happen, it forgets the range of any number that no check has needed yet, so that a number the loop changes every round, such as a count of its own, does not make every round look new (comment above process_iter_next_call(), line 7532).

may_goto, added in March 2024, is a jump instruction that the program takes only when a hidden count runs out. On x86-64 in v7.2 that count is checked against a clock, and the loop is cut off after a quarter of a second (bpf_check_timed_may_goto(), kernel/bpf/core.c line 3407).

The walk gives it the same treatment as an iterator call, yet in it made the plain loop dearer. The loop's test i < N is decided from the known value of i in every round. A register whose value decided a branch is compared by that value at a checkpoint, so no round's state ever falls within an earlier one's. The walk still goes round 256 times, and every round now adds a checkpoint and a pending branch. With the counter kept in the map value, where the walk does not follow it, the same loop is proved in 67 instructions at any size.

Function calls

Since 4.16 a program can call functions of its own. A function marked static in C is walked at each call site, inside the caller's walk, in a new frame of the state that holds its registers and stack. When it returns, the walk continues in the caller with what it learned. Two states can cover each other only if every frame was entered from the same call site, so a function called from four places is walked four times. In our measurement a 32-round loop in a function called four times cost 666 instructions of walking.

A global function, one without static, is verified once on its own, for any arguments that its types in the program's BTF allow. At each call the walk checks the arguments against those types, gives r0 an unknown number and moves on, and at level 1 it prints Func#%d ('%s') is global and assumed valid. Afterwards do_check_subprogs() walks each called global function from its own start (verifier.c line 18525). The same four calls cost 14 instructions in the caller and 163 in the function, 177 in all. The price is everything the caller knew, because a global function that indexes an array with its argument must check the bound itself even when every caller passes a constant.

Both kinds count against one budget. env->insn_processed is not reset between the main program and its global functions, which is why the statistics print one count per verified function after insns processed and their sum on the last line.

The limits, and where they live

The budget is the limit that most programs meet first, and puts it beside the others. Each counts something different. The budget counts instructions walked, so it grows with paths and rounds. The jump-sequence limit counts pending branches on the stack at once, which grow when one path passes thousands of branches it cannot decide before it reaches an exit. The call-depth and stack limits bound the frames that a walk must hold.

The stack row has a second form in v7.2. Programs of the tracing types (BPF_PROG_TYPE_KPROBE, TRACEPOINT, RAW_TRACEPOINT and PERF_EVENT, and BPF_PROG_TYPE_TRACING, _LSM and _STRUCT_OPS programs that ask for it; bpf_enable_priv_stack(), verifier.c line 5026) on x86-64 can give each function a stack of its own, and then a function that uses 64 bytes or more is checked against 512 bytes alone, with "stack size of subprog %d is %d. Too large" (line 5138). Three nested functions with 200 bytes of stack each were refused as a socket filter with the message in the table and loaded as a tracepoint program, with a largest frame of 208 bytes.

Inside the v7.2 source

lists the code behind everything so far, in the order a load reaches it. bpf_check() runs the shape check in cfg.c and a few passes that prepare the walk, among them the live registers of . Then do_check_main() builds the first state in do_check_common() and hands it to do_check(). draws the same phases around one log line and follows that line from verbose() into the loader's buffer, so we stay with the loop.

do_check() is one for (;;) over the current instruction. Each pass first increments insn_processed and returns -E2BIG once it passes the budget. At a prune point it calls bpf_is_state_visited(), and a return of 1 sends it to the exit handling. It then gives up the CPU if another task needs it, returns -EAGAIN on a pending signal, prints the instruction when the log asks for it, and hands it to do_check_insn(), which picks a checker by its kind.

A conditional jump goes to check_cond_jmp_op(), which first asks whether the test can be decided from what is known. Only if both sides can happen does it call push_stack() for the jump side and let the walk fall through.

push_stack() allocates an entry, copies the whole current state into it, links it at the head of env->head and counts it in env->stack_size, which is the number the jump-sequence limit tests. At an exit, or after a prune, the loop reaches the label process_bpf_exit, where pop_stack() copies the head entry over the current state and continues at its instruction. When the stack is empty it returns -ENOENT, the loop breaks, and the program is proved.

What it costs

CPU
Kernel 7.2.15 in a VM with 16 vCPUs, 12 November 2026. The counter's walk of 36 instructions sat inside a bpf_check() of 99 to 551 µs, median 156 µs over fifteen loads. Time follows instructions walked: about 0.5 µs each for the hash loops, 1,000,001 in 0.50 s; the plain loop over 4 KB took 16 ms, against 0.2 to 0.3 ms with bpf_loop() or bpf_for().
Memory
A checkpoint is a bpf_verifier_state_list of 256 bytes, a bpf_func_state of 1,032 per frame, which kmalloc rounds up to 2,048, and 96 per 8-byte stack slot (BTF of 7.2.15), about 2.4 KB; a pending branch is the same around a 256-byte stack entry. The loop that hit the budget held 10,001 checkpoints, about 24 MB, charged to the loader's memory cgroup until the load ended.
Switches
One bpf() call, the walk running in the loader's thread throughout; do_check() yields between instructions when another task needs the CPU and stops with -EAGAIN on a signal.
Locking
None with CAP_BPF. Without it every load takes the mutex bpf_verifier_lock: two loads as the user nobody, started together, took 30.7 and 60.7 ms of verification time, the second waiting for the first, while as root both took 30.8 ms.

Read the statistics line of every program at log level 4 before it ships. If the count grows with a loop's bound, or passes about 100,000, rewrite the loop with bpf_for() (6.4 and later) or bpf_loop() (5.17 and later), whose walk does not grow with the round count; keep plain loops for a dozen rounds or fewer.

When it goes wrong

The rows of come from programs we wrote to hit each limit, loaded one at a time with book/labs/walk-root.sh. The first three refuse loops, and they fail in different ways. The budget is met by a loop the walk follows round by round, and its statistics show thousands of checkpoints spread evenly along the walk. The jump-sequence limit is met far below the budget by a loop whose body holds a branch the walk cannot decide, because each round leaves one pending branch that nothing removes until the first path reaches an exit. The infinite-loop message arrives within a few instructions, as soon as a round brings the walk back to a checkpoint with nothing changed.

The error code sorts most of these before any reading. -E2BIG means a limit on size or depth, -EINVAL a loop the verifier will not walk, and -EACCES the stack, as it does for the broken rules that reads. The last four rows are loads that succeed, which only the statistics can explain, so a loader in production should record the statistics line of every load and not only of the ones that fail.

Recap

The verifier runs inside bpf_check() and refuses any program it cannot prove safe on every path, with a shape check over the jumps and then a depth-first walk that keeps a type for every register and stack slot, pushes the other side of each undecided branch onto a stack and pops it at the next exit. At prune points it compares the current state with saved checkpoints and stops a path that a finished one covers, comparing only what is live, which cut the counter's second path to 12 instructions and its walk to 36. Loops are walked round by round unless they give the walk a point where rounds can be compared, as bpf_loop(), bpf_for() and may_goto do, and static functions are walked at every call while global ones are verified once. The budget of one million instructions, 8,192 pending branches, 16 frames and 512 bytes of stack bound the walk, and log level 4 shows how close a program came to each.

Eight paths, and as few as four walks. Each block doubles the routes, so 2 × 2 × 2 = 8. The walk follows one full path and keeps the other side of each block for later, and when it comes back for one, that side ends where the blocks meet again if a saved state there covers it, which is likely, since nothing set in the blocks is read afterwards. That gives one full path plus three short arms. The saving rule in the margin note decides where states exist, so a cut can come a few instructions later than the meeting point. A walk that restarted from the top for each kept branch would need six, two per block, but this one resumes from the branch itself.

Because v and w are the same pointer to the kernel. The copy keeps the id the lookup gave, and when the test on w succeeds, mark_ptr_or_null_regs() (kernel/bpf/verifier.c, line 15706 in v7.2) clears the NULL flag on every register and stack slot with that id. The verifier page says the same in its paragraph on the id field, and in the counter's own log the id is the id=1 inside r0's entry. Expecting a rejection assumes that the kernel tracks only the register named in the test; clang copies pointers between registers all the time, and the id is what makes that harmless.

No. The verifier proves the six rows of , which are about jumps, registers, NULL tests, bounds, calls and an end, and the choice of key belongs to the program. The counter stores u32 pid = bpf_get_current_pid_tgid();, and the low 32 bits of that helper's result are the thread ID while the process ID is in the high half, so keying by bpf_get_current_pid_tgid() >> 32 counts per process. "Loaded" is easily read as "correct", but the verifier would accept either key, because both are plain numbers stored on the stack.

8,211 at 1,024 bytes, and about 125,000 bytes before the budget. Each byte costs the eight instructions of the loop's body, (32,787 − 2,067) / (4,096 − 256) = 30,720 / 3,840 = 8, and the rest of the program costs 2,067 − 8 × 256 = 19, so 19 + 8 × 1,024 = 8,211. The budget allows (1,000,000 − 19) / 8 ≈ 124,997 rounds. A loaded copy at 1,024 bytes printed processed 8211 insns on kernel 7.2.15. It is tempting to expect another limit first, but the loop's test is decided every round, so no pending branch piles up; the cost on the way would be 12,500 checkpoints, one per ten rounds, and about half a second.

The shape check refused it, before the walk. bpf_check_cfg() in kernel/bpf/cfg.c explores the jumps depth first, and when push_insn() meets a jump to an instruction still on its own path, a back-edge, it returns -EINVAL with that message unless the loader has CAP_BPF (lines 133 to 139). do_check_main() runs only after the shape check, so the statistics show 0 instructions and 5 µs. The fixes are CAP_BPF, or a BPF token that grants it, or a loop the compiler unrolls. A common mistake is to blame the budget, which is the same million for every loader; what changes without CAP_BPF is loops, a program length of 4,096 and 64 checkpoints per instruction.

Because a static function is walked at every call, and a global one once. The walk enters a static function in a new frame of the caller's state, and states_equal() requires every frame to come from the same call site, so the second call cannot be pruned against the first: 14 instructions in the caller plus four walks of about 163 make 666. A global function is checked once by do_check_subprogs() for any arguments its BTF types allow, and each call only checks the arguments and gives r0 an unknown number (verifier.c line 9398). The function therefore can no longer rely on what its callers pass: if it indexes an array with an argument, it must test the bound itself, even when every caller passes a constant.

8,193 rounds, at 9 instructions each. Every round's test of the random bit can go either way, so check_cond_jmp_op() pushes the jump side, and nothing is popped until the first path reaches an exit; push number 8,193 passes BPF_COMPLEXITY_LIMIT_JMP_SEQ (8,192). llvm-objdump -d shows a round as two calls, an and, the test, an add, a move, a jump, the decrement and the loop test, nine instructions, with three before the loop: 3 + 8,192 × 9 + 3 = 73,734, the last round stopping at its test. The loop test does not push a branch of its own, because the counter is a known number and the walk takes only the side that can happen.

Slot 1, *(u32 *)(r10 - 0x4) = w0, which writes the key before the call at slot 8 reads it through r2. The kernel's record shows those bytes as written, fp-8=mmmm????, where m means written and ? never written. The page's example without the store is rejected with "invalid indirect read from stack", and in v7.2 the wording is "invalid read from stack", at line 6725 of verifier.c. Testing the rule as root can mislead, because a loader with CAP_PERFMON may let helpers read unwritten stack (bpf_allow_uninit_stack()), so it is best tried as an ordinary user would hit it.

Because nothing after that point read the register on the saved path. If any later instruction had read it, the walk from the saved state would have been refused with !read_ok; it was accepted, so every instruction from there on writes the register before reading it, and whatever the current path holds in it is never looked at. In v7.2 the rule is the first test in regsafe(), kernel/bpf/states.c line 514, with the comment "explored state can't have used this". A stricter rule, matching "never written" only with "never written", would also be safe, but the kernel made it looser on purpose, because pruning depends on it.

Because the only register that differs, r0, is written at instruction 4 before anything reads it. The two states are r0 = 1, r1 = 0 and r0 = 0, r1 = 0, and from the checkpoint on the program reads r1 and overwrites r0, so only r1 matters, and r1 is the same in both. Liveness tracking finds this and drops r0 from the saved state, after which the states are equal and the second arrival is pruned. The write counter has the same shape, since the line from 9 to 12 in the lab solution lists no r0 at all. A comparison register by register would call the states different, which is the error liveness tracking exists to avoid.

Common wrong turn. Counting slots instead of instructions, which gives 27 for the first path, or counting the second path from slot 0. The other is expecting the second path to stop at slot 12, the jump target, where no state was saved.

What this shows. The plain loop is walked once per byte, eight instructions a round, so its count grows sixteen times with the size. bpf_loop() and bpf_for() give the walk a call at which a round's state can be compared with the round before, and once it falls within it the walk stops, at any size.

Common wrong turn. Reading the loader's wall clock, about 5 ms for every load, as the cost of verification; most of it is libbpf opening the object and probing the kernel. The other is concluding that bpf_loop() runs its body fewer times: it still calls it N times when the program runs.

back-edge
a jump to an instruction still on the jump's own path; the shape of every loop
bounded loop
a loop whose last round the verifier can see; accepted since Linux 5.3
checkpoint
a verifier state saved at a prune point, for later paths to be compared with
global function
a function of the program without static, verified once for any arguments its BTF types allow
instruction limit
one million instructions walked, across all paths, before the verifier gives up
live
of a register or stack slot at an instruction: some path from there may read it before writing it
log level
how much the verifier writes: 1 for the instructions walked, 2 for the full state at each one, 4 for statistics
open-coded iterator
a loop in the program's own code that asks a kernel function for each next round, such as bpf_for(); since 6.4
path
one route from the first instruction to an exit, taking one side at each branch
pending branch
a side of a conditional jump that the walk keeps on a stack, with a copy of the state, to follow after the current path ends
pointer-or-NULL
a pointer that may be NULL, such as a map lookup's result; it cannot be read through until a test on that path
pruning
stopping a path where it matches a saved state already proved safe
register type
the kind of value a register holds: never written, a scalar, or one of many pointer types
scalar
a plain number, with bounds, that may never be used as a pointer
shape check
the verifier's first step: every jump lands inside the program and every instruction is reachable
verifier
the part of the kernel that walks a program at load time and refuses it unless every path is safe
verifier log
the text the verifier writes into the loader's buffer: each instruction walked, the reason it stopped, and statistics
verifier state
what the verifier knows at one instruction: a type, and bounds or sizes, for every register and stack slot
