Calling the kernel: helpers and kfuncs

The write counter's slot 8 holds the number 1 when libbpf hands it to the kernel and the number 357,328 when it runs, and between the two the kernel decides what helper 1 means for a tracepoint program, checks the call against that meaning, and rewrites it. A call costs about 4 ns, a lookup the kernel writes in place costs half a nanosecond, and a kfunc that takes a reference and gives it back costs 40.

So bpf_copy_from_user() appears in the tracepoint list, yet a counter that calls it is refused, because that helper may sleep and the counter may not ().

A helper is a C function and a prototype

We begin with the C behind helper 1 in . Every helper is written with one of the macros BPF_CALL_0 to BPF_CALL_5, and BPF_CALL_x (include/linux/filter.h, line 611) turns the top five lines into three pieces. The body becomes an always-inline function with the real argument types, and a typedef records the same types. bpf_map_lookup_elem() itself takes five u64 values, one per argument register, and casts the first two before it calls the body. The kernel's BTF keeps both shapes.

That outer function is the calling convention of seen from the kernel's side. Up to five arguments arrive in r1 to r5, and the answer leaves in r0. The x86 JIT keeps r6 to r9 in rbx, r13, r14 and r15, which every x86-64 function preserves, so a helper is an ordinary C function and needs no glue around it.

The verifier never reads that code. A helper prototype is the struct bpf_func_proto beneath it (include/linux/bpf.h, line 968). It gives the helper's address, whether it is GPL-only or may sleep, and the types of its result and of up to five arguments. Linux 7.2 has 23 argument types and 9 return types. Flags such as PTR_MAYBE_NULL widen them, so that ARG_PTR_TO_MAP_VALUE_OR_NULL is the map-value argument with NULL allowed.

An argument type names a class of register state, and check_func_arg() (verifier.c, line 8211) compares each argument register with its type in turn. check_reg_type() looks the type up in compatible_reg_types[] (line 7807), a table from each argument type to the register types that satisfy it. Some types then ask for more. ARG_CONST_MAP_PTR notes which map r1 holds, so that ARG_PTR_TO_MAP_KEY can demand that map's key size at r2 (line 8324), and ARG_CONST_SIZE checks a length against the pointer in the register before it. How the verifier knows that four bytes at fp-4 are written, or that a length stays in bounds, is the business of chapters to ; the prototype only says which questions to ask.

Which helpers a program type may call

Which prototype an ID stands for depends on the program type. bpf_get_helper_proto() (verifier.c, line 10117) checks that the ID is below __BPF_FUNC_MAX_ID and then asks the type's own get_func_proto() callback. For a tracepoint program that callback is tp_prog_func_proto() in kernel/trace/bpf_trace.c, and follows it down. It answers four IDs itself and passes the rest to bpf_tracing_func_proto(), which adds three of its own and passes the remainder on to bpf_base_func_proto() in helpers.c.

bpf_base_func_proto() sorts helpers by what the loader holds. The first 25 are open to every program, 28 more come after a CAP_BPF test at line 2124, and the last 21, among them bpf_trace_printk(), after a CAP_PERFMON test at line 2192. A tracepoint program cannot be loaded without CAP_PERFMON at all (syscall.c, line 3045), so every tier is open to the counter. With bpf_probe_write_user(), which needs CAP_SYS_ADMIN as well, the sum is the 82 that bpftool listed.

A NULL anywhere in the chain becomes one message, program of this type cannot use helper, whatever the reason was. In our runs an XDP program that calls bpf_printk() loaded as root. Loaded by a process that had dropped CAP_PERFMON and CAP_SYS_ADMIN, it was refused with that message, because XDP's chain also ends in bpf_base_func_proto() and its test (). An ID beyond the last one the kernel knows fails a step earlier, as invalid func unknown#300 did for a call of helper 300.

check_helper_call() (line 10171) then refuses three kinds of call in turn. A GPL-only helper fails in a program that is not GPL-compatible, then a helper whose own allowed() callback says no, then a helper that may sleep in a program that cannot. Only after that does each argument go to check_func_arg(), as shows for two of the counter's calls. At slot 8, ARG_CONST_MAP_PTR finds a map pointer in r1 and notes the map, and ARG_PTR_TO_MAP_KEY finds the four written bytes at fp-4. The return type leaves r0 as map_value_or_null, the state that follows to the NULL test, while slot 0 takes no arguments and leaves nothing to check.

From call 0x1 to the code that runs

After the walk, bpf_do_misc_fixups() in kernel/bpf/fixups.c rewrites every call, one of the passes that lists. Most helpers reach patch_call_imm (line 2330), which puts the helper's distance from __bpf_call_base in the immediate, and the JIT turns that into a direct x86 call. For a JIT-compiled program on a 64-bit machine, map helpers go straight to the map's own functions instead (line 1984). So the update at slot 24 of the object becomes call htab_map_update_elem at slot 26 of the dump. A lookup in a map whose operations table has map_gen_lookup is written as instructions, for the hash map a call to __htab_map_lookup_elem() and two more.

Reading the offsetIn the VM, /proc/kallsyms put __bpf_call_base at ffffffffb6598d50 and bpf_get_current_pid_tgid at ffffffffb65d8580, 260,144 bytes higher, the number after the #. bpf_trace_printk lies below the base, at −129,920.

An array map goes further. Its array_map_gen_lookup() (arraymap.c, line 218) writes seven instructions that point r1 at the values, load the key, test it against max_entries and scale it, and no call remains. This is inlining, replacing a call with instructions that do the callee's work in place. measures it in a tracepoint program that repeats one operation 64 times per event, with kernel.bpf_stats_enabled=1.

The inlined lookup costs half a nanosecond. The same array created with BPF_F_INNER_MAP, for which array_map_gen_lookup() declines at its first test, costs 4.9 ns through a call to array_map_lookup_elem(), close to the 4.1 ns of bpf_get_current_pid_tgid(). Hashing the key and walking a hash chain take the hash map to 13.9 ns.

A few helpers are inlined as well, and loads a program that calls eight of them once each. bpf_do_misc_fixups() writes bpf_jiffies64() as three instructions for any JIT-compiled program on a 64-bit machine (line 2079). On x86-64 it also writes three each for bpf_get_smp_processor_id() and bpf_get_current_task() (lines 2105 and 2132), which read the processor number and the current task from this CPU's copy of a kernel variable. The other four remain calls. The x86 JIT inlines no helper of its own, since bpf_jit_inlines_helper_call() keeps its default answer, false, in core.c, so they are calls in the machine code too.

In the second run an inlined helper cost about 0.2 ns a call, against 4.1 ns for a called one. bpf_ktime_get_ns() cost 31.3 ns, because on the VM's clock reading the time costs far more than the call. The five variants of the first run came back within 0.9 ns of , with the lookup through a call at 4.7 ns and the kfunc pair at 38.8.

The prototype of bpf_get_smp_processor_id() also sets allow_fastcall. That tells the verifier that the inlined call changes no register but r0, so spills and fills of r1 to r5 that the compiler placed around it may be removed (bpf_remove_fastcall_spills_fills(), fixups.c line 2566). Inlining makes the program longer, though: 64 inlined array lookups took 7,744 bytes of bytecode, against 4,672 as calls.

kfuncs: kernel functions named by BTF ID

A kfunc has no helper ID and no prototype struct. Its definition carries __bpf_kfunc, which keeps the compiler from inlining it or dropping it (include/linux/btf.h, line 89). Its name goes into a BTF ID set, a list of BTF IDs with a word of flags for each, between BTF_KFUNCS_START and BTF_KFUNCS_END. The IDs stay zero until the resolve_btfids tool fills them in as the kernel is linked. pahole, run with its decl_tag_kfuncs feature while the kernel's BTF is written (scripts/Makefile.btf, line 17), then tags each function of a set with bpf_kfunc.

How manyThe vmlinux BTF of 7.2.15 carries 308 bpf_kfunc tags, against 211 helper IDs (bpftool btf dump file /sys/kernel/btf/vmlinux | grep -c "DECL_TAG 'bpf_kfunc'"). Modules carry their own.

A set does nothing until it is registered for a program type. At boot, kfunc_init() in helpers.c (line 4978) passes the generic set, which holds bpf_task_from_pid() and bpf_task_release() among others, to register_btf_kfunc_id_set() for six program types. It registers a common set once more for BPF_PROG_TYPE_UNSPEC, and every type shares that one. Each registration files the set under one of fourteen kfunc hooks, an index that bpf_prog_type_to_kfunc_hook() in btf.c (line 9029) picks for the type. Tracepoint, raw tracepoint, perf event, LSM and tracing programs all map to the TRACING hook, so the generic set registered for tracing programs reaches the counter as well.

A program declares a kfunc as an external symbol marked __ksym. libbpf finds the name in the kernel's BTF and writes its BTF ID into a call with source field 2, the third kind of call in , as shows for bpf_task_from_pid(). The first kfunc call of a program makes bpf_add_kfunc_call() (verifier.c, line 2677) demand kernel BTF, a JIT and a GPL-compatible licence, and look up the function's address with kallsyms_lookup_name(); a program may call at most 256 different kfuncs. check_kfunc_call() (line 12913) asks btf_kfunc_is_allowed() whether the ID is in a set of the common hook or of the program's hook, matches the registers against the BTF prototype and applies the flags. The fixup then writes the address's distance from __bpf_call_base, for the same direct call as a helper's.

What the flags make the verifier check

A BTF prototype says which types a kfunc takes, and the flags in its set say what a prototype cannot (). An acquire kfunc, flagged KF_ACQUIRE, returns a pointer that holds a reference. The program must pass that pointer to a release kfunc, flagged KF_RELEASE, on every path before it exits, or store it in a map. KF_RET_NULL makes the result maybe-NULL, KF_SLEEPABLE admits only sleepable programs, KF_DESTRUCTIVE only loaders with CAP_SYS_BOOT, and KF_RCU_PROTECTED only calls inside an RCU read section. The generic set gives bpf_task_from_pid() the flags KF_ACQUIRE | KF_RET_NULL and bpf_task_release() the flag KF_RELEASE (helpers.c, lines 4847 and 4830).

Every pointer argument must also be a trusted pointer, one the verifier knows to be valid and unchanged. That is a pointer the kernel passed to a tracepoint or struct_ops program, or one an acquire kfunc returned, used at offset zero and not loaded from a field of another pointer (kfuncs.rst, section 2.2). Until Linux 7.0 a kfunc asked for this rule with a KF_TRUSTED_ARGS flag. Puranjay Mohan's commit 1a5c01d2508a made it the rule for every kfunc, and v7.2's btf.h no longer defines the old flag. KF_RCU now relaxes the rule to pointers that RCU keeps valid.

The verifier keeps references in the state it walks, as shows. The call at slot 2 runs acquire_reference() (verifier.c, line 1427), which gives the new reference the next ID, 2, and records the slot. From there on every line of the log ends with refs=2. On the NULL side of the test at slot 3 the reference is dropped, since a NULL pointer holds nothing to release (mark_ptr_or_null_regs(), line 15706).

On the other side the reference lasts until the exit, where check_reference_leak() (line 9946) prints it with the slot that made it. A release kfunc ends it earlier, in release_reference() (line 8951). That function also makes every copy of the pointer, in a register or on the stack, a plain scalar, so a read through a copy after the release fails with R6 invalid mem access 'scalar'.

Adding a kfunc, and what it promises

Adding a kfunc is correspondingly short. Commit 187baa10963a by Kaitao Cheng, merged for Linux 7.2, added bpf_list_del() in fifteen lines: a nine-line function and a BTF_ID_FLAGS line with KF_ACQUIRE | KF_RET_NULL in helpers.c, and five lines in verifier.c. Those five are needed only because the verifier gives list kfuncs extra rules, such as a check that the list's lock is held. An ordinary kfunc needs no verifier change, since its BTF prototype and flags are the whole contract.

"This helper list is effectively frozen. If you are trying to add a new helper, you should add a kfunc instead which has less stability guarantees."

Comment closing the helper list in include/uapi/linux/bpf.h, Linux v7.2, line 6145

That contract carries no promise. The design Q&A counts the "set of helper functions and their arguments" as stable ABI, and the list stops at helper 211 with the comment above. Levi Zim added that comment in 2025 (commit 0abff462d802, Linux 6.15) "to prevent people from trying to add new helpers there and direct them to kfuncs". Section 3 of Documentation/bpf/kfuncs.rst, which David Vernet's commit 16c294a6aad8 added for Linux 6.3, likens kfuncs to EXPORT_SYMBOL_GPL and says that a kfunc "will never have any hard stability guarantees". The next kernel may therefore refuse a program that calls one ().

A program can prepare for a kernel that lacks a kfunc. Declared plainly, a missing kfunc stops libbpf before any program reaches the kernel, with extern (func ksym) '…': not found in kernel or module BTFs. Declared __weak, it lets libbpf go on, writing 0 wherever the program takes the function's address and turning each call into a call of helper 2,002,000,000 plus the symbol's index (poison_kfunc_call(), libbpf.c line 6239). If a path reaches that call, the verifier refuses it as an unknown helper and libbpf reports the refusal as an unresolved kfunc. A test with bpf_ksym_exists() closes the path, because the verifier sees the test compare 0 with 0, and for a loader with CAP_BPF the call is then removed with the rest of the dead code ().

lists that code in the order a load reaches it. A helper is defined by BPF_CALL_x and described by its prototype, and the program type's chain picks one prototype per ID. check_helper_call() checks the registers against it, and bpf_do_misc_fixups() writes either the helper's distance from __bpf_call_base or instructions that do its work. A kfunc is defined in a BTF ID set and filed under a kfunc hook at boot. check_kfunc_call() checks it against its BTF prototype and flags, the walk counts its references until every exit, and it is called through the same kind of direct call.

What it costs

CPU
Per operation (): 0.5 ns for an inlined array lookup, 4.1 ns for a helper call, 4.9 ns for an array lookup through a call, 13.9 ns for a hash lookup and 39.7 ns for a kfunc acquire and release pair, against 48.8 ns for a run without them. An inlined bpf_get_smp_processor_id(), bpf_get_current_task() or bpf_jiffies64() cost about 0.2 ns, and bpf_ktime_get_ns() 31.3 ns on kvm-clock (). All on kernel 7.2.15 in a 16-CPU VM, 12 November 2026.
Memory
Prototypes are 96-byte constants in the kernel image. A program that calls any kfunc gets a 12,296-byte table of call descriptors (struct bpf_kfunc_desc_tab, 256 entries of 48 bytes), charged to the loader's memory cgroup. Inlining lengthens the program: 64 array lookups took 7,744 bytes of bytecode and 3,838 of x86 inline, against 4,672 and 2,430 as calls.
Switches
None. Helpers and kfuncs run on the program's CPU in its context; only those marked might_sleep or KF_SLEEPABLE may block, and only sleepable programs may call them.
Locking
Map lookups read under RCU with no lock. bpf_task_from_pid() looks the PID up under rcu_read_lock() and takes a reference with an atomic increment of the task's rcu_users, and bpf_task_release() drops it.

Use an array map when keys are small dense integers, because its lookup is inlined at a tenth of the cost of a call, and call a helper whose answer does not change within a run once, keeping the result. Call a kfunc when no helper does the job, release what it acquired on the path that acquired it, and declare it __weak behind bpf_ksym_exists() when the program must also load on kernels that lack it.

When it goes wrong

Most failures of a call are refusals at load, and the verifier's message names the rule that failed (). The helper rows follow the steps of check_helper_call() in order, from an unknown ID and a NULL from the type's chain to the licence, sleep, and one argument against its type. The NULL from the chain hides its cause. A helper the type never offers and one that the loader's capabilities withhold print the same line, so the feature probe and the loader's capabilities are worth reading before the program is changed.

The kfunc rows follow check_kfunc_call() and the reference rules of . A kfunc that libbpf cannot find stops the load before the kernel sees anything. One declared __weak fails in the verifier only if a path reaches its call, and bpf_ksym_exists() is there to close that path. The last row is a cost that prints no error at all: a change to a map's flags can turn seven inlined instructions back into a call, and only the dump shows it.

Recap

A helper is a C function made by a BPF_CALL_x macro, and the verifier checks each call against its struct bpf_func_proto, chosen per program type by a chain of get_func_proto() callbacks whose last step also tests the loader's capabilities. bpf_do_misc_fixups() then turns the ID into a distance from __bpf_call_base, sends a map helper to the map's own code, or writes the work in place, as it does for an array lookup and, on x86-64, for three small helpers. A kfunc is named by BTF ID, allowed by sets registered per kfunc hook, checked against its BTF prototype and KF_ flags, and then called like a helper, while the verifier counts the references that acquire kfuncs open until every exit has closed them. Helpers are stable and frozen at 211; kfuncs promise nothing, and a program that must load on several kernels declares them __weak and tests them with bpf_ksym_exists().

Slot 32, and 0x400. The object has 27 slots; the hash map's rewrite turns slot 8 into three instructions, giving 29 and an exit at 28, while array_map_gen_lookup() turns it into seven, 27 − 1 + 7 = 33, so the exit moves to 32. The seven are r1 += 304, the offset of the values in struct bpf_array, then r0 = *(u32 *)(r2 +0), if r0 >= 0x400 goto pc+3, r0 <<= 3, r0 += r1, goto pc+1 and r0 = 0 (xlated-counter_array.txt from book/labs/ch13-root.sh). Had the map's creator lacked CAP_PERFMON, an eighth instruction, w0 &= 0x3ff, would mask the index against a speculative read, putting the exit at 33. Counting the two-slot map load as replaced is the usual slip; it stays.

bpf_trace_printk(), helper 6, which bpf_printk() becomes. Its prototype, bpf_trace_printk_proto in kernel/trace/bpf_trace.c, sets .gpl_only = true, and check_helper_call() compares that with prog->gpl_compatible, which bpf_prog_load() set from the licence string (); line 10201 of verifier.c prints the message. Slots 0 and 8 passed because their prototypes say false, as does slot 24's, and the log shows 16: (85) call bpf_trace_printk#6 just above the refusal. It is tempting to think the licence refuses the whole program; removing bpf_printk() lets it load, as does a GPL-compatible string such as "Dual MIT/GPL".

From the second argument type of bpf_map_lookup_elem_proto, ARG_PTR_TO_MAP_KEY. check_func_arg() calls check_reg_type(), which looks the argument type up in compatible_reg_types[] in verifier.c; for a map key that is mem_types, the ten pointer kinds the message lists, starting with fp, a pointer into the stack. Here r2 holds the thread ID as a scalar, and a scalar is never an address, or the helper would read four bytes wherever the number pointed. The cast satisfies clang, which cannot know what helper 1 expects. A common mistake is to suspect the key size; that check comes only after the type check passes.

The BTF ID sets. check_kfunc_call() asks btf_kfunc_is_allowed() whether ID 82636 is in a set registered for the common hook or for the program type's hook. A socket filter maps to BTF_KFUNC_HOOK_SOCKET_FILTER in bpf_prog_type_to_kfunc_hook(), and kfunc_init() registers the generic set, which holds bpf_task_from_pid(), only for tracing, tc, XDP, struct_ops, syscall and cgroup skb programs, so bpf_fetch_kfunc_arg_meta() returns -EACCES and line 12935 prints the message. In the tracepoint counter the same call loads, because tracepoint programs share the TRACING hook. Whether the function exists was never the question: a kfunc is allowed per hook, much as get_func_proto() allows a helper per program type.

The loader's capabilities, through the last step of the chain. XDP's xdp_func_proto() passes bpf_trace_printk through bpf_sk_base_func_proto() in net/core/filter.c to bpf_base_func_proto(), which answers it only after bpf_token_capable(…, CAP_PERFMON) at line 2192 of helpers.c; CAP_SYS_ADMIN had to go too, because bpf_ns_capable() in token.c accepts it in place of any other capability. Without them the chain returns NULL, and bpf_get_helper_proto() turns every NULL into the same refusal, which check_helper_call() prints as a matter of program type. bpftool ran its probe as root. It is easy to blame XDP itself, but the same object loaded as root (load-xdp-root.txt against load-xdp-noperfmon.txt, from book/labs/calls-root.sh, step 6).

About 31.3 ns a call, and about a fifth of the counter's run. The 64 calls added 2,049.0 − 47.5 = 2,001.5 ns, and 2,001.5 / 64 = 31.3 ns. One call per event would add 31.3 / 155 ≈ 0.20 to a run that the costs box of measured at 144 to 162 ns without bpf_printk. The call itself is the 4 ns of any helper call; the rest is reading the clock, which in this VM is kvm-clock, so the number belongs to the clock source as much as to BPF. A common mistake is to expect the clock to be inlined like bpf_jiffies64(); in v7.2 the dump keeps call bpf_ktime_get_ns (), and a program that needs one timestamp per run should read it once.

The map's flags, which array_map_gen_lookup() reads. Its first test, at line 227 of arraymap.c, returns -EOPNOTSUPP for a map created with BPF_F_INNER_MAP, which the user-space API header describes as a map that may go into another map "with dynamic max entries": the program may then reach arrays of other sizes through the same call, and seven instructions with one array's max_entries written into them would be wrong for the rest. bpf_do_misc_fixups() falls back to a direct call of the map's own array_map_lookup_elem(), the 4.9 ns bar of . Nothing in the bytecode differs, so the object's dump looks the same; it is tempting to look for a compiler change, but only bpftool prog dump xlated of the loaded program shows the call where seven instructions stood.

libbpf's probe counts any refusal other than an unknown or refused helper as support (libbpf_probes.c, line 478), and its test program fails here for another reason, the sleep check. bpf_copy_from_user_proto sets might_sleep, and check_helper_call() refuses it at line 10227 when the program is not in a sleepable context. Making the program sleepable lets the call load: for a system-call tracepoint that is the section SEC("tp.s/syscalls/sys_enter_write"), the prefix under which our copy that calls the sleepable kfunc bpf_copy_from_user_str() loaded (load-sleepkf_s.txt). It is tempting to read the probe's list as a promise for every program of the type, but it lists what the type may name, and the sleep, licence and argument checks still apply.

Common wrong turn. Testing the result of the call, if (bpf_book_missing(pid)), instead of the symbol. The call is still on a path the verifier walks, and the load fails as in the second case; bpf_ksym_exists() tests the address, which libbpf has set to 0.

acquire kfunc
a kfunc flagged KF_ACQUIRE, which returns a pointer holding a reference that the program must release
BTF ID set
a list of BTF IDs, each with a word of flags, built into the kernel; registered for a program type, it makes the functions in it kfuncs for that type
helper prototype
the struct bpf_func_proto that gives a helper's address, flags, return type and argument types; the verifier checks calls against it
inlining
replacing a call with instructions that do the callee's work in place, as the verifier does for an array lookup
release kfunc
a kfunc flagged KF_RELEASE, which takes such a pointer and drops its reference
trusted pointer
a pointer the verifier knows to be valid and unchanged, such as a tracepoint's argument or an acquire kfunc's result; every kfunc wants its pointer arguments trusted
