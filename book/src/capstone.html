Capstone: a new data structure, twice

A hash map keeps an exact count for every thread it has room for and nothing for the rest. In this chapter the write counter keeps an approximate count for every thread in memory fixed in advance, first as a count-min sketch that a program builds in an arena on a stock kernel, then as a map type of its own in a kernel we patch, and we weigh what each build costs the counter, the kernel and its maintainers.

A hundred thousand threads

The workload is the one a hash cannot hold. Four heavy threads each write 100,000 times while 100,000 light threads come and go, 64 at a time, each writing three times, so the counter sees 700,000 writes from 100,004 threads. The loader, cbench in book/labs/capstone, records each thread's ID and writes, so the truth is known exactly, and each version of the counter counts only the loader's own threads. The VM's kernel.pid_max is raised to 4,194,304 first, because at its default of 32,768 thread IDs would be reused long before the hundred-thousandth thread.

shows three versions on the stock kernel. The hash of , 1,024 entries, kept exact counts for the first 1,024 threads, the heavy four among them, and refused 296,940 inserts with -E2BIG. The LRU hash of the same size kept 740 of the loader's threads and none of the heavy four. They had finished their writes early in the run, and a hundred thousand inserts later they were the entries used least recently, which is what an LRU hash evicts.

The sketch kept an estimate for all 100,004 threads in 110,592 bytes. No estimate fell below the truth, the heavy threads were over by at most 93 writes in 100,000, and the light ones, which wrote three times, by at most 135. The table of the heaviest threads beside it named the heavy four, and user space read the table and every estimate with no system call.

What a count-min sketch promises

A count-min sketch is a table of d rows of w counters with one hash function per row, from which any key's count can be estimated. Cormode and Muthukrishnan introduced it in 2005. To add c to a key, add c to the one counter that each row's hash picks for the key. To estimate a key, read the same d counters and take the smallest, because every counter holds the key's own count plus whatever other keys hashed there.

Two guarantees follow. An estimate is never below the true count, since counts only grow. And if N is the total of all counts, an estimate exceeds the truth by more than εN with probability at most δ when w = ⌈e/ε⌉ and d = ⌈ln(1/δ)⌉, provided the hash functions come from a pairwise-independent family (Theorem 1 of the paper). For ε = 0.001 the width is 2,719, and five rows give δ = e−5, about 0.0067. The sketch then takes 13,595 counters, 108,760 bytes of eight-byte counters, whatever the number of keys.

draws the counters of the run, rebuilt from every thread's true count with the program's own hash; the rebuild reproduces all 100,004 estimates. A light thread's five counters held between 93 and 138 and its estimate is the smallest. A counter holds 257 writes on average (700,000 over 2,719), and the minimum of five such counters is what a light thread reads. A heavy thread's estimate is off by the same 90 or so, which is 0.09 per cent of its count. The sketch's error is absolute, so it suits the heavy hitters, the few keys that account for a large share of the total, and says little about a key that wrote three times.

The paper finds the heavy hitters by keeping a heap of the keys whose estimate passes a threshold, checking each key after its update (section 5.2). Our table keeps the 16 largest estimates instead, a choice that needs no threshold set in advance.

The sketch in an arena

The arena version, c_sketch.bpf.c, reserves its counters with one call. A syscall program, init, run once by the loader, asks bpf_arena_alloc_pages() for 27 pages and writes the width and depth into a header before the rows. With the table compiled in, it also takes 16 nodes from bpf_alloc() of the selftests' bpf_arena_alloc.h and links them into a list. The address of the sketch goes into a global in .bss. shows the result from the loader's side, with the addresses of the run in see.txt.

The program can use only what it carries. No helper hashes a buffer, so cms.h holds a copy of the kernel's jhash2() for an eight-byte key, seeded with the row number, and picks the slot with the kernel's reciprocal_scale(), a multiply and a shift that maps a 32-bit hash onto 0 to w − 1. They are the functions the map type of the second half uses, so both sketches put a thread in the same counters. jhash with a seed per row is not a family proven pairwise independent, as the paper assumes, so the measured errors are the check that it behaves like one here.

The update in is also the query, because __sync_fetch_and_add() returns each counter's old value. Linux v7.2 accepts that on arena memory. atomic_ptr_type_ok() in verifier.c asks the JIT, and the x86 JIT's bpf_jit_supports_insn() refuses only the fetching forms of AND, OR and XOR on the arena; an exchange or a compare-and-swap is accepted, and the table uses compare-and-swap to claim a node. The empty asm statement names the arena map in the program. Without it the verifier refused the counter's first cast with the message met, since the program reached the arena only through a pointer in .bss.

The table walks its 16 nodes on every write. It refreshes the thread's node if it finds one, and otherwise, when the new estimate beats the smallest in the table, claims that node by compare-and-swap on its thread ID. A global kmin lets a light thread skip the walk. No lock is taken, so a node's estimate can trail by a write when two CPUs race, which a table of the heaviest can afford.

The limits of shaped two choices. The table stores thread IDs and estimates, never a task_struct pointer, which would load back as a scalar. And the key reaches the hash as a number in a register, so no arena buffer is ever handed to a helper, which would be refused, as the tenth row of shows.

What the arena sketch costs

Each version ran with one writer pinned to a CPU making 2,000,000 one-byte writes to /dev/null, three times, by the method of , and again with eight writers on eight CPUs (). The sketch cost 70.7 ns a run against 83.7 for the hash. Five hashes and five atomic adds on memory the program addresses directly came out cheaper than one hash lookup, a call into the kernel that hashes the key and walks a bucket under RCU.

The table is the one structure every writer shares. With one writer it added 2.6 ns a run; with eight it added 38, because the 16 nodes sit in a few cache lines that every heavy writer's walk stores into, so the lines travel between CPUs on almost every write. The counters themselves are shared only by chance, when two threads' keys land in one 64-byte line, so the bare sketch rose by only 3.4 ns.

The workload of a hundred thousand threads made every version slower, through cold caches and the creation and exit of threads between writes, but it split them further. The hash paid most, 213.9 ns a run, because each of 296,940 refused inserts searched the free lists of all 16 CPUs before failing (___pcpu_freelist_pop()), and the 262,144-entry hash that held everything paid 153.4 for its inserts.

The same sketch in .bss, which libbpf creates as a one-element array map with BPF_F_MMAPABLE, cost the same as the arena within a nanosecond, and user space reads it through mmap as well. What the arena adds over the array is pointers, which the array version cannot hold, so its table is a fixed array searched by index. The structure the program can grow, link and hand to user space as a graph is what the arena buys, at a few pages of memory charged by the page and no memlock.

sets the errors against the bound at three widths. At w = 2,719 every error lay between 33 and 144 against a bound of 700. A sketch ten times narrower, 10,880 bytes, made the typical error about ten times larger, a median of 1,041, as εN predicts. No estimate at any width passed its bound, and the typical error was about a seventh of it, the slack of the Markov inequality behind Theorem 1.

A map type: the API decides the shape

A map type is code in kernel/bpf that programs reach through the map helpers and user space through bpf(), so its design starts with which helpers fit. weighs the three choices. Lookup returns a pointer to a value stored in the map, and a sketch stores no value for a key; its answer is computed on each query. The bloom filter of kernel/bpf/bloom_filter.c had the same problem and solved it with a keyless map, one created with a key size of 0, whose value is the item itself, pushed to add it and peeked to test it.

The value of BPF_MAP_TYPE_COUNT_MIN is therefore the key's bytes followed by a u64 count. Push adds the count to the key's d counters, so a program can count bytes as easily as writes, and peek returns the smallest of them. From user space, BPF_MAP_UPDATE_ELEM pushes, and BPF_MAP_LOOKUP_ELEM reads the key from the value buffer and writes the estimate into its count. max_entries is the width, the low four bits of map_extra the depth, five by default as the bloom filter's hash count is, and BPF_F_ZERO_SEED fixes the seed for tests.

cms_map_alloc_check() refuses a key, a value of eight bytes or less, a width of 0, unknown flags, other bits in map_extra, and more counters than a 32-bit slot index reaches. cms_map_mem_usage() reports the header and 8wd bytes, which is the memlock bpftool prints. The counters are shared and updated with atomic64_add(). A per-CPU sketch would cost 16 times the memory on this machine and make every query sum 16 copies of each counter, and the write counter does not need one: a thread runs on one CPU at a time, so two CPUs meet on a counter only when their keys collide, as the eight-writer runs confirm.

The program in c_cms.bpf.c is shorter than the arena version, a struct cms_value on the stack and one push. What the API takes away is the table: push cannot return the estimate, so keeping the heaviest threads costs a second pass of five hashes, a peek, where the arena version had the estimate for free.

What the series touches

is the series as git format-patch wrote it into book/labs/capstone/patches, eight patches against the v7.2 tag. Twenty-one files change for 209 lines of map. The uapi header gains an enum value that can never be taken back, and its copy under tools/include must match it, or libbpf's build warns and then fails. syscall.c learns where push and peek replace update and lookup, that map_extra is allowed, and that creating the map needs CAP_BPF. libbpf learns the type's name and how to probe for it, and bpftool its name; until it does, bpftool prints type 36.

The verifier needs the most care, because it must learn the map's rules from us in four places. check_map_func_compatibility() allows push and peek on the new type and refuses every other helper. resolve_map_arg_type() says that peek reads its buffer, where for a queue it writes it. check_map_prog_compatibility() keeps a list of the map types a sleepable program may use, and the first selftest run failed on it: a syscall program sleeps, and it was refused with "Sleepable programs can only use array, hash, ringbuf and local storage maps".

The fourth place was found the hard way, when the counter with its table was refused at its peek. Stack liveness in v7.2 reads a helper's prototype, where peek's buffer is marked write-only, and does not ask resolve_map_arg_type(), so it takes the stored key as dead before the call and poisons it, and the argument check then refuses to read it.

The bloom filter has the same bug on the stock kernel. On 7.2.15 the two smallest programs in book/labs/capstone/bad that peek one with a value on the stack are refused with "slot poisoned by dead code elimination". Mainline fixed it for the bloom filter in commit 830e4372de5c, merged for Linux 7.4 and first tagged in 7.4-rc1. Patches 1 and 2 carry the same rule for a v7.2 tree, and on bpf-next the count-min patch would only add its type to that condition.

The selftests check creation's refusals, user-space access, a program's push and peek against user space, and three programs the verifier must refuse. On the final kernel the seven subtests of count_min_map, the two of verifier_bloom_peek and the bloom filter's own test passed. scripts/checkpatch.pl --strict raised three kinds of complaint, all inherent: no Signed-off-by, since only the author can certify the Developer's Certificate of Origin, a question whether MAINTAINERS needs updating, which its kernel/bpf/ pattern already covers, and the extern declarations by which bench.c registers every benchmark.

The cover letter, the message numbered 0 that explains a series before its patches, says what the map does and why, gives the benchmark's numbers, and asks the maintainers the question the next sections take up. The series was not sent. It is in the book's lab folder to be read, and nothing was mailed, pushed or posted.

The two builds measured

The patched kernel ran the comparison in one VM session (). Its configuration came from vng and the selftests' fragments, with lock debugging turned off; the fragments as given turn on CONFIG_PROVE_LOCKING, under which the hash's run cost 137 ns instead of 83. Compare the columns of one session only, since the stock and the patched kernels are built differently.

In that session the map type cost 93.1 ns a run with one writer, between the arena sketch at 75.9 and the hash at 89.5. With the table of the heaviest the gap widened, 108.4 against 78.1 for the arena, because every write then pays for a peek, a second pass of five hashes. The first build of the map was slower still. Its push called a slot function five times, and inlining it, the change now in patch 3, took the counter from 108.0 to 86.0 ns a run, each measured beside an arena sketch at 70 to 72, and the benchmark's push from 25.3 to 45.3 million a second. This CPU runs the kernel with the SRSO mitigation in its "Safe RET" mode, which sends each return of kernel C code through a thunk, while the arena version's hashing is compiled into the program itself.

The benchmark takes the hook away and repeats each operation 1,024 times a run from getpgid(). With one producer a push took about 21 ns and the hash's lookup and add, whose lookup the verifier inlines, about 27. Eight producers pushing the same 100,000 random keys reversed the order. Push fell to 19.3 million a second per producer because every push writes five counters that the other CPUs write too, while peek, which only reads, held at 42.1, and the bloom filter's push, which sets bits in one dense bitmap, fell to 7.4. Thread IDs do not collide that way, which is why the counter's eight writers cost the map type only 12 ns more; keys that every CPU updates are the case for a per-CPU sketch.

The map type's errors matched the arena's within the variation between runs, as the same hash with the same seeds should make them. Reading all 100,004 of them took one lookup each, 63.8 ms against the arena's 1.4 ms of loads.

Inside the v7.2 source

follows the bloom filter from BPF_MAP_CREATE to its push and peek in Linux v7.2, and then the count-min map along the same path in the patched tree. The two share every step but the last, the map's own file, which is why a new keyless map is mostly a matter of adding its type to lists that already exist.

The rewrite in fixups.c explains the cost of a map helper. Once the verifier knows which map a call names, it replaces the call to bpf_map_push_elem() with a direct call to the map's map_push_elem, so the program pays one call and no indirect jump, and then the op's own loop of d hashes and atomic adds.

What upstream says about new map types

The bloom filter is the closest precedent, and its review is on lore. On 1 September 2021, answering its first version, Andrii Nakryiko wrote that "bloom filter logic is actually simple enough to be implementable by pure BPF program logic", lacking only a helper that hashes memory, and went on: "We could go further, and start implementing other simple data structures relying on hashing, like HyperLogLog. And all with no kernel modifications." The map type was merged all the same, as commit 9330986c0300 for Linux 5.16. A count-min sketch is one of the structures he described, built from hashing and counters.

Two and a half years later the arena gave programs the memory that argument needed. Alexei Starovoitov's commit message for it, 317460317a02 of March 2024, lists as its second use case that "the bpf program builds arbitrary data structures in bpf_arena (hash tables, rb-trees, sparse arrays), while user space consumes it". The kernel's later work on arenas, the error streams and kernel-side faults of , makes that use easier.

We found no statement by a maintainer that rules new map types out, and they still land: the instruction array (b4ce5923e780, Linux 6.19) and the resizable hash (16b4d3e2fb24, Linux 7.2) came after the arena. What a map type costs is fixed by its place in the uapi, which kfuncs avoid; Documentation/bpf/kfuncs.rst calls them "a kernel <-> kernel API" that is "not bound by any of the strict stability restrictions associated with kernel <-> user UAPIs". A module can register its own with register_btf_kfunc_id_set(), as showed, so a sketch kept by a module needs no uapi change at all, at the price of no bpf() access and no promise across releases.

What it costs

CPU
Per run with one writer: hash 83.7 ns, LRU hash 84.2, arena sketch of five rows 70.7, with its table of 16 73.3, the same sketch in .bss 70.6 (kernel 7.2.15, 16-CPU VM, 13 November 2026); on the patched kernel, in one session, the map type 93.1, the arena sketch 75.9 and the hash 89.5.
Memory
Sketch: 8wd bytes whatever the number of keys, 108,760 for w = 2,719 and d = 5, held in 27 arena pages that report 0 to memlock, or 109,272 bytes of memlock as the map type. Hash: 82 bytes a thread from creation, about 21 MB to hold 100,004 threads.
Switches
Reading 100,004 estimates: none for the arena or the array, 1.5 ms of loads; one bpf() lookup each for the hash, 69.5 ms, and for the map type, 63.8 ms.
Locking
None: atomic adds on counters that two CPUs share only when keys collide. The table of the heaviest is shared by every heavy writer and cost 38 ns more a run with eight writers.

Count exactly while the keys fit a map; when they do not and an error of ε times the total is acceptable, use a sketch. Build it in an arena when user space reads it often or it needs pointers, as a map type only to give it a uapi of its own and bpf() access for any tool, which means proposing it upstream with tests, documentation and a reason the arena cannot serve; a kfunc module serves a single site without either.

When it goes wrong

The rows fall into three groups. The first three concern a kernel and its tools that disagree about the map type, which is the everyday cost of a new uapi value: every loader, bpftool and header must be rebuilt before the type has a name. The middle rows are refusals by the verifier, half of them rules that a new map type must teach it and half the arena's single type showing through, and each log names the instruction. The last rows load and run. A sketch never errs below the truth, so an estimate that looks high calls for its bound, e·N/w, before suspecting the hash.

Recap

A count-min sketch keeps d rows of w counters and adds each key's count to one counter per row; its estimate is the smallest of the key's counters, never below the truth and above it by more than εN with probability at most δ when w = ⌈e/ε⌉ and d = ⌈ln(1/δ)⌉. On a hundred thousand short-lived threads, a hash of 1,024 entries refused 296,940 inserts and an LRU hash evicted the heaviest threads, while a sketch of 108,760 bytes kept an estimate for every thread, the heavy ones within 0.1 per cent. Built in an arena, the sketch cost 70.7 ns a run against 83.7 for the hash, user space read it and a pointer-linked table of the heaviest without a system call, and an array map would have held the counters but not the pointers. Built as a map type it became a keyless map reached by push and peek, at the price of eight patches over twenty-one files, a value in the uapi for good, and four rules the verifier had to be taught by hand, one of which v7.2 had already got wrong for the bloom filter. That verifier is a program too, and begins Part V's question of how anyone can know it is right.

The bound scales with the total: e × 7,000,000 / 2,719 is about 7,000, exceeded by a given thread's estimate with probability at most e−5, 0.0067. The run at 700,000 writes had a median error of 90 against a bound of 700, so the typical error should be near 900, a seventh of the bound, because a counter holds about N/w = 2,574 writes and the smallest of five such counters is well below the average. It is tempting to think the error stays fixed as the stream grows, but the sketch's memory is fixed and its error grows with N.

It works as designed: each of its five counters also holds the writes of every other thread hashed there, about 257 on average, and 93 is the smallest of the five. The guarantee is an absolute error of εN, which is large next to three. A wider sketch brings it down in proportion, 272 to 2,719 counters took the median error from 1,041 to 90, and more rows lower the chance of an unlucky thread. A common mistake is to blame the hash; summing a row, which gives N, and comparing with e·N/w shows the error is the expected one.

An LRU hash evicts the entries used least recently, not the smallest. The heavy threads made their 100,000 writes early in the run, in about 50 ms, and then stopped, while the light threads went on inserting for two seconds. To insert into a full LRU hash, __bpf_lru_list_shrink() in bpf_lru_list.c takes entries from the tail of the inactive list, sparing only those looked up since the last scan, and the heavy threads' entries had not been looked up for most of the run. The count a long-lived, now quiet thread built up is exactly what an LRU hash throws away, and the sketch keeps.

The sixteen 24-byte nodes sit in a few cache lines of one arena page, and every heavy writer finds its own node and stores a new estimate there on each write. With one writer the lines stay in one CPU's cache; with eight, the lines move between CPUs on almost every write, which is the 38 ns. The counters rarely share a line, since keys land at random among 1,700 lines. Updating the table only every hundredth write, or giving each node a line of its own, would cut the traffic; padding nodes to 64 bytes costs 640 bytes more.

Lookup must return a pointer to a value the map stores, and a sketch stores nothing per key; its answer is the minimum of d counters, computed on each query. Peek, as the bloom filter uses it, takes the key in a buffer and can return a number, so the estimate comes back as peek's return value. User space has no such return value, so BPF_MAP_LOOKUP_ELEM on the count-min map reads the key from the value buffer and writes the estimate into the count that follows it, a branch the series adds to bpf_map_copy_value() in syscall.c.

Peek's prototype marks its buffer MEM_UNINIT, written by the call, which is true for a queue. For a bloom filter resolve_map_arg_type() turns it into a buffer the call reads, but stack liveness in v7.2, bpf_helper_stack_access_bytes(), reads only the prototype. It concludes that the key stored before the call is never read, poisons those stack slots when it cleans the state, and the argument check then refuses to read them. Mainline commit 830e4372de5c made liveness ask about bloom filter peeks, which is why a kernel with that fix loads the program.

The fetching OR becomes an atomic instruction that the x86 JIT cannot emit for arena memory: bpf_jit_supports_insn() refuses fetching AND, OR and XOR there, and the verifier, which asks the JIT, prints "BPF_ATOMIC stores into R1 arena is not allowed". A compare-and-swap loop does the same work and is accepted: read the counter, compute the value with the flag set, and retry __sync_val_compare_and_swap() until it succeeds; its return value says whether the flag was already set. A non-fetching OR, whose old value is discarded, is also allowed.

The arena, in most cases. It runs on the kernels the team already has, provided they support arenas and the atomics it uses, needs no change to the kernel, and leaves the team owning its code, its locking and its bugs; user space reads it without a system call. A map type needs the eight patches, maintainers who agree to a permanent uapi value and the kernels that carry it, which can take years to reach a fleet. A kfunc module gives kernel code and speed without a uapi change, but the team then maintains a module against every kernel it runs, since kfuncs promise no stability.
