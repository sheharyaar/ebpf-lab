The argument. Chapter 10 (src/maps.html, "A map for the counter") left the counter on an LRU hash, which forgets the threads written least recently, and said that keeping a count for every thread a server ever ran, in memory fixed in advance, needs approximate counts. A count-min sketch gives them: d rows of w counters, one hash function per row, an update adds one to a counter in each row, and a query returns the smallest of the d counters, which never undercounts and overcounts by at most epsilon times the total with probability 1 - delta when w = ceil(e/epsilon) and d = ceil(ln(1/delta)) (Cormode and Muthukrishnan, "An improved data stream summary: the count-min sketch and its applications", Journal of Algorithms 55(1), 2005: fetch it or its preprint and check the bounds and the notation before you use them). The chapter builds this structure twice, and the comparison is the point: what you get by building it on an arena in an unmodified kernel (chapter 11), against what you get, and what it costs to the kernel and its maintainers, by making it a map type of its own.

Part A, on an arena, on the VM's stock kernel 7.2.15:
- What you see: the counter keeping a count-min sketch in an arena, with a small table of the heaviest threads beside it (a top-k list or min-heap held in the same arena, linked by arena pointers, which is what a plain array map could not hold and so what justifies the arena), read from user space through the arena's mmap with no bpf() call; a workload that a HASH cannot hold (many short-lived threads, for example 100,000 threads that each write a few times, plus a few heavy writers), where the HASH returns -E2BIG and the LRU hash forgets, and the sketch keeps an estimate for every thread.
- How it works: the sketch's layout in the arena, the hash functions (what the program can use: jhash from bpf_helpers? a multiply-shift family you write? check what is available and what the verifier accepts), the update with atomic adds on arena memory (check in v7.2 which BPF_ATOMIC operations the verifier and the x86 JIT accept on arena pointers), the query, and the top-k list; then what chapter 11's limits mean here (kernel pointers cannot live in the arena; data copied to the stack to reach a kernel function).
- Measured, with chapter 10's method (kernel.bpf_stats_enabled, run_time_ns over run_cnt, a writer pinned with taskset): per-event cost against HASH and LRU_HASH; memory (fixed, against the HASH's 82 bytes an entry); accuracy (the estimate against exact counts kept in user space or in a HASH big enough to hold them all: the error distribution against the epsilon-N bound); and the same sketch in a BPF_F_MMAPABLE array map, to show what the arena adds and what it costs over a plain array.
