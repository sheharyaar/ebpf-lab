Chapter 12 of Plan v4, "struct_ops through sched_ext: a program as the CPU scheduler", the second chapter of Part IV, "Extending the kernel". File src/schedext.html, section id "schedext", no data-aliases (it absorbs no old chapter). This chapter is new: every claim is checked against the v7.2 source or a real run in the VM, every number carries its provenance (kernel, VM, date), and point 3's limit on new prose does not apply.
The argument: every program so far has been called at a hook to observe or decide one thing. struct_ops lets a set of BPF programs implement a whole kernel interface, a table of function pointers the kernel calls as it would call a built-in implementation. sched_ext is the largest such interface: a BPF program set becomes a scheduling class. Contrast it, briefly and from the source, with tcp_congestion_ops (net/ipv4/bpf_tcp_ca.c, the first struct_ops user), and name the other users in v7.2 (hid_bpf_ops, net/sched/bpf_qdisc.c, io_uring/bpf-ops.c's io_uring_bpf_ops) without teaching them.
Read first, beyond the brief's list (add sparse paths as needed: kernel/sched/ext* or kernel/sched/ext/, include/linux/sched/ext.h, net/ipv4/bpf_tcp_ca.c, net/sched/bpf_qdisc.c; io_uring and tools/sched_ext are already there): kernel/bpf/bpf_struct_ops.c (BPF_MAP_TYPE_STRUCT_OPS, registration, the trampolines per member, the link), the sched_ext core (sched_ext_ops and its callbacks, dispatch queues, the kfuncs scx_bpf_*, the watchdog and the error exit), Documentation/scheduler/sched-ext.rst (add the path), and tools/sched_ext (scx_simple, scx_qmap and the others; the Makefile and its include directory).
What the chapter covers:
- What you see: the host and the VM kernel have CONFIG_SCHED_CLASS_EXT=y. Build scx_simple from tools/sched_ext of the v7.2 tree (in the VM if that is where the toolchain works; check what it needs and report anything missing rather than installing), run it, and show /sys/kernel/sched_ext/ (state, root/ops), bpftool struct_ops list/dump, and its programs in bpftool prog show; then the write counter running unchanged under it.
- How it works: struct_ops from the loader's side (a SEC(".struct_ops.link") value whose members are programs, BPF_MAP_TYPE_STRUCT_OPS, the update that registers it, the link that holds it) and the kernel's side (bpf_struct_ops_desc, the per-member trampolines, how the verifier checks each member against its BTF prototype); sched_ext: the callbacks a scheduler fills (select_cpu, enqueue, dispatch, running, stopping and the rest; which are required), dispatch queues (the global, the local per-CPU ones, custom DSQs), the kfuncs a scheduler calls (scx_bpf_dsq_insert and others in v7.2: check names, they were renamed in 2024-2025), what happens when the BPF scheduler misbehaves (scx_bpf_error, the runnable-task watchdog, sysrq-S, the fallback to the fair class); arenas in schedulers: what LWN 1019885 says about them (scx_sdt in tools/sched_ext uses one; chapter 11 teaches arenas).
- Inside the v7.2 source: the path from the struct_ops map update to the class switch, and from a wakeup to ops.enqueue and ops.dispatch, with file:line, checked.
- Costs, measured in the VM: scheduler latency and throughput under scx_simple against the default class (perf bench sched messaging and pipe, and one more if available), the per-callback cost (bpftool prog show run_time_ns/run_cnt with kernel.bpf_stats_enabled), memory and load time of the scheduler; one costs box and a decision rule (when a BPF scheduler pays for itself, and when not).
- When it goes wrong: rows from real runs: a scheduler that never dispatches (watchdog ejects it, with the message in dmesg), scx_bpf_error, a struct_ops member with the wrong signature refused by the verifier, a missing required callback, loading a second scheduler while one runs, a struct_ops map whose link is closed; each with the command that confirms it.
- A lab (lab12-1) run in the VM: build and run scx_simple, measure against the default class, then break it on purpose (a dispatch that never runs) and read the watchdog's report; with a solution and expected output.
