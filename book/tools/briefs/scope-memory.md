Chapter 11 of Plan v4, "Memory you manage: allocated objects, kptrs, lists and trees, arenas", the first chapter of Part IV, "Extending the kernel". File src/memory.html, section id "memory", no data-aliases (it absorbs no old chapter). This chapter is new: every claim is checked against the v7.2 source or a real run in the VM, every number carries its provenance (kernel, VM, date), and point 3's limit on new prose does not apply.
Where it starts: chapter 10 (src/maps.html) ends on what maps cannot do: a map is a fixed table the kernel allocates up front, keyed lookups only, no pointers between entries, no structure the program shapes itself. This chapter is the memory a program allocates and links itself, in two models: objects the verifier tracks one by one (bpf_obj_new and its kin, kptrs, lists and red-black trees, reference counts), and the arena, a region of pages shared with user space where the program builds any data structure and the verifier gives up tracking individual objects.
Read first, beyond the brief's list: kernel/bpf/helpers.c (the bpf_obj_*, bpf_list_*, bpf_rbtree_*, bpf_refcount_acquire, bpf_kptr_xchg kfuncs), kernel/bpf/memalloc.c (the BPF memory allocator), kernel/bpf/arena.c, the verifier's handling of these (search verifier.c for KF_ARG_PTR_TO_LIST_HEAD, bpf_spin_lock, PTR_TO_ARENA / addr_space_cast, and the kptr checks), Documentation/bpf/ (graph_ds_impl.rst, kfuncs.rst, map_arena or similar if v7.2 has it), and the selftests' arena helpers: tools/testing/selftests/bpf/bpf_arena_alloc.h, bpf_arena_list.h, bpf_arena_htab.h and their progs. Fetch and read LWN 1019885 ("Arenas in sched_ext", Daroc Alden, 13 May 2025, LSFMM+BPF) with the ctx tools: it is the source of this chapter's argument about the arena's limits (kernel pointers cannot be stored in an arena; data must be copied to the stack to reach kernel functions; the verifier types arena and stack pointers differently, so helpers get duplicated or inlined; Alexei Starovoitov: mixing the two is hard, work in progress). Check each limit against v7.2 and say what has changed since May 2025, if anything.
What the chapter covers, each shown with the write counter or a small program you write:
- What you see: the counter rewritten to keep its per-thread counts in an object it allocates (one bpf_obj_new per thread, linked into an rbtree keyed by pid under a bpf_spin_lock, the tree's root in a map value), loaded and run in the VM, with bpftool showing what it holds; and the same counts in an arena hash table built from the selftests' bpf_arena_htab.h, read from user space through the arena's mmap without a single bpf() call.
- How it works: what bpf_obj_new returns and what the verifier tracks about it (an owning reference that must be dropped, pushed into a collection, or stored as a kptr before exit); kptrs in map values (__kptr, bpf_kptr_xchg, who frees what); collections: bpf_list_head / bpf_rb_root with __contains, the lock that must be held, owning and non-owning references after a push, bpf_refcount for shared ownership; the BPF memory allocator (per-CPU caches, why it can run in any context, what it costs); arenas: the map type, its size and flags, user-space mmap, address_space(1) pointers and the verifier's casts between kernel and user addresses, pages allocated on demand (bpf_arena_alloc_pages) and faults handled, and why the verifier cannot type what lives in an arena.
- Inside the v7.2 source: the functions above with file:line, checked.
- Costs, measured in the VM: allocation and free latency (bpf_obj_new / bpf_obj_drop, arena page allocation), memory per element (object header, rbtree node, arena page granularity), the counter's per-event cost with an rbtree against a HASH map (chapter 10's method) and against an arena hash; locking (the spin lock's cost, contention across CPUs). One costs box, then a decision rule: when a map, when objects and collections, when an arena.
- When it goes wrong: rows from real messages you trigger in the VM, for example an object never dropped ("Unreleased reference"), a list or tree used without its lock, a kptr stored without xchg, a pointer from the arena passed to a kernel function, a kernel pointer stored into the arena, an arena access past its size, an allocation from a context that cannot (if any); each with the command that confirms it.
- A lab (lab11-1) run in the VM: the counter on an rbtree and on an arena hash, measured against the HASH version; with a solution and expected output. Figures at least one per 450 words; candidates: the two memory models side by side as a table, an owning reference's life (alloc → push → pop → drop) as a flowchart, the arena's address translation (program view, kernel view, user-space view of one page).
- Go deeper: LWN 1019885, the arena commits (BPF_MAP_TYPE_ARENA's introduction), the graph data structures commits (bpf_obj_new, lists, rbtrees), the BPF memory allocator's commit; each sha verified on git.kernel.org.
