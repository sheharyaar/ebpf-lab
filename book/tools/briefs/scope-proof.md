The argument. The refresher before it (src/ch17.html, "Formal proving: a refresher, and the reads to do first") defines a specification, soundness and completeness, abstract values, and what an SMT solver is asked, and checks tnum_mul on four bits with a plain-Python exhaustive checker (labs/ch17-check.py); its Z3 query was shown but not run, because Z3 was not installed then. This chapter does the work the refresher prepares: one soundness proof carried out by hand, the same property proved by a solver at the full 64-bit width where no exhaustive check can reach, and a real bug the kernel shipped and fixed, found by the solver as a counterexample. The reader leaves able to state a soundness property of a verifier operation, check it on small widths, prove it at full width, and read a counterexample.

Tools. Z3 is installed for the book in a venv in the book folder: book/.venv (z3-solver 5.4.1, created 2026-11-13). Run every script with book/.venv/bin/python -I. Do not install anything else; if you need another package, stop and report. The chapter's lab tells the reader how to make the same venv (python -m venv .venv; .venv/bin/pip install z3-solver) and gives the version you used.

Read first, beyond the brief's list: src/ch17.html and labs/ch17-check.py in full (do not repeat its definitions: refer to them with xrefs); src/numbers.html (chapter 6, how the verifier tracks numbers: tnums, ranges, the 32-bit halves; refer to it); kernel/bpf/tnum.c in v7.2 (tnum_add, tnum_and, tnum_or, tnum_mul and the rest); the scalar range functions in kernel/bpf/verifier.c for AND, OR and XOR (scalar32_min_max_and and its kin, and scalar_min_max_*), with file:line; the CGO 2022 tnum paper (Vishwanathan, Shachnai, Narayana, Nagarakatte, "Sound, Precise, and Fast Abstract Interpretation with Tristate Numbers": fetch it, check what it proves and how, and cite it accurately); "Programming Z3" (Bjørner, de Moura, Nachmanson, Wintersteiger), the bit-vector sections.

What the chapter covers:
- What you see: the plain-Python checker of the refresher run on one tnum operation at 4 and 8 bits (and how its run time grows, measured, so the reader sees why 64 bits needs a different method), then the same property handed to Z3 at 64 bits, answered unsat in measured seconds.
- One proof by hand: pick one operation (tnum_and is the natural first, tnum_add if you can keep the proof readable; say why you chose it). State the soundness property precisely in the refresher's terms, using the membership relation of a tnum (x is in (v, m) when x & ~m == v, with v & m == 0 as well-formedness), and prove it for n bits on paper, step by step, each step justified. Check every step's claim against the 4-bit exhaustive check, so the proof and the checker agree visibly.
- The same in Z3: how the property becomes a query (bit-vectors of width 64, the well-formedness constraints as assumptions, the negated property, unsat meaning proved, sat meaning a counterexample with a model); the full script listing (at most 80 characters a line); timings at 8, 16, 32 and 64 bits on the host, measured; what happens with a deliberately wrong version (an off-by-one or a dropped term in the operation), so the reader sees a sat answer and reads its model.
- One bug by solver: the 2021 bug in the verifier's 32-bit bounds tracking for AND, OR and XOR (CVE-2021-3490), introduced with explicit ALU32 bounds tracking and fixed in 2021. Find the introducing and fixing commits and verify both shas and release versions on git.kernel.org (do not trust a sha from memory, this brief's or yours). Fetch the buggy function from the kernel release that had it and the fixed one, encode each as Z3 constraints faithfully (show the C beside the encoding), and state the property the verifier needs: every concrete 32-bit result of the operation lies within the computed bounds. Z3 should return a counterexample for the buggy version (show it as concrete register values and the bounds the old code computed for them) and unsat for the fixed version. Then show what v7.2 computes for the same inputs, from its source and, if practical, a verifier log in the VM. Keep this educational: explain why wrong bounds break the verifier's promise, but do not write or describe an exploit, privilege escalation steps, or a program meant to abuse the bug.
- What it costs: a costs box adapted to this part: solver time against bit width, script length against the C it models, what an exhaustive check costs per bit, and the memory Z3 used, all measured on the host (say which CPU); then a decision rule (when an exhaustive check on small widths is enough, when a solver is needed, when a hand proof is worth writing).
- When it goes wrong: rows from real runs of your scripts, for example a missing well-formedness assumption that makes Z3 report a bogus counterexample, signed against unsigned comparison operators in Z3 (the difference between < and ULT on bit-vectors), mixing Python integers and bit-vectors of different widths, a query that times out, reading sat as "proved", and an encoding that is not faithful to the C (sign extension, 32-bit halves); each with the command that shows it.
