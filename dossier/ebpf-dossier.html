Two machines, twenty-one years apart

Still runningThe left column has not gone away. Run tcpdump -d 'tcp port 22': it prints the classic program tcpdump compiles. Linux rewrites such filters into the new instructions before it runs them.

Look at the left side of the two-machines figure (figure 1.1). That is the 1993 machine: the accumulator A, an index register X, a few words of scratch memory, and one packet in. Linux ran it for years for tcpdump's socket filters, and later for seccomp's system-call filters.

In 2014 Alexei Starovoitov rebuilt that machine inside the kernel as the one on the right. LWN called it "internal BPF" at the time; the kernel documentation now calls it eBPF, extended BPF. Linux 3.15 shipped it in June 2014 and converted every classic filter into the new instructions, so tcpdump never noticed.

Read the right column top to bottom. Each row answers a limit of the left one. Ten 64-bit registers, r0 to r9, match the registers of a modern 64-bit CPU.

A read-only frame pointer, r10, points at a small stack. A call instruction reaches into the kernel. Linux 3.18 added maps in December 2014, so a program could keep state between runs.

"The latter expands the set of available registers from two to ten, adds a number of instructions that closely match real hardware instructions, implements 64-bit registers, makes it possible for BPF programs to call a (rigidly controlled) set of kernel functions, and more."

Jonathan Corbet, "BPF: the universal in-kernel virtual machine", LWN, 21 May 2014

Eight bytes per instruction

Every eBPF instruction is eight bytes, cut into the fields of the encoding figure (figure 1.2). The first byte is the opcode: what to do, such as move, add, jump or call. The next byte holds two register numbers of four bits each, a source and a destination. Then come a signed 16-bit offset, used for memory addresses and jump distances, and a signed 32-bit immediate, a constant carried inside the instruction.

The two lower rows are your own program. Slot 4 is bf a2: a 64-bit move whose source is r10 and whose destination is r2. Slot 8 is 85, the call opcode, with 1 in its immediate. Your machine is little-endian, so the bytes 01 00 00 00 are the number 1. Together these instructions are your program's bytecode: what clang -target bpf writes into the object file, and what the kernel receives.

One kind of instruction does not fit in eight bytes. Loading a full 64-bit constant needs a wide instruction, which takes two slots and sixteen bytes. Your program has three of them. That is why the disassembler's slot numbers jump from 6 to 8.

Calling into the kernel

Your program calls into the kernel four times; the bytecode figure (figure 1.3) highlights the first two. Each target is a helper function: a function inside the kernel that a program may call by number. That number is the helper ID, and it sits in the immediate. Helper 14 returns the current process and thread IDs, and helper 1 looks up a key in a map. The full list is the BPF_FUNC_ enum in the vmlinux.h your program already includes.

Your slot 1Slot 1 stores w0, the low 32 bits of r0; every register has a w name for its low half. Helper 14 puts the thread ID in that low half and the process ID in the high half, so your table counts writes per thread. In a single-threaded process the two numbers are the same.

Arguments reach a helper through a fixed calling convention, stepped through in the helper-call figure (figure 1.4). Registers r1 to r5 carry up to five arguments, and r0 carries the answer back. After the call, r1 to r5 cannot be read; the kernel documentation says they are "reset to unreadable". Registers r6 to r9 keep their values across the call, and r10 never changes.

Watch r1 in your listing. The map goes into r1 at slot 6 and again at slot 21, because no value in r1 is kept across a call. A value the program needs after a call has to be parked in r6 to r9.

Five arguments is a deliberate limit. A 64-bit CPU passes a function's first arguments in registers, and r1 to r5 can sit in exactly those registers. On x86-64 the kernel documentation pairs r1 with rdi and r0 with rax, the registers an ordinary kernel function already uses. A call from a program then needs no registers shuffled before it.

Recap

The 2014 machine keeps the 1993 shape and widens it: ten 64-bit registers, a read-only frame pointer over a stack, calls into the kernel, and maps. Every instruction is eight bytes, cut into opcode, two register numbers, offset and immediate; a 64-bit constant takes a second slot. A helper call carries the helper's ID in the immediate, its arguments in r1 to r5 and its answer in r0, and it leaves r1 to r5 unreadable.

One log line, one source line

Remove the NULL check from your write counter and load it. The log ends with a line of statistics, and the line just above it gives the reason: R0 invalid mem access 'map_value_or_null'. One verbose() call printed it. Search the v7.2 tree for its fixed middle, as in the search figure (figure 10.1), and two lines of kernel/bpf/verifier.c come back.

Read upward from each hit to the branch around it. Line 6164 sits in the branch for a different kind of pointer. Line 6322 is the last else of check_mem_access(), the function that checks every load and store through a pointer. It catches every pointer type that no earlier branch accepted.

Your broken copyThe broken copy also shows the calling convention from the bytecode chapter at work. Clang moved the key pointer into r6 before the call, because the program needs it again afterwards and r1 to r5 do not keep their values.

Line 6106 says why your r0 was not accepted. The map-value branch compares the type with ==, so it takes a plain map value and nothing else. Your r0 still carried the maybe-NULL flag from the lookup, and log.c prints that flag as the suffix _or_null. The kernel never says "you forgot the check". It says that this type may not be read through here.

The map around that line

check_mem_access() is one stop on a longer trip, drawn in the verifier-map figure (figure 10.2). Each time a program is loaded, the kernel runs bpf_check() once. It checks the program's shape, walks every path, then rewrites the program for running. In v7.2 those phases live in separate files: the shape check in cfg.c, the state comparison behind pruning in states.c, the rewrites in fixups.c, and the log's wording in log.c.

The walk stays in verifier.c. Its loop, do_check(), hands each instruction to do_check_insn(), which picks a checker by the kind of instruction: arithmetic, load, store, call or jump. Your call, your test and your load go to three different checkers.

The three-stops figure (figure 10.3) follows them. At the call, check_helper_call() resets r1 to r5 at line 10414 and gives r0 the map-value type, flag and all, at line 10455. At your test, check_cond_jmp_op() splits the state in two. On one branch r0 becomes a plain map value; on the other it becomes the number 0. At the load, line 6106 accepts only the first.

A comment that is wrongNo code in v7.2, or in bpf-next on 11 November 2026, uses CONST_IMM. Line 15689 makes the false branch a scalar known to be zero. A comment that disagrees with the code is a classic first patch. Search the list archive before you write it.

"When type PTR_TO_MAP_VALUE_OR_NULL passes through 'if (reg != 0) goto +off' insn, the register holding that pointer in the true branch changes state to PTR_TO_MAP_VALUE and the same register changes state to CONST_IMM in the false branch. See check_cond_jmp_op()."

The test that pins your message, and the road upstream

A message a user can hit is pinned by a selftest: a test kept in the kernel tree, under tools/testing/selftests/bpf. Search the v7.2 selftests for your full message and six files under progs/ come back. One of them, verifier_map_ret_val.c, holds a test called "don't check return value before access". Its body is your bug in BPF assembly: r2 = r10, a call to the lookup, then a write through r0 with no test.

The test annotations above it, __failure and __msg("R0 invalid mem access 'map_value_or_null'"), tell the test runner to load the program, expect a rejection, and find that text in the log. Reword the message in check_mem_access() and this test fails. That is the point. The BPF maintainers' guide asks for a test with every change to verifier behaviour, because behaviour that no test tracks "could potentially be subject to change".

The road-upstream figure (figure 10.4) is the rest of the trip, also from that guide. Fixes go to the bpf tree; features and cleanups go to the bpf-next tree. You can run BPF CI, the maintainers' test system on GitHub, before anyone reads your patch. Then it goes to bpf@vger.kernel.org with PATCH bpf-next in its subject. It waits in patchwork, the review queue, and reaches mainline through net-next.

Answer key

Chapter 1

1.1

24 instructions in 216 bytes. Every slot is eight bytes, so the section holds 27 × 8 = 216 bytes. Three of the slots are the second halves of wide instructions, so there are 27 − 3 = 24 instructions. Check it with llvm-readelf -S /tmp/hashmap.bpf.o: the section named after your hook has size 0xd8, which is 216. The near-miss is 27 instructions: the disassembler numbers slots, which is why the line after the wide instruction at slot 6 is slot 8.

1.2

The program read r1 after a call, and after a call r1 holds nothing readable. A helper call leaves r1 to r5 unreadable whatever the helper did, so after call 1 the map is no longer in r1. Load the map into r1 again before the next call, as your own slot 21 does, or keep a value you need in r6 to r9. The rule is in the kernel's "Classic BPF vs eBPF" page: after a call, "R1 - R5 are reset to unreadable". The near-miss is to think the helper overwrote r1 with junk; the kernel never looks at what the helper did, it applies the rule to every call.

1.3

No. The zero is a placeholder. The line under it, R_BPF_64_64 write_counts, is a relocation: a note telling the loader that this instruction must point at the map named write_counts. The map does not exist yet when clang writes the file. When your loader creates it, libbpf writes the map's file descriptor into the instruction and marks it as a map reference, and the kernel swaps in the map itself; section 5.4 of the RFC lists that form. The load-and-attach chapter walks through it. The near-miss is to read 0x0 as NULL; nothing runs from the file as written.

1.4

The jump class, and a call that takes its target from the immediate. The low three bits of 0x85 are 101, which is 0x5, the JMP class in the class table of section 3.3. The top four bits are 1000, which is 0x8, CALL in the jump table of section 4.3. The bit between them is 0, which section 4 calls K: the operand is the immediate. The near-miss is to look for CALL among the arithmetic instructions; CALL and EXIT both live in the jump class.

1.5

Because the immediate holds only 32 bits. A 64-bit constant, such as an address, cannot fit in one slot, so the wide encoding of section 3.2 appends a second eight bytes whose immediate carries the upper half. Section 5.4 gives the arithmetic: dst = (next_imm << 32) | imm. Your object uses it three times, twice for the map and once for the bpf_printk format string. The near-miss is to think the wide form exists for long jumps; in this standard only the 64-bit immediate loads use it.

1.6

An ID, and nothing else about the helper. Section 4.3.1 says a helper was identified by a static ID in the immediate, and that platforms with kernel type information may put a type ID there instead. What each helper does, which arguments it takes and what it returns are left to the platform: on Linux, the kernel's helper documentation and the BPF_FUNC_ list. That is why helper 1 means "map lookup" on Linux without the standard saying so. The near-miss is to expect the RFC to list helpers; it leaves that to future work.

Chapter 10

10.1

10: (79) r1 = *(u64 *)(r0 +0), then R0 invalid mem access 'map_value_or_null'. The verifier prints each instruction as it checks it, opcode in hex, stops at the first rule that fails, and then prints one statistics line that starts with processed. The opcode is a load into a register: class LDX is 0x1, mode MEM is 3 shifted to 0x60, size DW is 3 shifted to 0x18, and 0x1 + 0x60 + 0x18 = 0x79. Check the line format in kernel/bpf/disasm.c, which prints "(%02x) r%d = *(%s *)(r%d %+d)". The near-miss is slot 9, the call: the call is legal, and only the read through r0 is not.

10.2

No. It moved and was renamed. In v7.2 the shape check is bpf_check_cfg() in kernel/bpf/cfg.c, still called from bpf_check() before the walk, still a depth-first search that reports jumps out of range, unreachable instructions and back-edges. Search for a message instead of the function name: grep -rn "unreachable insn" kernel/bpf finds the code in cfg.c, and otherwise only the design comment. The near-miss is to trust the old name and conclude the check is gone. Function names and files drift between releases; the two-pass design has not changed since 2014.

10.3

The test still expects the old wording. Its __msg(...) annotation names the exact text, the runner searched the new log and did not find it, and test_loader.c reports that as expect_msg. That is the test doing its job: the message is behaviour, and someone depends on it. If the rewording is worth making, the same patch series must update every test that pins the old text, which you find with grep -rln over the selftests. The near-miss is to think the kernel broke; the program was rejected just as before, only in different words.

10.4

bpf-next, with PATCH bpf-next in the subject. The guide sends fixes to the bpf tree and "features, cleanups or other kind of improvements" to bpf-next, and a comment correction is a cleanup. It gives the exact command, git format-patch --subject-prefix='PATCH bpf-next'. A Fixes: tag is required only for fixes. Before you write the patch, check that the comment is still wrong in today's bpf-next and that nobody has sent the same patch to the list. The near-miss is to send it to bpf because "it fixes something"; the code was never wrong, only its description.

10.5

Test cases in the BPF selftests. The guide says that for a change to verifier behaviour "it is absolutely necessary to add test cases", and that the maintainers "might ask for them before accepting any changes". The reason is in the same answer: behaviour that no test tracks "could potentially be subject to change", because the next person to touch the verifier has nothing to tell them it mattered. In practice you add a function with __success or __failure and __msg(...) to a progs/verifier_*.c file. The near-miss is to think tests are optional for small changes; small verifier changes are the ones most likely to break an existing program.

10.6

The selftests from the 7.2 tree. The guide's rule is "If you run a kernel xyz, then always run the BPF kernel selftests from that kernel xyz as well." Newer selftests are adapted to a newer verifier, which tracks more and accepts programs an older one refuses, so they can fail on 7.2 for reasons that have nothing to do with your change. The tag you cloned for this chapter, v7.2, already has the matching selftests. The near-miss is to fetch the newest bpf-next tests and read their failures as bugs in your kernel.

Glossary

Chapter 1

bytecode
a program's instructions as stored in the object file and handed to the kernel
calling convention
arguments in r1 to r5, answer in r0, r6 to r10 kept across a call
eBPF
extended BPF: the 64-bit instruction set Linux has run since 3.15
frame pointer
r10, read-only, the address of the program's stack
helper function
a kernel function a program may call by number
helper ID
that number, carried in a call's immediate
immediate
a signed 32-bit constant carried inside the instruction
instruction
one eight-byte unit of a program
offset
a signed 16-bit field for memory addresses and jump distances
opcode
the first byte of an instruction: what to do
register
one of r0 to r10, each 64 bits; w0 to w10 name their low 32 bits
wide instruction
a 64-bit constant load that takes two slots

Chapter 10

BPF CI
the maintainers' automatic test runs, started from a pull request on GitHub
bpf tree
the git tree for BPF fixes
bpf-next tree
the git tree for BPF features, cleanups and improvements
patchwork
the web queue where patches sent to the list wait for review
selftest
a test kept in the kernel tree; the BPF ones live under tools/testing/selftests/bpf
test annotations
markers such as __failure and __msg(...) that tell the test runner what result to expect
