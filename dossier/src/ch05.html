Three logs from one program

These are the last lines of three failed loads. Each comes from a copy of your write counter with one line changed, loaded on the kernel you run. The text is the verifier log: what the verifier writes as it walks, one line per instruction, then the reason it stopped, then a line of statistics.

The log never reaches the kernel's own message buffer. The load call carries a buffer, its size and a level, the fields log_buf, log_size and log_level in include/uapi/linux/bpf.h, and the verifier writes only there. libbpf first loads with no log at all. If that fails, it loads again with one and prints the result between BEGIN PROG LOAD LOG and END PROG LOAD LOG. Your loader sets no print function of its own, so the log lands on standard error, just above your "Failed to open and load BPF skeleton".

How much the verifier writes is the log level. Level 1, the one libbpf asks for after a failure, prints each instruction walked and the registers it changed. Level 2 prints the whole state at every instruction, and 4 adds the statistics; bpftool -d asks for 1, 2 and 4 together. Level 1 also forgets. When a path is proved safe and the walk goes back for another, pop_stack() in verifier.c rewinds the log to where that path began, so what is left is the path that failed.

Three error codesThe two rule breaks fail with -EACCES and the loop with -E2BIG; libbpf prints the code on its "failed to load" line. A helper the program type does not allow gives -EINVAL. The code alone says which kind of no it was.

Reading one log from the bottom

Read a log from the bottom up, as the log-parts figure (figure 5.2) does with log (b). The last line is statistics, printed even when the load fails; skip it unless the reason is the limit. Above it is the reason. Above the reason is the instruction the walk stopped at, with its slot and opcode, and above that is the walk itself, interleaved with your C lines, which the kernel takes from the object's BTF.

The reason names a rule and usually a register. From there the search goes upward: find where that register took on the state the rule refused. In log (b) the entry at slot 9 shows vs=8, and the reason says off=8 size=8. Eight bytes read from offset eight end past the end of an eight-byte value.

"However, when the verifier rejects a program, the unclear error makes repair challenging: the error reports where verification stopped, not where the program lost the proof the verifier required."

Yusheng Zheng and seven co-authors, "Characterizing and Bridging the Diagnostic Gap in eBPF Verifier Rejections", arXiv 2607.02748, July 2026 (abstract)

From message to rule

The message-to-rule figure (figure 5.3) puts the three side by side. Log (a) breaks the pointer-or-NULL rule from the last chapter. The read at slot 10 is a correct read of a map value; what is missing is the test that should come between the lookup and it.

Log (b) breaks the bounds rule, and here the fix is on the line the log quotes: the + 1. Log (c) breaks the instruction limit. The loop's bound is read from the map, so no round can be shown to be the last, and r7 had reached 0x1e841, about 125,000 rounds, when the walk gave up. Cap the loop with i < *curr_val && i < 16 and the same copy loads after 190 instructions.

The study behind the field note found single messages with as many as nine different causes. The message tells you which rule; only the walk above it tells you where. A later chapter, on the verifier's source, follows log (a) into the kernel's own code.

The other side of the logResearchers find verifier bugs by running this chapter backwards. They generate programs, then flag any where the verifier's verdict disagrees with what the program really does or with a written specification: State Embedding (OSDI 2024), BVF (EuroSys 2024) and Veritas (SOSP 2025). Between them they found more than two dozen verifier bugs.

Recap

A refused load returns a verifier log: the walk, the instruction where it stopped, the reason, and a statistics line. libbpf asks for it at log level 1 only after a failure, and level 1 keeps only the path that failed. Read it from the bottom: the reason names a rule and a register, and the walk above shows where that register lost what the rule needed. Your three copies broke the pointer-or-NULL rule, the bounds rule and the instruction limit, and only the bounds fix sat on the line where the walk stopped.

5.1

About eight: 1,000,001 ÷ 124,993 ≈ 8.0. Seven are the loop body, slots 16 to 23 with the wide load at 16 counted once. The eighth is the exit side of slot 23's test. The walk follows the fall-through first, out of the loop to slot 24, finds a saved state there that covers it, because r7 is never read after the loop, and prunes it at once. Then it comes back for the next round. The accepted copy with the cap shows this directly: at log level 2 its exit side is pruned once per round. The near-miss is seven, which forgets that every round also checks the way out.

5.2

A type rule: the instruction reads memory through r1, and r1 holds a scalar, a plain number, which may never be used as an address. Climb the log to the last line whose entry after the ; changed R1. That line is where r1 became a number, often a load from a map value or a helper's return value, such as your own slot 10, r1 = *(u64 *)(r0 +0), which leaves R1=scalar(). The fix is wherever the program meant to keep a pointer and kept a number instead. The near-miss is to fix the offset on the stopping line: the address was never an address.

5.3

The verifier erased them. At log level 1, which libbpf asks for after a failure, each finished path is wound back out of the log: when the walk returns for a kept branch, pop_stack() in kernel/bpf/verifier.c resets the log to where that branch was saved. Only at level 2 are the lines kept. What you see is the path that failed. To see every path, load with sudo bpftool -d prog load, which asks for levels 1, 2 and 4. The near-miss is to conclude that the other side was never checked; it was checked, accepted and then removed from the text.

Expected output. The ends of the three logs, abridged; each is followed by a statistics line. They were run on 12 November 2026 on kernel 7.2.15-arch1-1 with bpftool v7.8.0 and clang 23, in a throwaway virtual machine booted with virtme-ng (vng), as root inside it, using the same script. The map's address differs on every load.

What this shows. Key: a helper's arguments have types, and the key must be a pointer the program may read, such as the stack; the thread ID is a scalar. That is the second half of the promise figure's fifth row, and the proof was lost at slots 5 to 7, where r2 was built from a number. Redirect: each program type allows its own list of helpers, and the type your write counter has may not redirect packets; the first half of the fifth row, lost at the call itself. Var: the bounds rule again, fourth row. Here the offset is 0 or 8, so the smallest access fits and the largest does not, which is why the reason says max where log (b), with a fixed offset of 8, said min. The proof was lost at slot 13, where the offset joined the pointer.

Common wrong turn. Reading the long expected= list as a list of things to try. It lists every pointer type the key may be; the fix is to pass &pid again. The other is to read off=8 in the third log as a fixed offset of 8; the instruction says r0 +0, and the 8 is the largest value of the variable part.
