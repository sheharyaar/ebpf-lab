One log line, one source line

Remove the NULL check from your write counter and load it. The log ends with a line of statistics, and the line just above it gives the reason: R0 invalid mem access 'map_value_or_null'. One verbose() call printed it. Search the v7.2 tree for its fixed middle, as in the search figure (figure 10.1), and two lines of kernel/bpf/verifier.c come back.

Read upward from each hit to the branch around it. Line 6164 sits in the branch for a different kind of pointer. Line 6322 is the last else of check_mem_access(), the function that checks every load and store through a pointer. It catches every pointer type that no earlier branch accepted.

Line 6106 says why your r0 was not accepted. The map-value branch compares the type with ==, so it takes a plain map value and nothing else. Your r0 still carried the maybe-NULL flag from the lookup, and log.c prints that flag as the suffix _or_null. The kernel never says "you forgot the check". It says that this type may not be read through here.

Your broken copyThe broken copy also shows the calling convention from the bytecode chapter at work. Clang moved the key pointer into r6 before the call, because the program needs it again afterwards and r1 to r5 do not keep their values.

The map around that line

check_mem_access() is one stop on a longer trip, drawn in the verifier-map figure (figure 10.2). Each time a program is loaded, the kernel runs bpf_check() once. It checks the program's shape, walks every path, then rewrites the program for running. In v7.2 those phases live in separate files: the shape check in cfg.c, the state comparison behind pruning in states.c, the rewrites in fixups.c, and the log's wording in log.c.

The walk stays in verifier.c. Its loop, do_check(), hands each instruction to do_check_insn(), which picks a checker by the kind of instruction: arithmetic, load, store, call or jump. Your call, your test and your load go to three different checkers.

The three-stops figure (figure 10.3) follows them. At the call, check_helper_call() resets r1 to r5 at line 10414 and gives r0 the map-value type, flag and all, at line 10455. At your test, check_cond_jmp_op() splits the state in two. On one branch r0 becomes a plain map value; on the other it becomes the number 0. At the load, line 6106 accepts only the first.

"When type PTR_TO_MAP_VALUE_OR_NULL passes through 'if (reg != 0) goto +off' insn, the register holding that pointer in the true branch changes state to PTR_TO_MAP_VALUE and the same register changes state to CONST_IMM in the false branch. See check_cond_jmp_op()."

The test that pins your message, and the road upstream

A message a user can hit is pinned by a selftest: a test kept in the kernel tree, under tools/testing/selftests/bpf. Search the v7.2 selftests for your full message and six files under progs/ come back. One of them, verifier_map_ret_val.c, holds a test called "don't check return value before access". Its body is your bug in BPF assembly: r2 = r10, a call to the lookup, then a write through r0 with no test.

The test annotations above it, __failure and __msg("R0 invalid mem access 'map_value_or_null'"), tell the test runner to load the program, expect a rejection, and find that text in the log. Reword the message in check_mem_access() and this test fails. That is the point. The BPF maintainers' guide asks for a test with every change to verifier behaviour, because behaviour that no test tracks "could potentially be subject to change".

The road-upstream figure (figure 10.4) is the rest of the trip, also from that guide. Fixes go to the bpf tree; features and cleanups go to the bpf-next tree. You can run BPF CI, the maintainers' test system on GitHub, before anyone reads your patch. Then it goes to bpf@vger.kernel.org with PATCH bpf-next in its subject. It waits in patchwork, the review queue, and reaches mainline through net-next.

Recap

A rejection is one verbose() call; yours is line 6322 of verifier.c in v7.2, the last branch of check_mem_access(), reached because line 6106 accepts only a plain map value. The call to the lookup marked r0 "maybe NULL", and only a test of r0 clears that flag. The walk lives in verifier.c, while the shape check, pruning comparison, rewrites and log wording live in their own files. A selftest pins the message, and a change to verifier behaviour goes upstream with a test, to bpf for fixes and bpf-next for everything else.

10.1

10: (79) r1 = *(u64 *)(r0 +0), then R0 invalid mem access 'map_value_or_null'. The verifier prints each instruction as it checks it, opcode in hex, stops at the first rule that fails, and then prints one statistics line that starts with processed. The opcode is a load into a register: class LDX is 0x1, mode MEM is 3 shifted to 0x60, size DW is 3 shifted to 0x18, and 0x1 + 0x60 + 0x18 = 0x79. Check the line format in kernel/bpf/disasm.c, which prints "(%02x) r%d = *(%s *)(r%d %+d)". The near-miss is slot 9, the call: the call is legal, and only the read through r0 is not.

10.2

No. It moved and was renamed. In v7.2 the shape check is bpf_check_cfg() in kernel/bpf/cfg.c, still called from bpf_check() before the walk, still a depth-first search that reports jumps out of range, unreachable instructions and back-edges. Search for a message instead of the function name: grep -rn "unreachable insn" kernel/bpf finds the code in cfg.c, and otherwise only the design comment. The near-miss is to trust the old name and conclude the check is gone. Function names and files drift between releases; the two-pass design has not changed since 2014.

10.3

The test still expects the old wording. Its __msg(...) annotation names the exact text, the runner searched the new log and did not find it, and test_loader.c reports that as expect_msg. That is the test doing its job: the message is behaviour, and someone depends on it. If the rewording is worth making, the same patch series must update every test that pins the old text, which you find with grep -rln over the selftests. The near-miss is to think the kernel broke; the program was rejected just as before, only in different words.

10.4

bpf-next, with PATCH bpf-next in the subject. The guide sends fixes to the bpf tree and "features, cleanups or other kind of improvements" to bpf-next, and a comment correction is a cleanup. It gives the exact command, git format-patch --subject-prefix='PATCH bpf-next'. A Fixes: tag is required only for fixes. Before you write the patch, check that the comment is still wrong in today's bpf-next and that nobody has sent the same patch to the list. The near-miss is to send it to bpf because "it fixes something"; the code was never wrong, only its description.

10.5

Test cases in the BPF selftests. The guide says that for a change to verifier behaviour "it is absolutely necessary to add test cases", and that the maintainers "might ask for them before accepting any changes". The reason is in the same answer: behaviour that no test tracks "could potentially be subject to change", because the next person to touch the verifier has nothing to tell them it mattered. In practice you add a function with __success or __failure and __msg(...) to a progs/verifier_*.c file. The near-miss is to think tests are optional for small changes; small verifier changes are the ones most likely to break an existing program.

10.6

The selftests from the 7.2 tree. The guide's rule is "If you run a kernel xyz, then always run the BPF kernel selftests from that kernel xyz as well." Newer selftests are adapted to a newer verifier, which tracks more and accepts programs an older one refuses, so they can fail on 7.2 for reasons that have nothing to do with your change. The tag you cloned for this chapter, v7.2, already has the matching selftests. The near-miss is to fetch the newest bpf-next tests and read their failures as bugs in your kernel.
