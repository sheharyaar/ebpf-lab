One million instructions

One million: that is how many instructions the kernel will walk through your program before it gives up. The number is BPF_COMPLEXITY_LIMIT_INSNS in include/linux/bpf.h, next to the comment "yes. 1M insns". Until Linux 5.2 a program could have at most 4096 instructions. Your write counter needed 36.

The part of the kernel that does this walking is the verifier. It runs inside the load from the load-and-attach chapter, before any hook sees the program. Its job is the promise figure (figure 4.1): six things a loaded program never does. If it cannot show all six on every path, the load fails and nothing runs.

The page lagsThe kernel's verifier page still opens by saying the first step disallows loops. That was true before 5.3. In v7.2, push_insn() in kernel/bpf/cfg.c refuses a backward jump only when the loader lacks CAP_BPF.

It works in two steps. The shape check looks at every jump once: none may leave the program, and every instruction must be reachable. Then the walk starts at the first instruction and follows every path, one route from the start to an exit that takes one side at each branch.

The promise covers safety and nothing else. Your counter keys its map by thread ID, as the bytecode chapter noticed, and the verifier has no opinion about that. It checks what the program may touch. What the program counts is up to you.

Walking your program

Your program has one branch, the test of r0 at slot 9, so it has two paths. The walk figure (figure 4.2) follows them. At each instruction the verifier updates its verifier state: for every register and stack slot, what kind of value it holds.

After the lookup at slot 8, r0 is a pointer-or-NULL: it points at a map value or it is NULL, and the kernel cannot know which. Nothing may be read through it. At slot 9 the walk splits. On the fall-through side the test has shown that r0 is not zero, so r0 becomes a plain map value and slot 10 may read it. The other side, where r0 is 0, waits on a list until the first path reaches its exit.

The second path starts at slot 12 and stops at slot 25. On the first path the verifier saved its state there. It compares the two and finds them equal in everything the rest of the program still uses, so the rest is already proved. Cutting a path short like this is pruning. Loaded with bpftool -d, the kernel reports processed 36 insns: 24 on the first path and 12 on the second.

Why 25 and not 12Slot 12 is a jump target, so it could be compared too, but the first path saved no state there. The verifier saves one only after at least two jumps and eight instructions since the last save (bpf_is_state_visited() in kernel/bpf/states.c, v7.2). On your first path that left slots 9 and 25.

A loop is a branch that jumps backwards. Since Linux 5.3 the verifier accepts a bounded loop, one whose last round it can see: it walks every round as more states. A loop whose bound it cannot see goes round until the walk hits the instruction limit, the one million this chapter opened with. The chapter on reading a rejection, next, shows what that looks like.

What the kernel knows about one register

Load as root with bpftool -d prog load and the kernel writes down every step. After each instruction it lists the registers that changed, in the form taken apart by the one-register figure (figure 4.3). The first word is the register type. A scalar is a plain number that may never be used as a pointer; map_value points into a value inside a map.

The rest of the entry is what the checks need. The value size, vs=8, is what every read through r0 is measured against. The id=1 is shared by every copy of this pointer, so a test on one copy clears the NULL flag on all of them. A scalar carries bounds instead: the key read back at slot 12 lies between 0 and 0xffffffff. How the kernel works out such bounds is the subject of the numbers chapter (chapter 6).

Hint 1 · direction

The walk follows the fall-through side of a branch first and keeps the jump side for later. A wide instruction counts once.

Hint 2 · mechanism

Hint 3 · nearly there

Recap

The verifier runs at load time and refuses any program it cannot prove safe on every path: a shape check over the jumps, then a walk that tracks a type for every register and stack slot. A map lookup leaves r0 as a pointer-or-NULL, and only a test on that path makes it readable. When a path reaches a saved state that covers it, the walk stops there, which is pruning; your program cost 36 instructions of walking, 24 and 12. Loops are walked round by round, and one million instructions is the end of the walk.

4.1

Eight paths, and as few as four walks. Each block doubles the routes, so 2 × 2 × 2 = 8. The walk follows one full path and keeps the other side of each block for later. When it comes back for one, that side ends at the next join if a saved state there covers it, which is likely, since nothing set in the blocks is read afterwards. That gives one full path plus three short arms. The saving rule in the margin note decides where states exist, so a cut can come a few instructions later than the join. The near-miss is six, two per block: the walk starts again from each kept branch, never from the program's start.

4.2

Because v and w are the same pointer to the kernel. The copy keeps the id the lookup gave, and when the test on w succeeds, mark_ptr_or_null_regs() (kernel/bpf/verifier.c, line 15706 in v7.2) clears the NULL flag on every register and stack slot with that id. The verifier page says the same in its paragraph on the id field. In your own log the id is the id=1 inside r0's entry. The near-miss is to think the kernel tracks only the register named in the test; clang copies pointers between registers all the time, and the id is what makes that harmless.

4.3

No. The verifier proves the six rows of the promise figure, which are about jumps, registers, NULL tests, bounds, calls and an end. Which key you count under is your program's business. Your program stores u32 pid = bpf_get_current_pid_tgid();, and the low 32 bits of that helper's result are the thread ID; the process ID is in the high half. Keying by bpf_get_current_pid_tgid() >> 32 counts per process. The near-miss is to read "loaded" as "correct": the verifier would accept either key, because both are just numbers stored on the stack.

4.4

Slot 1, *(u32 *)(r10 - 0x4) = w0, which writes the key before the call at slot 8 reads it through r2. The kernel's record shows those bytes as written: fp-8=mmmm????, where m means written and ? never written. The page's example without the store is rejected with "invalid indirect read from stack"; in v7.2 the wording is "invalid read from stack", at line 6725 of verifier.c. The near-miss is to think root is held to the same rule: a loader with CAP_PERFMON may let helpers read unwritten stack (bpf_allow_uninit_stack()), so test this rule as an ordinary user would hit it.

4.5

Because nothing after that point read the register on the saved path. If any later instruction had read it, the walk from the saved state would have been refused with !read_ok; it was accepted, so every instruction from there on writes the register before reading it. Whatever the current path holds in it is never looked at. In v7.2 this is the first test in regsafe(), kernel/bpf/states.c line 514, with the comment "explored state can't have used this". The near-miss is to expect "never written" to match only "never written"; the rule is looser on purpose, and pruning depends on it.

4.6

Because the only register that differs, r0, is written at instruction 4 before anything reads it. The two states are r0 = 1, r1 = 0 and r0 = 0, r1 = 0. From the checkpoint on, the program reads r1 and overwrites r0, so only r1 matters, and r1 is the same in both. Liveness tracking finds this and drops r0 from the saved state, after which the states are equal and the second arrival is pruned. Your own program has the same shape: the line from 9 to 12 in the lab solution lists no r0 at all. The near-miss is to compare the states register by register and call them different.
