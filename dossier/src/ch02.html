Chapter 2

Load, then attach

Your loader turns the object file into kernel objects in two steps. Load makes them exist and attach makes them run. One SEC() line decides what both steps do.

What your loader asks the kernel

The strace figure (figure 2.1) is your write counter's loader, run without sudo. It fails, and the failure is useful. The loader reaches the kernel only through one call, the bpf() system call, whose first argument names a command such as BPF_PROG_LOAD. Linux 3.18 added it in December 2014, together with maps.

The two-instruction programs are a test by libbpf, the C library your loader links against, which reads the object file, creates what it describes and attaches it. Your machine sets kernel.unprivileged_bpf_disabled to 2, so only a privileged process may load anything. The rest of this chapter follows the run with sudo.

From a section name to a hook

SEC("tracepoint/syscalls/sys_enter_write") does one thing in the compiler: it names the ELF section that the function's bytecode goes into. An ELF section is a named block of an object file. llvm-readelf -S on your object lists one under exactly that name, 216 bytes long, beside .maps, .rodata and license.

libbpf reads the name back and matches it against its own table, section_defs in tools/lib/bpf/libbpf.c (116 entries in v7.2), as the section-name figure (figure 2.2) shows for three of your exercises. The part before the first slash selects the program type: the kind of program, which fixes what it receives when it runs and which helpers it may call. The part after the slash names the hook.

Some program types also need an attach type: which variant of a hook the program is for. Your fork tracer's tp_btf prefix brings type TRACING with attach type BPF_TRACE_RAW_TP, fixed at load; your write counter gets its attach type only when it is attached. A prefix that matches no entry leaves the type unset, and libbpf stops before the kernel sees the program.

A typo after the slashMisspell the part after the slash, sys_enter_wrte, and everything still loads. The failure comes at attach, when libbpf looks the tracepoint up in tracefs: failed to determine tracepoint 'syscalls/sys_enter_wrte' perf event ID.

Load: the maps first, then the program

With sudo, the run goes on as the load-sequence figure (figure 2.3) shows. Your loader calls hashmap_bpf__open_and_load() from the skeleton, the header that bpftool gen skeleton wrote from your object, with the whole object inside it as bytes. Open parses those bytes. Load creates everything in the kernel: each map with BPF_MAP_CREATE, then each program with BPF_PROG_LOAD.

A map, formally, is a kernel object of keys and values that programs and user space both read and write. Your loader knows each map by a file descriptor. libbpf writes that number into every wide instruction that named the map, the zeros at slots 6 and 21 in the bytecode chapter (bpf_object__relocate_data(), libbpf.c line 6434). It also sets the instruction's source-register field to 1, BPF_PSEUDO_MAP_FD, which marks the constant as a descriptor.

Numbers before mapslibbpf 1.8, the version on your machine, picks each map's number before the map exists. At open it reserves a descriptor per map and patches the instructions with it; when BPF_MAP_CREATE returns, it moves the real map onto that number with dup3().

Your object has a second map that you never declared: bpf_printk's format string, in a read-only map named hashmap_.rodata that slot 13 points into. BPF_PROG_LOAD then carries the program type and all 27 slots. The kernel checks every path through the program, which is chapter 4, and swaps each descriptor for the map's address. check_and_resolve_insns() says so in its comment: "if it accesses map FD, replace it with actual map pointer".

The kernel hands back one more descriptor, for the program. The program is now loaded, and it still runs nowhere.

"In the load phase, libbpf creates BPF maps, resolves various relocations, and verifies and loads BPF programs into the kernel. At this point, libbpf validates all the parts of a BPF application and loads the BPF program into the kernel, but no BPF program has yet been executed."

libbpf Overview, "BPF App Lifecycle and libbpf APIs", Linux kernel documentation

Attach, and what keeps a program there

Attach connects a loaded program to its hook. For your tracepoint, hashmap_bpf__attach() reads the tracepoint's number from /sys/kernel/tracing/events/syscalls/sys_enter_write/id and opens a perf event on it with perf_event_open(). It then joins program and event with BPF_LINK_CREATE, attach type BPF_PERF_EVENT. The result is a link, a bpf_link in the kernel's terms since Linux 5.7: an object whose job is to hold one program on one hook.

Before linksOn kernels without links for perf events, the program was handed to the event with an ioctl, PERF_EVENT_IOC_SET_BPF, and nothing in the kernel held the attachment as an object. libbpf still falls back to it there (libbpf.c line 11569).

Every object in the object-model figure (figure 2.4) counts the references held on it. The link holds the program and the event, the program holds its two maps, and your loader holds descriptors for them all. When the loader exits, its descriptors close and the counts fall. Releasing the link is what detaches the program; then the program and its maps are freed, and the counter stops.

An object can also outlive every process. Pinning gives it a file name in bpffs, the BPF file system that Linux 4.4 added, mounted at /sys/fs/bpf on your machine. The file holds a reference of its own. sudo bpftool link pin id ID /sys/fs/bpf/wc keeps your counter counting after the loader exits, and sudo rm /sys/fs/bpf/wc stops it; from C, bpf_link__pin() does the same.

Recap

Everything your loader does in the kernel goes through the bpf() system call, driven by libbpf. The SEC() string is an ELF section name; libbpf matches its prefix against its table to pick the program type, and sometimes an attach type, and reads the hook from the rest. Load creates the maps, writes their descriptors into the wide instructions, and loads the program, which the kernel checks and rewrites with real map addresses. Attach creates a link that holds the program on its hook; the program runs while a descriptor or a pin holds that link.

2.1

27 and two. The kernel counts eight-byte slots, and the three wide instructions take two each: the section is 216 bytes, and 216 / 8 = 27. The two maps are write_counts and hashmap_.rodata, the read-only map that holds bpf_printk's format string; find them with grep map_name= strace.txt. The other BPF_MAP_CREATE and BPF_PROG_LOAD lines in the trace are libbpf's feature probes. The near-miss is 24, the number of instructions, or one map, because the .rodata map is easy to forget. (Derived from libbpf 1.8 and the v7.2 source; the lab's root script records the real lines.)

2.2

The program was loaded and never attached, so it has never run. Load only creates the program; it runs once a link holds it on its hook. sudo bpftool link show lists no link whose prog_id is the ID of count_writes. The usual cause is a loader that calls open_and_load() and skips attach(), or ignores the error attach() returned, for example for a tracepoint name that tracefs does not know. The near-miss is a bug in the program: a program that loaded has passed the kernel's checks, and this one updates the map on every run, so an empty map means no run at all.

2.3

libbpf's load step failed, before any BPF_PROG_LOAD, so the kernel never saw the program. tracepoints has an extra s. The table entry tracepoint+ accepts only the bare word, or the word followed by a slash, so no entry matches and the program type stays unset. libbpf refuses such a program in bpf_object_load_prog() (libbpf.c line 7939 in v7.2), with exactly that message. The near-miss is a missing tracepoint: a wrong name after the slash loads fine and fails later, at attach.

2.4

The plus means both forms are accepted: the bare word, or the word, a slash and extras that say how to attach automatically. A program in plain SEC("kprobe") still gets program type KPROBE and loads, but it names no function, so the skeleton's attach() skips it; your loader must attach it by hand, for example with bpf_program__attach_kprobe(). The rules are the two bullets at the top of the page, and libbpf's attach_kprobe() has the comment "no auto-attach for SEC("kprobe")". The near-miss is to expect a load error: the bare form is legal, it just does not attach itself.

2.5

BPF_PROG_TYPE_TRACEPOINT, reached by two section names, tp+ and tracepoint+, with the attach type column empty. So SEC("tp/syscalls/sys_enter_write") would give exactly the same program. The attach type your write counter ends up with, BPF_PERF_EVENT, appears only at attach, in BPF_LINK_CREATE, and so is not in this table. The near-miss is to read the empty cell as "cannot be attached": it means nothing has to be chosen at load.

2.6

Because they receive different things. tp_btf+ gives BPF_PROG_TYPE_TRACING with attach type BPF_TRACE_RAW_TP: the program gets the tracepoint's raw arguments, here two task_struct pointers, typed by the kernel's own type information. tracepoint+ gives BPF_PROG_TYPE_TRACEPOINT: the program gets the tracepoint's formatted record, which is why your write counter's argument is a struct trace_event_raw_sys_enter. The table puts the two prefixes in different rows, and the footnote for tp_btf+ gives its format. The near-miss is to treat tp_btf as another spelling of tp, as tp is of tracepoint.

Each matched trace line starts with the loader's PID. Before them come many short BPF_PROG_LOAD, BPF_MAP_CREATE and BPF_BTF_LOAD calls: libbpf's probes, and the type information of the next chapter. bpftool prog show prints count_writes with two map_ids, and bpftool link show a perf_event link that names the same program ID. After pkill, the pinned link keeps count_writes listed and the counts in write_counts keep rising; after rm, bpftool prog show name count_writes prints nothing.

What this shows. Load is the maps and the program; attach is perf_event_open and then BPF_LINK_CREATE, several calls later. The value size of 26 is the format string's length, the size of the .rodata section. The pin replaced the loader's descriptor as the link's last holder, and when it went, the link, the program and both maps went with it.

Common wrong turn. Taking every BPF_PROG_LOAD in the trace for yours; only one names count_writes. The other is running bpftool without sudo, which prints Operation not permitted on this machine.
