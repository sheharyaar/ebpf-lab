Every packet, copied

It is 1992, and a campus network is misbehaving. You run a network monitor on a SunOS workstation to find the one host at fault. You want a handful of packets, and the wire can deliver a new one every few microseconds. SunOS's capture facility, NIT, copies every packet into a kernel buffer and passes it up a chain of modules before any filter looks at it. In the measurements Steven McCanne and Van Jacobson of Lawrence Berkeley Laboratory published in January 1993, a packet that NIT's filter threw away still cost 136 microseconds, plus 210 nanoseconds for every byte in it.

Their answer was the BSD Packet Filter. In the same test it spent 4.6 microseconds on a rejected packet, whatever the packet's size. The difference is where the decision is made. BPF decides inside the kernel, on the packet where the network card left it, so a packet nobody wants is never copied.

Three ways to put code in the kernel

The three columns of the three-ways figure (figure 0.1) are the choices facing anyone who wants their own code to see what the kernel sees. A kernel extension is code added to a running kernel to change or watch what it does. The first column is the kernel module: compiled to machine code and loaded with the kernel's full power. A bug in it is a bug in the kernel, and it must be rebuilt for each kernel version.

The second column keeps your code outside. The kernel copies everything to a user-space program, which nothing you write can crash, at the price of one copy per packet. NIT stood close to this column.

The third column is the one McCanne and Jacobson chose. A filter is a small program, written for an imaginary machine, that the kernel runs on each packet to answer one question: keep it, and how many bytes of it.

Its safety comes from what the machine cannot do. It reads the packet and sixteen words of scratch memory, and nothing else. Its jumps only go forward, so every run reaches the end. A read past the end of the packet stops the filter and drops the packet. A wrong filter keeps the wrong packets, and the kernel carries on.

The tap and the machine

The tap figure (figure 0.2) redraws the paper's overview. When a packet arrives, the network driver calls BPF before the protocol stack sees it. BPF runs every listening program's filter on the packet, copies the bytes each filter accepted into that program's buffer, and hands control back to the driver. The place where the driver calls out is a hook: a point on the kernel's own path where it stops to run code attached there. Your write counter sits on a hook as well, at the entry to the write system call.

Section 3.3 of the paper describes the machine. It has an accumulator, the register most instructions read and write; an index register X; the scratch memory; and an implicit program counter. That machine is now called classic BPF. The paper draws its programs as a control-flow graph: instructions as nodes, jumps as edges, and in 1993 every edge pointed forward.

About 40 minutes · LINEAGE

Linux adopted the design in December 1997. Kernel 2.1.75 added the Linux Socket Filter, which attaches a classic BPF program to one socket, together with a check that runs before the kernel accepts the program.

"You simply create your filter code, send it to the kernel via the SO_ATTACH_FILTER ioctl and if you[r] filter code passes the kernel check on it, you then immediately begin filtering data on that socket."

Jay Schulist, Documentation/networking/filter.txt, Linux 2.1.75, December 1997
The first checkIn 2.1.75 the check was sk_chk_filter in net/core/filter.c. It tested three things: every jump lands inside the program, every scratch-memory index is below 16, and the last instruction is a return. Its comment reads "If we let some ugly filter code slip through kaboom!" Chapter 4 shows what the check grew into.

Thirty-two years on one page

The lineage figure (figure 0.3) carries the rest of the story, one row per change, with the chapter that covers it. The first group shows the machine leaving the network. Linux 3.0 began translating filters into x86-64 machine code in 2011, and Linux 3.5 let seccomp run classic BPF on system calls in 2012. In 2014 the machine itself was rebuilt, which is chapter 1.

Most rows after that add a hook or a kind of map. From 2018 the kernel describes its own types to programs, and from 2021 programs can call ordinary kernel functions.

Recap

There are three ways to run your own code where the kernel's data is: as a module with the kernel's full power, by having the kernel copy data out, or as a small program for a limited machine that the kernel runs itself. The 1993 BSD Packet Filter chose the third: a filter run in place on each packet, with forward-only jumps and nothing to read but the packet and its scratch memory. Linux adopted it in 1997 together with a check before attaching, and later used the same machine for system calls. Everything from 2014 on widens that machine.

0.1

About 346 microseconds, roughly 75 times BPF's 4.6. NIT's line in the paper's Figure 3 starts at 136 microseconds and climbs 210 nanoseconds per byte, so 136 + 0.21 × 1,000 = 346. BPF's line is flat: it spends 4.6 microseconds on a rejected packet of any size, because it reads only the bytes its filter tests, where the packet lies, and copies nothing. NIT copies the whole packet before any filter sees it, so its cost grows with every byte. The near-miss is to use the "accept all" numbers in section 2.2, about 6 and 89 microseconds: they measure buffering a packet you keep.

0.2

Thirty. Every classic BPF jump goes forward: the paper's jump fields are offsets from the next instruction, and Linux treats them as unsigned. A run therefore visits each instruction at most once and ends at or before the last one. The kernel can know this from the program text alone, by checking that every jump lands inside the program and that the last instruction is a return; in Linux v7.2 that is bpf_check_classic in net/core/filter.c. The near-miss is 4,096, the BPF_MAXINSNS limit: that caps the program's length. The forward jumps are what cap the steps.

0.3

The kernel requires the last instruction to be a return. bpf_check_classic in Linux v7.2 net/core/filter.c ends with the comment "Last instruction must be a RET code" and returns -EINVAL for anything else, at attach time, before any packet. Because jumps only go forward, every run ends at the last instruction or earlier. If that instruction is a return, every path produces a verdict; if it were a jump, a path could run off the end of the program with no answer and no next instruction. The near-miss is to think the filter ran and failed on a packet: the kernel refused it from its text, without running it.

0.4

Because memory traffic is the bottleneck, and most packets are rejected. Section 2.1 says the packet should be filtered "in place", where the network interface's DMA engine put it, so that a rejected packet costs only the bytes the filter read. SunOS's NIT copied every packet into an mbuf and then into a STREAMS message before its filter module saw it, so even unwanted packets paid for two copies. Section 3 adds the reason this matters: packet capture rejects far more packets than it accepts, so the cost of rejecting dominates. The near-miss is to answer "to save buffer space"; the paper's argument is about time spent copying.

0.5

A simulated stack and redundant work. Section 3.1 says CSPF's expression tree needs an operand stack, which on a register machine becomes loads, stores and pointer arithmetic in memory, the bottleneck again. It also says the tree often computes what it does not need: the tree for "IP or ARP" still evaluates the ARP test when the IP test is already true. A control-flow graph keeps values in registers and lets each test send the packet straight to its next step, so a packet answers only the tests on its own path. The near-miss is to name speed alone; the authors pin down where the time goes.

0.6

Two nodes, then TRUE. The root, ldh [12] and jeq #0x800, loads the Ethernet type and finds IP. The true edge leads to ld [26] and jeq #foo, which loads the IP source address, at byte 26 of an Ethernet frame, and finds foo. Its true edge goes straight to TRUE. That is four instructions and the return; the destination test at byte 30 and the ARP and RARP nodes never run. The near-miss is to count every node in the figure: a control-flow graph is walked along one path, which is why the paper prefers it to a tree.
